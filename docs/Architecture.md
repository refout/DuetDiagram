# 架构

## 分层

```
                 ┌────────── 入口层 ──────────┐
  GUI 画布/面板   内部 LLM   MCP stdio/HTTP   文件导入导出
        │            │            │              │
        └────────────┴────────────┴──────────────┘
                          │
                   ┌──────▼──────┐
                   │  DiagramCommandBus  │   ← 两条通路在此汇合
                   └──────┬──────┘
        校验 → 应用 → 版本/哈希 → 版本日志 → 审计日志 → 历史栈 → 广播
                          │
                   ┌──────▼──────┐
                   │ DiagramDocument (IR) │   ← 唯一事实源
                   └─────────────┘
```

「人和 LLM 能力对等」的落点就是这条汇合线：**命令之下没有任何东西知道变更来自谁**，
只有一个 `ChangeSource` 字段用于审计与变更高亮。

## 工具层

八个粗粒度工具（读、改结构、改外观、布局、组合、导出、校验、撤销重做）在 `DuetDiagram.Llm` 里
定义一次，模型侧与代理侧都从这一份派生。四十多条命令如果一条一个工具，模型每次调用前
都要在一长串名字里挑，而挑错的代价是一次失败往返；收成八个之后，模型先选"改结构还是改外观"，
再用 `action` 参数说明具体做什么。

三条约定：

- **参数约束进 schema，不只写在描述里。** 描述是给模型的建议，模型偶尔不照做；
  schema 里的正则约束则是在模型生成参数之后、命令层之前就被校验的硬条件。
  约束由参数上的标注回填进 schema，校验器读的是同一份 schema——约束怎么进去的、
  就怎么被读出来，分成两处之后会出现"约束看得见却拦不住任何东西"。
- **工具层不碰文档。** 每个执行体只做参数解析与分发，真正的变更走命令总线。
  绕开总线的话，撤销栈、版本号、审计日志与变更广播全都不经过，
  而这几样正是"人和模型能力对等"所依赖的东西。
- **定义只写一份。** 代理侧的工具由模型侧的函数派生，两侧指向同一个对象，
  声明不可能不一致。两边各写一份的话，某天升级依赖之后会静默分叉，
  表现为"模型能调通的工具代理调不通"。

## 上下文摘要

`diagram_read` 返回的是**归一化摘要**，不是文档本身。六块：节点、边、布局、锁定、
可用样式令牌、最近修改。同一份文档无论集合的插入顺序如何，摘要逐字节相同。

判据是**只注入决策所需的最小信息**，而不是"把文档转成文字"。所以摘要里
不含原始坐标、不含人工产物里的折点与固定位置、不含整份 DSL。多注入一样，
模型就会去用它——坐标每次重排都会变，模型照着它去调位置，学到的是一条不存在的能力。
位置只以「第几层」这种量化形式出现，而层号在图的形状不变时是稳定的。

四件事各有各的来路，只有第一样在 IR 里：

| 块 | 来路 |
|---|---|
| 节点、边、方向、调色板 | IR。令牌**实时**取自调色板，写死一份的话用户改了调色板之后模型会照着一个不存在的令牌去设样式 |
| 层数与同层分组 | 宿主的布局结果。工具层不引布局引擎，所以由宿主量化成层号传进来；没有的时候留空，**不自己按拓扑算一个** |
| 锁定列表 | 宿主。固定位置在人工产物里，摘要只收标识、不收坐标 |
| 最近修改 | 命令总线的版本日志。**不自己比较两次文档**——那样只能看到两次调用之间的差，而模型的调用间隔是不定的 |

文本由结构对象渲染，不另写一份：两者各写一份的话，改了一处忘了另一处，
模型看到的与程序读到的是两份不同的内容，而两边各自都自洽。
相对时间（"几分钟前"）需要一个参照时刻，由渲染时显式传入。

## 动作分发

`diagram_edit` 与 `diagram_style` 收到的 `action` 落到一条命令上。动作名到命令标识的
对照写在 `ActionTable` 里，**它是声明而不是从实现推出来的**：不记下来的话，
"这个动作到底改的是哪条命令"只能靠读实现，而读实现的人正是要核对这件事的人。
那张表与 `docs/Command-List.md` 里的对照表由用例逐行核，两边分头维护的话，
加了一条命令而忘了挂动作，表现是模型调用时得到「未知动作」——而命令本身是好的。

**一个动作一条命令，所以原子性是现成的。** 命令自己的 `Apply` 已经是原子的，
跨命令原子的场合现在没有。工具层不复制字段表：字段该不该写、值合不合法，
到了命令层还会再判一次，那一次才是权威的；复制一份的后果是命令层明明支持某个字段，
模型却总被工具层挡住，而两处各自都自洽。

命令被拒时返回的是**命令层的错误码**，不是工具层那一套。这两套分开是因为处置不同
（改文档还是改这一次调用），而"命令被拒"说的正是文档里的值不对——另起一套的话，
按命令层错误码建的修复建议表会漏掉所有经由工具层的失败。

三处**不这么写就会变成空话**的地方：

- **样式令牌的白名单是运行时判据。** 令牌表是文档里的数据，用户随时可以加一个，
  所以它进不了 schema 里那份写死的约束，只能在执行体里判；判不中时把可用的列出来，
  只回一句「没有这个令牌」的话，模型只能猜着重试。
- **`set-style` 与 `set-text` 靠字段前缀分。** 两者最终都走 `set-node-field`，
  前缀检查就是这两个动作各自唯一的那点语义。
- **幂等键不进参数表。** 它是调用侧的属性、与文档结构无关，进 IR 会让同一份文档
  在不同调用历史下得到不同的哈希；放进 schema 也不行，模型没有重试的概念。

## 错误回环与模型通路

`DiagramChatClient` 是内部模型那条通路：一次对话进来，工具调用出去，结果或失败回到模型手里。
工具调用循环**不自己写**——那是依赖里现成的，它已经处理了多轮往返、并发调用、最大轮数与终止条件；
这一层加的是两样依赖给不了的东西：工具走的是**注册表那一个入口**（与代理侧同一条），
以及**失败按结构化错误回灌**。

回灌的不是异常栈，是一条结构化错误：错误码、出错参数、可用取值、一句可执行的修复建议。
只有一句「参数非法」的话，模型只能靠猜重试，而每次重试都是一轮往返。

三件事定死了这一层的形状：

- **映射表放在一处，但它是两张表。** 界面上那张回答「怎么呈现给用户」，
  这一张回答「给模型看什么、怎么改」。App 不引用 `DuetDiagram.Llm`，放进 Core 又会让
  纯数据层认识上层名字，所以两张表各在一处，各自被一条逐行核对的用例兜住。
  修复建议表比呈现表多覆盖一套码：回灌给模型的失败里，命令层的前置检查与工具层的
  参数校验都会出现，而界面只看得到前一套。
- **可用取值不进表。** 可用的动作名、样式令牌、字段名、已登记的工具名都随文档与工具表变，
  静态表里写不出来。它们由失败现场填进错误自己的期望字段，信封上取的就是那一份；
  取不到才回落到表里——顺序反过来，模型会照着一份过期的取值去改。
- **同一个错误连着来第二次时，回灌的内容不一样。** 多一句「上一次这么改也不行」，
  不带的话模型会原样重试，表现是它卡在一个错误上反复撞。判据只比**上一轮**，
  不比整段历史：中间换过做法之后又绕回原来那一步，那是另一件事。

回环有次数上限（缺省三次，数的是回灌次数），到上限就停下并把整段往返记录写进应用日志，
同时把「别再试了」回给模型。上限挂在宿主那一侧而不是共享的注册表上：
「同一个错误连着来」与「这一轮试了几次」都是跨调用的状态，挂在共享对象上的话，
一个窗口的错误会算到另一个窗口的账上。

## MCP 服务端

`DuetDiagram.Mcp` 把注册表里那八个工具挂到协议上，供外部代理调用。两条传输：
标准输入输出（由客户端作为子进程拉起来，一个进程服务一个客户端）与 HTTP
（监听端口，一份凭据表挡在前面）。两条传输共用一份会话——文档、命令总线、变更广播，
以及调用方随请求带上来的声明。

挂上去的是**已经建好的工具实例**，不是按标注扫出来的静态方法：按标注那套要求参数由服务端容器解析，
而这条通路上服务端不持有容器，非基础类型参数会被当成工具参数，调用直接失败——
客户端只看到「调用出错」，原因只在服务端日志里。用实例还顺带保证代理侧与模型侧是同一份定义。

四件事定死了这一层的形状：

- **服务端不保存会话上下文。** 调用方把「我在编辑哪份文档、停在第几版」随**每一条请求**带上来，
  服务端每次现读。这是实测出来的性质（扩展位随每条请求携带，不只是会话建立那一次），
  也是这一层能做无状态的原因：连接断了重连、服务端换一个实例、甚至完全不保留上下文，
  同一个调用送出去的结果都一样。
- **声明的版本真的接到命令上。** 只把它记进日志等于没做：文档会被照着旧副本改掉，
  而两边都不报错。工具的执行体在发命令之前现读一次声明，翻成一次版本检查交给命令总线——
  带版本检查的通路上不带声明会被判成「缺少版本声明」，声明旧了会拿到冲突。
  读的是一个**委托**而不是一个值：它随每条请求变，而工具是按会话建一次、之后一直复用的。
- **标准输入输出下日志改道标准错误。** 标准输出被协议占用，一条日志写进去就会让对端解析失败，
  而症状是解析错误而不是超时，很容易被误判成消息格式有问题。标准错误也是那条传输下
  唯一的观察窗口，所以每条请求连同它带的会话状态各记一行。
- **网络那一档默认无状态。** 协议端点不在请求之间记任何东西，所以同一个请求发给哪个实例都成立，
  前面的负载均衡不必做会话粘滞。这是当前协议版本的缺省行为，代码里显式写出来，
  免得哪天缺省变了而这一层跟着悄悄变成有状态的。

自定义字段走**能力声明的扩展位**（`clientCapabilities.extensions` 与 `serverCapabilities.extensions`），
不放协议给自定义字段留的元数据位——那个位置在当前版本下没有入口。两个方向用的是**不同的字段名**：
调用方声明的是 `hasVersion`（我看到的是第几版），服务端应答的是 `serverVersion`（我这边是第几版）。
同名的话，一份应答被当成声明读回来时不会被发现，而那种错误的表现是
「服务端拿自己的版本去比自己的版本」，永远不冲突。

**不按会话建立请求的方法名做分支。** 当前协议版本用服务发现请求取代了早期版本里的初始化请求，
按名字匹配的代码会静默失效——服务端不报错，只是那条分支永远不走。
断言一律按「第一条请求」取样本。

### 网络那一档前面的那道关

四种拒绝各自一个状态码、各自一个错误码，因为它们要的处置完全不同：

| 拒因 | 状态码 | 错误码 | 调用方该做什么 |
|---|---|---|---|
| 凭据不认得、或者没带 | 401 | `MCP_UNAUTHORIZED` | 换一份凭据 |
| 凭据认得，但权限档只到读 | 403 | `MCP_FORBIDDEN` | 换一份能改的凭据，或者只做读的那些 |
| 一分钟里发得太密 | 429 | `MCP_RATE_LIMITED` | 按响应里的间隔退避重试 |
| 这一次写入注定冲突 | 409 | `VERSION_CONFLICT` | 按正文里那份差异追平，再照着重发 |
| 写入点名的图层不在允许范围里 | — | `LAYER_FORBIDDEN` | 换一个图层，或者让配凭据的人放开这一层 |
| 要打开的路径落在工作区之外 | — | `MCP_PATH_ESCAPED` | 换一个在工作区里的路径 |
| 单次调用超过时间预算 | — | `MCP_TIMEOUT` | 把活拆小一点重发；**文档一个字节都没改** |

**权限分两档，判在两处。** 粗的那一档是"能不能改这份文档"，判据是凭据的权限档，
只有传输层拿得到，所以它在那里判；细的那一档是"能改哪些图层"，而一次写入点名了哪个图层
藏在动作参数里（改节点归属时图层写在 `value` 上，建图层与改图层时写在 `id` 上），
只有解析过动作参数的工具层判得出来，所以它在那里判。两处合起来覆盖全部——
把细的那一档也搬到传输层的话，那张对照表就得抄一份，而抄漏的那一格会静默放行。

图层范围随请求放进会话的随异步流走的槽里，与版本声明同一个做法：工具表是按会话建一次、
之后一直复用的，权限存成值的话，第一条请求的图层范围会一直管着后面的每一条。

限流按**凭据**计数，不按来源地址：一个代理可能从多个出口发请求，而一个出口后面可能挤着
好几个代理，按地址算会让前者被无辜限制、后者互相掩护。窗口是滑动的，报出的重试间隔是
「最早那一次滑出窗口」的时刻——报一个比实际等待时间还短的值，调用方会在同一秒里再撞一次。

路径那道关的判据是**解析之后**的路径：先归一化掉 `..`，再解析符号链接，最后按目录边界比较。
只在字符串层做前缀比较的话，`..` 与符号链接这两种最普通的写法都能绕过去，而它们看起来完全正常。

时间预算在**发命令之前**检查。命令是同步的，中途取消观察不到，能给的保证是
「不会回一个超时响应、而那条命令还在后台把它改完」——那比放行还糟，因为调用方以为没改成。

审计记的是谁、什么方法、打到哪条路径、结果如何、花了多久。**凭据本身与完整文件路径都不进来**：
日志是最容易被复制走的东西，凭据进了日志谁都能拿去冒充，完整路径进了日志就把这台机器上的
目录结构画了出来。被挡下的请求也留一条——只记成功的调用等于没有审计，
而真正要看的是「谁在反复撞门」。

### 变化源

已连接的代理靠它知道文档什么时候变了：`GET /changes?since=<版本>`。有比 `since` 新的变更就立刻回，
没有就长轮询等到超时再回一个空响应。

**它不是协议那条推送。** 协议那条路在当前版本下走不通：无状态模式明文写着服务端主动发的消息
不支持（响应可能落到另一个进程上），而有状态那条路上唯一能拿到会话对象的入口是实验性接口、
它的空闲超时又被标为过时。所以这一条做成一条普通的只读端点，形状就是传输那一节说的长轮询。

**只保存最新的一份状态，不保存通知历史。** 于是断线重连按版本号补差：
调用方报上它见过的最后一版，服务端要么立刻告诉它现在是第几版，要么等。
存历史的话，一个断了一小时的调用方会把这一小时里的每一条都收一遍，
而它真正需要的只是「现在是第几版、结构哈希是什么」。

版本号与结构哈希在应答的那一刻一起从文档上读。分开读的话，两份值可能来自不同的版本，
而调用方拿它们是要去比对并据此决定重不重读的——对不上比不读还糟。

### 冲突时回什么

调用方报的版本与服务端对不上时，回什么内容由四种情形决定，分界是**能不能只回差异**：

| 情形 | 回什么 |
|---|---|
| 没声明版本 | 全量快照 |
| 版本相等 | 空差异（不是冲突，那条写入照常执行） |
| 落在版本日志范围内，且声明的结构哈希与当前一致 | 一份受影响元素清单 |
| 超出日志范围，或结构哈希对不上 | 全量快照 |

最后一种刻意退成全量，**尽管逐条增量算得出来**：走到那一步说明调用方声明的结构哈希与服务端对不上，
而它的本地副本是否还与它自己声明的那个版本对得上，从这边无从验证。把字段级的增量按在
一份来路不明的副本上，正是产生「静默改错」的方式——改完之后两边都不报错，而那份图已经与谁都对不上。
逐条增量仍然留给界面那条通路，它手里的副本是本地的，不存在这个问题。

网络那一档把这四种情形做成 **409 加正文里那份内容**。这一条判在协议之前，因为工具调用的失败
是协议内的结果，状态码那一层看不见它；只回一句「版本冲突」的话，代理只能整份重读再重试，
而重试大概率还是冲突。命令总线那一道检查仍然是说了算的那一道——这里判完之后到命令真正执行之间
还有个窗口，那个窗口里的冲突由总线在门锁内挡下。

撤销重做**不在这条路上**：它走历史栈，不接受也不检查声明。对着一个旧版本撤销是调用方自己的判断，
替它挡下来只会让它无从知道该怎么撤。

### 文档软锁

软锁管的是"哪个主体正在改这份文档"，与跨进程那把文档锁是两件事：那一把靠独占句柄、
抢不到就退只读，粒度是进程与文件；这一把靠时刻、到期自动放，粒度是文档。
合并的话，一个卡住的 agent 会让整个进程连只读都退不进去。

**到期判据是「最后一次操作」，不是「拿到锁的时刻」。** 只看拿锁时刻的话，
一个每二十九秒动一次的 agent 会被判成过期，而它其实正在写——于是两个 agent 同时以为
自己在改这份文档。所以持有者的每一次操作都要把那个时刻往前推；已经过期就续不上，
它要重新走一次拿锁，那时拿得到就拿得到、拿不到就知道有人接手了。

释放是懒的：到期的锁在下一个来拿的人看来就是空的，不另起一条清理线程——
那会多一处会在进程退出时卡住的定时任务。工作区只把锁摆出来，不在每条命令上自动拿它：
拿不到时该报错还是该排队只有宿主知道。

### Skill 与渐进式披露

三层，各层进上下文的时机不同，代价也不同：

| 层级 | 内容 | 什么时候进上下文 | 覆盖 |
|---|---|---|---|
| 工具描述 | 一句话做什么 + 何时用 + 限制 | 每一轮都在 | 约八成场景 |
| Skill 正文 | 操作顺序 + 常见错误 | 任务匹配上时 | 约一成半 |
| 资源文件 | 精确语法 + 罕见形状 | 写到那一步时 | 约半成 |

**第一层的代价与另外两层不同。** 工具描述每一轮都在，八条一起算，所以它只能是一句话——
撑到几百字的时候付出去的是每一轮的预算，而这件事看不出来，因为它表现为「内容更全了」。
描述里出现了编号顺序或者代码块，都是这一层被撑开的征兆。

两份 Skill 按 `skill://<标识>` 取：`diagram-workflow` 讲一次改动该按什么顺序走、
常见错误有哪些；`diagram-syntax` 讲语法从哪看。语法本身放在它的资源文件
`skill://diagram-syntax/dsl` 里，而那一份**就是** `docs/DSL-Syntax.md` 本身——
构建时作为嵌入资源随程序集走，不另抄一份。抄一份的话两边迟早对不上，
而对不上的表现是模型照着一份过期的语法写；接过来之后，「文档与实现不分叉」
由构造保证，再加上一条把里面每段例子交给真解析器跑一遍的门禁。

**「什么时候该取它」写进清单，不写进正文。** 清单是调用方唯一能据以决定取不取的依据；
没有它，调用方只有两个选择——全取，或者瞎猜。而全取等于把三层压成一层。
所以每份资源的说明里都有一句「要做什么的时候取它」，正文里则一个字都不重复。

**`skill://` 的路径判据与工作区那道关同一条口径：先解析，再判在不在根里。**
前缀比较挡不住 `..`，也挡不住百分号编码过的 `..`；而直接交给 URI 那一层去解析的话，
它自己会把 `..` 规范化掉——拿它的结果做判断，等于把要判的东西先擦掉了。
所以这里自己切段、先解码再归一、`.` 丢掉、`..` 弹一层，而**弹到 Skill 名那一层就拒绝**：
Skill 名就是这一层的根，越过去之后没有落点。

内部模型那条通路的入口是 `ChatOptionsFactory`，而它不认识 Skill 这种类型——
依赖方向是反的（代理那一层引模型那一层）。所以它收的是一段**纯文本**：
这一轮匹配上的正文，接在系统提示后面。选哪一份不在这里，只有调用方知道这一轮要做什么。

## 布局引擎的选型与已知缺口

**选型已确定**：`Mostlylucid.Dagre` 2.0.1 的**索引式布局入口**。
并排取证数据在 `reports/phase0a-layout.md`，复现命令：

```bash
dotnet run --project tools/Poc/LayoutCandidates -c Release
```

选它的原因是硬门槛：坐标必须是有界的。主选在那个判据上不成立——
同样 100 个节点、只多加了交叉边，主选算出的横向宽度从 1152 涨到 330248，
而备选在两个用例上都是 1044（加交叉前后完全不变）。

**四个已知缺口，必须由我们自建：**

| 缺口 | 影响 | 补齐思路 |
|---|---|---|
| 不支持固定位置 | 人工拖动的位置带不进下一次布局，手动微调形同虚设 | 布局后回填锚点，再按层做一次线性让位 |
| 不支持同层约束 | 表达不了"这两个是并列的" | 把同层组收缩成一个超节点参与布局，布局完成后再展开 |
| 不支持层内次序 | 表达不了"判定之后先走通过再走不通过"，连线交叉数随声明顺序漂 | 按给定次序把成员换位到它们自己占过的槽位上，再跑一次行内让位 |
| 不支持逐元素对齐 | 表达不了"这几个排成一列" | 在垂直于分层方向的那个轴上取齐；组里有固定成员时以它为准 |

四项都不是可以延后的细节：方案要求把人工拖动作为布局约束反馈，
缺口不补，用户的所有调整都会在下一次重排时丢失。

**补齐方案已经定下来并验证过**，完整设计、不变量与实测数据见 `docs/Layout-Constraints.md`，
结论已固化进正式工程：实现在 `DuetDiagram.Layout`，不变量测试在 `DuetDiagram.Layout.Tests`。要点：

- 无重叠是算法的必然结果，不是收敛目标。层内让位一次线性扫描精确可解。
- 同层组按展开后的总尺寸申报超节点，展开因此是纯局部操作，既不溢出也不挤压邻居。
- 让位方向垂直于分层方向，四个主方向都已验证。对齐轴与让位轴是同一个，理由相同。
- 约束作用在不同的自由度上（分层、层内左右关系、跨层的那个坐标），所以能同时成立；
  不能同时成立时如实报出来，不靠优先级悄悄丢掉一条。
- 节点的坐标一旦被移动，折线必须跟着重算；折线路由必须用空间索引，
  写成逐边遍历全部节点是平方复杂度，实测比索引化慢十倍。
- 补齐逻辑合计 5.3 毫秒（1000 节点、950 条边、250 个固定节点），
  引擎耗时是它的十倍以上。后续优化性能时应当先看引擎。

**实现时的注意事项：**

- 必须用索引式入口。默认入口在 1000 节点多层图上要 1204 毫秒，已经超出 1000 毫秒的预算。
- 建立图时必须传复合模式。非复合模式下布局主流程会抛异常，连四节点的菱形图都跑不完。
- 该库的说明文件与真实接口有多处不符（命名空间、构造函数签名），不要照抄说明写代码。
- 想知道某个能力支不支持，要看**行为**而不是接口里有没有同名字段。
  该库的节点类型里有坐标字段，但它们是算法的输出，写进去会被覆盖。

## 三条关键不变量

**1. 版本单调。** 每次成功且非空操作的命令都让 `DiagramDocument.Version` +1；
失败、被拒、`NoOp` 都不推进。撤销与重做也会推进版本 —— 版本描述的是**状态序列**，
不是「变更次数」。因此 `VersionLog` 的区间 `(from, to]` 永远可以完整重建状态。

**2. 结构哈希 ⟂ 视觉哈希。**
`StructuralHash` 只覆盖「谁和谁相连」+ `Parent`，决定是否需要重布局；
`VisualHash` 覆盖标签、形状、样式令牌，决定是否需要重绘。
两者都不覆盖 `Version` 与自身，避免自引用。
门禁：`Structural_hash_ignores_labels_but_visual_hash_does_not`。

**3. 一份文档在任一时刻只有一个写者。**
同一进程里由 `WorkspaceRegistry` 按标识共用同一份工作区——两个窗口因此是**同一份**文档，
不存在第二个副本；跨进程由锁文件的独占句柄定所有权，拿不到的那一份退成只读，
界面上所有写入口禁用，会话那一层再拒一次。
两套机制合起来的意思是：写者唯一，而「只读」不是一句提示，是一条能拦住写入的路。
门禁：`Category=DocumentLock`、`Category=MultiWindow`。
