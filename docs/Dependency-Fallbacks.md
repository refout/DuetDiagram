# 依赖备选方案

方案要求每个关键依赖至少有一个备选，并说明**触发条件**。
只有名字列在那里没有意义——出事的时候才去找备选，等于没有备选。

本文件对每一项给出：为什么选它、备选是什么、切换要改多少代码、
什么情况下切、以及**备选是否被实际验证过**。

## 产品依赖

### 界面框架：Avalonia 12.1.2

| | |
|---|---|
| 备选 | Avalonia 11 LTS |
| 切换代价 | 小。界面声明与代码结构基本不变，主要是版本号与少量接口调整 |
| 触发条件 | 12 版本在原生编译下不可用；或 12 版本出现影响使用的缺陷而短期不修 |
| 验证状态 | **主选已验证**：自检能脱屏渲染出图，冷启动约 700 毫秒。备选仅确认版本存在 |

方案原本就把它列为备选，这个安排是合理的：同框架的两个大版本之间，
代码层面的迁移成本远低于换框架。

### 绘图与文本：SkiaSharp 4.148.0

| | |
|---|---|
| 备选 | 无独立备选——它是界面框架的渲染后端，换它等于换框架 |
| 切换代价 | 不适用 |
| 触发条件 | 并入界面框架的判断 |
| 验证状态 | **主选已验证**：原生库能加载、能测量中英混排文本 |

这一项要如实说明：**它不是可独立替换的层**。
列在这里是因为方案把它单列成了选型行，但实际上它的可用性绑定在界面框架上。
如果它出问题，处置方式是换界面框架版本，而不是换一个绘图库。

### 布局引擎：Mostlylucid.Dagre 2.0.1

| | |
|---|---|
| 备选 | Sugiyama 0.12.2；Microsoft.Msagl 1.1.6 |
| 切换代价 | 中。布局适配层换实现，约束补齐逻辑不受影响——那部分在引擎之外 |
| 触发条件 | 该包停止维护；或实测出现无法绕过的坐标缺陷；或原生编译不通过 |
| 验证状态 | **两个候选都实测过**，见 `phase0a-layout.md` |

这是本项目**唯一一个换过主选的依赖**。原主选 Sugiyama 在带交叉的图上坐标失控
（20 节点就把合理宽度撑到 50 倍），改用 Dagre 后坐标有界、性能达标。

Microsoft.Msagl 是第三备选，尚未实测。它的定位是研究级实现，
能力全面但体积与复杂度都高得多，属于最后手段。

### 内部模型集成：Microsoft.Extensions.AI 10.7.0

| | |
|---|---|
| 备选 | 直接用网络客户端调兼容接口 |
| 切换代价 | 小到中。工具定义与调用编排要自己写，但接口本身是 HTTP + JSON |
| 触发条件 | 该包与外部代理侧的抽象不再兼容；或它引入我们不接受的依赖 |
| 验证状态 | **备选已实证可用**——对比测试的语料生成器就是直接调接口写的，跑通了 150 次调用 |

这个备选不是纸上谈兵：`tools/CompareHarness` 已经用它完成了整个语料生成，
包括重试、超时、用量记录。真要切换，那部分代码可以直接搬。

### 外部代理接入：ModelContextProtocol 2.2.0

| | |
|---|---|
| 备选 | 自实现 JSON-RPC |
| 切换代价 | 大。协议握手、传输、能力协商、会话管理全都要自己写 |
| 触发条件 | 官方实现与协议规范长期不齐；或它无法支撑我们需要的三种传输 |
| 验证状态 | **主选已验证**：三条传输全部可用，见 `phase0a-mcp.md` |

自实现是重活，但因为协议本身是 JSON-RPC 加一层约定，技术风险不高，只是工作量大。
真正会逼我们走这条路的情形是**官方实现在会话建立方式上再次变动**且长期不跟进——
本次已经遇到过它用服务发现请求取代初始化请求这件事。

### Mermaid 导入导出：Mermaider 0.12.2

| | |
|---|---|
| 备选 | 自实现词法语法；或只做导出不做导入 |
| 切换代价 | 中到大。解析器要自己写，但那本来就是方案里预期手写的部分 |
| 触发条件 | 方言兼容性不足导致导入失败率过高 |
| 验证状态 | 仅确认版本存在。**主选尚未做兼容性验证** |

这一项的验证缺口最明显：方案的风险登记册里写着"Mermaid 方言差异大｜中｜高"，
缓解手段是"宽松模式 + 原始片段保留"，但**没有实测过方言覆盖情况**。
方案把这件事排在 P1-08 到 P1-10，也就是说现在还没有数据。

## 开发期依赖

### 测试框架：xunit.v3 4.0.1

| | |
|---|---|
| 备选 | MSTest 或 NUnit。三者都支持当前使用的测试平台 |
| 切换代价 | 中。断言写法要改，但测试结构不变 |
| 触发条件 | 该框架在原生编译或新平台下不可用 |
| 验证状态 | 主选已验证（74 个用例） |

### 断言库：FluentAssertions 7.2.2

| | |
|---|---|
| 备选 | AwesomeAssertions 9.6.0；Shouldly 4.3.0；框架自带的断言 |
| 切换代价 | 中。断言语法要逐处改写，但这是机械工作 |
| 触发条件 | 升级到 8 版本需要商业授权而我们不打算购买 |
| 验证状态 | 主选已验证；两个备选仅确认版本存在 |

选 7.2.2 而不是最新版，原因就是许可：8 版本起改为商业许可。
这一点必须停留在文档里，否则将来有人顺手升级会踩到许可问题。

### 性能测量：BenchmarkDotNet 0.15.8

| | |
|---|---|
| 备选 | 自写计时循环 |
| 切换代价 | 小。但要自己处理预热、多次迭代、统计与噪声控制 |
| 触发条件 | 该工具在目标平台上不可用 |
| 验证状态 | 主选已验证，已产出性能基线 |

自写计时循环的代价常被低估：预热轮数、迭代次数、异常值剔除都要自己定，
定得不好会得出误导性的数字。本次实测就出现过短作业下误差棒比均值还大的情况。

## 后续阶段的依赖

### PDF 导出

| | |
|---|---|
| 主选 | 待定（方案的三个候选：QuestPDF、PdfSharpCore、位图嵌入） |
| 备选 | 三者互为备选 |
| 触发条件 | 许可、原生编译支持、或中文排版能力不满足 |
| 验证状态 | **未验证**，方案排在 Phase 4 |

QuestPDF 2026.9.0 与 PdfSharpCore 1.3.67 都真实存在。
QuestPDF 采用社区版/商业版双许可，**需要在选用前确认许可边界**，
这与断言库那一项是同类问题。

## 汇总

| 依赖 | 备选 | 备选是否验证过 | 切换代价 |
|---|---|---|---|
| Avalonia | Avalonia 11 LTS | 否 | 小 |
| SkiaSharp | 无（绑定框架） | 不适用 | 不适用 |
| 布局引擎 | Sugiyama / Msagl | **是（Sugiyama 实测不合格）** | 中 |
| 模型集成 | 直接调接口 | **是（已跑通）** | 小到中 |
| 代理接入 | 自实现 JSON-RPC | 否 | 大 |
| Mermaid | 自实现解析器 | 否 | 中到大 |
| 测试框架 | MSTest / NUnit | 否 | 中 |
| 断言库 | AwesomeAssertions / Shouldly | 否 | 中 |
| 性能测量 | 自写计时循环 | 否 | 小 |
| PDF 导出 | 三候选互备 | 否 | 中 |

**两个必须记在台账上的许可风险：**

1. **FluentAssertions 升到 8 版本需要商业授权。** 现已锁在 7.2.2，不要在升级时踩坑。
2. **QuestPDF 采用双许可。** 选用前需确认我们的使用方式落在哪一档。

**一个明显的验证缺口：**

Mermaid 方言兼容性完全没有数据。它的风险等级是"中概率、高影响"，
而验证被排在 Phase 1。如果方言覆盖不足，影响面比布局引擎那次更大——
布局引擎换掉只动了适配层，Mermaid 换掉会动到导入导出的整条链路。
