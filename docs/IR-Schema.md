# IR Schema

IR 是唯一事实源。本文件描述**当前已实现**的字段，以及尚未实现的部分。

序列化由 `DuetDiagram.Core/Serialization/DiagramJsonContext.cs` 的 AOT 源生成完成，
选项为 `camelCase` + 字符串枚举 + 忽略 null。

## DiagramDocument

| 字段 | 类型 | 可变性 | 说明 |
|---|---|---|---|
| `id` | `string` | 构造后只读 | 文档唯一标识 |
| `kind` | `DiagramKind` | `internal set` | `Flow` / `Flowchart` / `Block` / `State` |
| `direction` | `Direction` | `internal set` | `LR` / `TB` / `RL` / `BT`，方向的唯一来源 |
| `version` | `int` | `internal set` | 仅命令总线可递增；初始 0 |
| `structuralHash` | `string` | `internal set` | 见下文"哈希覆盖范围" |
| `visualHash` | `string` | `internal set` | 同上 |

### 九个集合

九个集合全部对外只读，修改只能通过命令。它们**共用一个命名空间**：
成员列表里的标识不区分它是节点还是组合，引用关系也都不带类型前缀。
因此新增任何定义之前都要用整体的标识占用检查，而不是只查自己那一个集合。

| 集合 | 元素类型 | 计入 |
|---|---|---|
| `pages` | `PageDef` | 视觉 |
| `layers` | `LayerDef` | 视觉 |
| `nodes` | `NodeDef` | 结构 + 视觉 |
| `edges` | `EdgeDef` | 结构 + 视觉 |
| `composites` | `CompositeDef` | 结构 + 视觉 |
| `tags` | `TagDef` | 视觉 |
| `actions` | `ActionDef` | **都不计**——只影响交互 |
| `fonts` | `FontDef` | **结构**——字体改变标签宽度 |
| `textPresets` | `TextStylePreset` | 视觉 |

除 `actions` 外，集合的**内容**都计入哈希。但**集合里的先后位置基本不进哈希**：
两个哈希都先把集合按标识排序再遍历，所以换个位置算出来的哈希一样。
真正表达次序的是各自的次序字段——图层看 `LayerDef.order`，页面看 `PageDef.order`，
泳道里的条带次序看 `CompositeDef.members` 的先后（那个列表本身就是内容，按顺序参与哈希）。

`LayerDef.order` 从 P4-02 起真的被消费了：渲染按它分档出笔，数值大的画在上面。
没有图层归属的节点（以及全部连线与组合）归一个**隐含的缺省层**，它固定在最底下，
所以每加一个图层都不会让那批元素莫名其妙地换前后。图层次序相同的文档由渲染层
用标识断掉并列，结果仍然确定。

两处例外要说清楚，因为它们容易被"换个位置反正哈希不变"这句话误伤：

- **边的集合先后决定绘制列表里边的先后。** 它进不了哈希，但绘制列表是逐条比的，
  所以它仍然是"同一份输入必须给出同一份输出"的一部分。撤销删边时按原索引插回，
  保住的就是这一条。
- **节点的集合先后什么也不表达。** 哈希按标识排序、布局在同层内按横坐标排序并在并列时
  用标识断掉、绘制虽然按集合顺序出笔但布局保证同层不重叠——三个可能观察到它的地方
  都看不见它。

### 三个子对象

| 子对象 | 类型 | 计入 |
|---|---|---|
| `palette` | `Palette` | 视觉 |
| `layout` | `LayoutHints` | **结构**——改了间距就必须重排 |

### 构造入口

| 入口 | 用途 | 版本号 | 哈希 |
|---|---|---|---|
| `new DiagramDocument(id, kind, direction)` | 新建空文档 | 0 | 空串（还没有内容） |
| `DiagramDocument.CreateFromContent(...)` | **按内容新建**，外部程序集唯一一条路 | 0 | 构造时算好 |
| `[JsonConstructor]` | 反序列化 | 取文件里的值 | 取文件里的值 |
| 命令总线 | 每次成功变更 | +1 | 重算 |

`CreateFromContent` 存在的原因是另外两条路外部都走不通：空文档构造没有集合参数，
而反序列化构造要求把版本号与哈希一并传入，哈希却要先有文档实例才算得出来，
setter 又是 `internal`——外部算得出、赋不进去。Mermaid 导入（P1-09）与 DSL 映射（P1-17）
都靠它产出文档。

三条限定，都是刻意的：

- **只造新实例。** 哈希的计算权仍然只有两处——命令总线，与这里构造时算的那一次。
  这条入口不提供改已有文档的路，否则它就成了绕过命令层的后门。
- **版本号固定为 0。** `version` 是变更计数，构造不是变更。
- **不检查标识唯一性。** 重复标识是可诊断的（`DUPLICATE_ID`），不是构造错误。
  在这里抛异常会让"造一份带重复标识的文档去测校验器"变得做不到，
  也会与反序列化路径不一致——那条路同样不检查。

### 快照

| 方法 | 行为 |
|---|---|
| `TakeFullSnapshot()` | 深拷贝所有集合与子对象，连同版本号与两个哈希 |
| `RestoreFromSnapshot(snapshot)` | 整体替换内容，**连版本号与哈希一起恢复** |
| `ApplySnapshot` | **未实现**，语义待澄清 |

`RestoreFromSnapshot` 恢复版本号而不是留给命令总线推进：这个方法的用途是
"把文档退回某个已知状态"，版本号如果被重新推进，退回去的那份内容就再也无法与历史上的
版本号对上，增量同步会失去参照。

快照的文档标识与目标不一致时抛异常。跨文档套用会得到一个自相矛盾的对象——
标识是甲的、内容是乙的。打开另一份文档应当新建实例。

## 各类型的字段

### NodeDef

| 字段 | 类型 | 默认 | 计入 |
|---|---|---|---|
| `id` | `string`（required） | — | 结构 |
| `label` | `string` | `""` | 视觉 |
| `shape` | `NodeShape` | `Rect` | 视觉 |
| `parent` | `string?` | `null` | 结构 |
| `layer` | `string?` | `null` | 视觉 |
| `styleToken` | `string?` | `null` | 视觉 |
| `style` | `NodeStyle?` | `null` | 视觉 |
| `text` | `TextStyle?` | `null` | 视觉 |
| `ports` | `IReadOnlyList<PortDef>` | 空 | **结构** |
| `richText` | `bool` | `false` | 视觉 |
| `mathMode` | `MathMode` | `None` | 视觉 |
| `desc` | `string?` | `null` | 视觉 |
| `meta` | `IReadOnlyDictionary<string,string>` | 空 | **都不计** |

**`label` 为空串是什么意思，没有定论。** 两个映射层（DSL 与 Mermaid）在原文没写显示文本时
**主动回退到标识**，所以从外部导入的文档里 `label` 不会是空串——除非原文明确写了空标签。

导出层按**字面**写：空串时写出 `A[""]`（渲染成空方框），不回退到标识。理由是这是一条真正的不动点——
回退会让 `A[""]` 在「导出 → 再导入」里变成 `A`，而往返的口径正是"同一份 IR 走一圈还是同一份 IR"。

代价是命令层或别处构造出的"没设标签"的节点会导出成空方框。彻底解决要先给这个字段定语义
（空串是"没有标签"还是"空标签"），或者把"没写"表达成 `null`。两种改法都要动 IR 契约与两个映射层，
所以留着没做。

### EdgeDef

| 字段 | 类型 | 默认 | 计入 |
|---|---|---|---|
| `id` / `from` / `to` | `string`（required） | — | 结构 |
| `fromPort` / `toPort` | `string?` | `null` | 结构 |
| `label` | `string` | `""` | 视觉 |
| `style` | `EdgeStyle` | 空 | 视觉 |

`Line` / `Arrow` / `StyleToken` 是 `style` 上的只读便捷属性，不是独立字段。
**这个形状与节点不同**：节点的样式令牌留在顶层，边则全部收在样式里。
不对称是方案本身的规定，改动它要同时改线格式。

#### 端点可以是组合

`from` / `to` 指向的可以是节点，也可以是组合（`GroupDef` / `LaneDef` / `SubflowDef` / `ComboDef`）。
分层架构图里 `ODS --> DWD` 拿分组当端点，说的是"这一层流向那一层"——
外部格式允许，Mermaid 语料里出现过**七份**（见 P1-09 的 `subgraph-as-endpoint`）。

**别把标识撞名也算进来。** 对比语料的 `parse-report.md` 在"端点是分组的边"一列上数出八条，
多出来的那条是 `c-dsl` 的 C02：模型把泳道与其中的一个节点都叫 `pay`，
那一列的判据是"端点标识与某个分组标识相同"，于是把它记成了组端点。
它实际指向的是节点，属于 P1-17 的 `group-and-node-share-a-name`，不是这里的证据。

**线格式没有因此改动。** 标识本来就是字符串，九个集合也共用同一个命名空间，
所以数据层本来就容得下它；改的只是校验器的端点解析（先按节点找，找不到再按组合找，
与成员列表同一口径）。

| 项 | 规则 |
|---|---|
| 端点解析 | 先 `FindNode`，再 `FindComposite`。两者都找不到报 `EDGE_SOURCE_MISSING` / `EDGE_TARGET_MISSING` |
| 端口 | **只属于节点。** 端点是组合时必须为空，否则报 `EDGE_PORT_ON_COMPOSITE` |
| 命令层 | `ConnectEdgeCommand` 用同一个判据，两层不得各写一份 |

**布局已经跟上。** 组合的包围盒由成员的最终坐标算出来（`CompositeOutline`），
端点落在组合上的边就落在那个盒子的边界上。盒子**不进坐标网格**——组合本来就罩着它的成员，
把它当成要绕开的障碍会让每条穿过这个分组的边都判成压过节点。
盒子的尺寸比真实的分组框小一圈（渲染时分组框还要往外留内边距与标题），
所以线会稍微扎进分组框一点——那一圈是渲染的事，布局不知道也不猜。

失败计数拆成了两项，因为处置不同：`EndpointFailures` 是端点没落在边界上（几何算错了），
`UnresolvedEndpoints` 是端点根本解析不出来（输入里有悬空引用）。两项都必须为零。

### CompositeDef 及其派生

抽象基类，派生 `GroupDef`（分组）、`LaneDef`（泳道）、`SubflowDef`（子流程）、
`ComboDef`（组合框）。多态标签写在 `$composite` 字段上。

| 字段 | 类型 | 计入 |
|---|---|---|
| `id` / `parent` | `string` | 结构 |
| `label` | `string` | 视觉 |
| `members` | `IReadOnlyList<string>` | 结构 |
| `direction` | `Direction?` | 结构 |
| `collapsed` | `bool` | 结构 |
| `style` | `NodeStyle?` | 视觉 |
| `localLayout` | `LayoutHints?` | 视觉（其约束内容另计结构） |

**成员关系的两处表达**：`CompositeDef.members` 与成员的父级字段（`NodeDef.parent`、
`CompositeDef.parent`）说的是同一件事。约定**以 `members` 为准**，父级字段是便于查询的冗余索引，
两者必须一致。校验见 `DiagramValidator`。

两处都要反向查：成员列表里列了谁、而那个谁的父级不是本组合，要报；
父级指向了某个组合、而那个组合的成员列表里没有它，同样要报。
只查前一个方向的话，"一个组合记着外层是谁、而那个外层的成员列表里根本没有它"这种文档
不会被报出来——解散那个外层时它也就不会被放出来，于是用户拆了一个分组，却发现里面少了一层。

**嵌套深度有上限**，见 `CompositeLimits.MaxDepth`（顶层组合是第 1 层）。
成环已经单独挡住，所以深度天然有界；上限要防的是**深而窄**的链——
一千层逐级嵌套的合法文档会让任何按层递归的遍历一路压到栈底。
上限只在那一处定义，命令层与校验器读的是同一个常量。

### 样式与端口

- `NodeStyle`：`fill` / `stroke` / `text` / `border` / `weight` / `radius` / `opacity` / `badge`
- `EdgeStyle`：`line` / `arrow` / `color` / `weight` / `route` / `labelPosition` / `styleToken`
- `TextStyle`：十六个字段，全部可空，逐层继承
- `PortDef`：`name` / `side` / `offset` / `isCustom`

`PortDef.isCustom` 区分自动端口与人工端口。不做这个区分的话，
用户手摆的端口每次重排都会跑回默认位置。

### 布局提示

四个约束列表，每项都带归属方与创建时间：

| 列表 | 值类型 |
|---|---|
| `sameRank` | `SameRankConstraint`（节点标识列表） |
| `order` | `OrderConstraint`（节点标识 + **出边标识**的有序列表） |
| `align` | `AlignConstraint`（节点标识列表） |
| `place` | `PlaceConstraint`（节点标识 + 参照物 + 关系） |

`OrderConstraint` 的次序项是**边标识**而不是目标节点标识：它的用途是减少连线的交叉，
而交叉是边之间的事，节点标识区分不了平行边（同一个终点可以有多条边）。
DSL 那边写的是节点名，转换在映射层做，见 `docs/DSL-Syntax.md` 的「映射阶段的规则」。

归属方取 `Auto` / `Llm` / `Human`，决定冲突时听谁的。
`LayoutHintsDefaults` 只提供返回新实例的 `Create()`，**不提供可变单例**。

## 哈希覆盖范围

### 判据不是"结构变了吗"

两个哈希回答的是两个问题：

| | 问题 | 变了要做什么 |
|---|---|---|
| `StructuralHash` | **现有坐标还有效吗** | 重新求解布局 |
| `VisualHash` | **画出来会不一样吗** | 重绘 |

按"结构变了吗"来理解会把三类东西漏在外面：布局提示改了间距、字体换了宽度、
端口挪了位置——都不改变图形拓扑，却都会让已算出的坐标失效。

名称保留为"结构"是历史原因，读的时候按"要不要重排"理解。

### 包含关系是构造出来的

视觉哈希先算结构部分的内容再追加外观部分，因此**结构哈希的每一次变化必然让视觉哈希变化**。
反过来不成立——只改颜色时结构不变而视觉变。

早先的实现里视觉哈希漏掉了节点的父级，于是"结构变了视觉却没变"。
那种不一致没有任何地方会报错，只能靠实现来保证。现在这条性质由构造方式保证。

### 具体覆盖

| 哈希 | 覆盖 |
|---|---|
| 结构 | `kind`、`direction`；节点 `id` / `parent` / `ports`；边 `id` / `from` / `to` / `fromPort` / `toPort`；组合 `id` / `parent` / `direction` / `collapsed` / `members`；字体全部字段；布局提示的间距与四类约束 |
| 视觉 | 结构部分的全部内容，加上节点 `label` / `shape` / `layer` / `styleToken` / `desc` / `richText` / `mathMode` / `style` / `text`；边 `label` / `style`；组合 `label` / `style` / `localLayout`；标签、文本预设、图层、页面、调色板、画布设置 |

### 三样刻意不覆盖的东西

1. **版本号**。覆盖它会让哈希随无关的版本推进而变化。
2. **约束的创建时间**。覆盖它，重复添加一条一模一样的约束就会触发一次全图重排。
3. **`actions` 与节点 `meta`**。它们只影响交互或由宿主自定义，改了不该引发重绘。

### 排序与规范化

按标识排序后拼接，保证与插入顺序无关（撤销后哈希必然回到原值）。

样式一类的子记录走序列化取规范化文本，**不是手写字段拼接**。
手写拼接的隐患是给记录加了字段却忘了同步改哈希函数，
于是那个字段怎么改都不会被判定为"画出来不一样"。走序列化则让新字段自动进入哈希。

## 一致性校验

`DiagramValidator.Validate` 做整体校验，用于加载外部文件、接收同步结果与测试断言——
这些入口不经过命令层。检查项：

| 码 | 含义 |
|---|---|
| `DUPLICATE_ID` | 标识在九个集合中重复 |
| `EDGE_SOURCE_MISSING` / `EDGE_TARGET_MISSING` | 边的端点（节点或组合）不存在 |
| `EDGE_PORT_MISSING` | 边指定的端口在节点上不存在 |
| `EDGE_PORT_ON_COMPOSITE` | 端点落在组合上，却指定了端口 |
| `LAYOUT_NODE_MISSING` | 布局约束引用的节点不存在 |
| `LAYOUT_ORDER_EDGE_MISSING` | 层内次序引用的边不存在，或不是主语节点的出边 |
| `PARENT_MISSING` | 节点或组合的父级不是已定义的组合 |
| `MEMBERSHIP_MISMATCH` | 成员列表与父级不一致 |
| `GROUP_MEMBER_MISSING` | 组合的成员既不是节点也不是组合 |
| `GROUP_CYCLE` | 组合的归属关系成环 |
| `COMPOSITE_TOO_DEEP` | 组合的嵌套深度超过上限 |
| `TAG_MEMBER_MISSING` / `ACTION_TARGET_MISSING` | 标签成员或动作目标不存在 |

这张表原先写的码名有六个是错的（`ID_DUPLICATE`、`EDGE_FROM_MISSING`、`EDGE_TO_MISSING`、
`COMPOSITE_PARENT_MISSING`、`NODE_PARENT_MISSING`、`MEMBER_MISSING`），
与 `ErrorCodes.cs` 对不上，而没有任何东西会报错。权威定义在
`DuetDiagram.Core/Commands/ErrorCodes.cs`，**这张表是手抄的副本，改码要两边一起改**。
下面「字段名与元数据」一节用登记表加门禁避开了这个问题，错误码还没走那条路。

校验只报告不修改。发现问题时由调用方决定是拒绝加载、丢弃问题部分，还是照常打开并提示。

## 字段名与元数据

`FieldChange.Field` 的取值来自 `DuetDiagram.Core/Model/FieldRegistry.cs`，**不得在调用处写裸字符串**。
错误码曾经在两处各写一份、名字不一致而没有任何东西会报错；字段名不走同一条路。

### 元素级与字段级

| 形态 | 含义 | 例子 |
|---|---|---|
| `@` 前缀 | **整个元素被增删** | `@node`、`@edge`、`@layer` |
| 无前缀 | **某个字段改了** | `label`、`shape`、`ports` |

前缀不是装饰。不加的话 `layer` 有两种读法：图层元素被增删，还是某个节点的图层字段改了——
靠 `ElementId` 也分不出来，因为标识本身不带类型信息。

### 每个字段的作用域

登记表给出每个字段的作用域，取值与哈希口径一致：

| 作用域 | 含义 |
|---|---|
| `Structural` | 改了要让坐标失效，必须重新求解布局 |
| `Visual` | 改了只需要重绘 |
| `Neither` | 只影响交互或由宿主自定义，两个哈希都不计 |

**同一个字段名在不同定义上必须同义。** 同名而作用域不一致的登记表在装载时会直接拒绝，
因为那意味着冲突判定与哈希口径会各按一半理解。

未登记的字段返回"未知"而不是猜一个作用域。猜错的后果是"改了它图没重排，看起来没生效"，
这类问题极难定位。

## 冲突判定

两组变更能否自动合并，判据只有一条：**两边有没有改同一个元素的同一个字段**。

| 情形 | 结论 |
|---|---|
| 元素不相交 | 直接合并 |
| 同一元素、不同字段 | 自动合并 |
| 同一元素、同一字段 | 冲突，交给人决定 |
| 一侧增删元素、另一侧修改该元素 | 冲突——增删与修改的前提互斥 |
| 两侧都增删同一元素 | 冲突——双方都认为自己是创建者 |

判定只做判定，不做合并。合并需要写回文档，而写回必须走命令层——
在判定处直接改文档会绕过版本推进、历史入栈与广播。

## 尚有缺口

| 项 | 说明 |
|---|---|
| `ApplySnapshot` | 语义待澄清。协作同步设计清楚之前不实现 |
| `PageDef` / `LayerDef` 的字段 | 方案只列出集合存在，未给字段。现取最小集合，等对应交互开工时再补 |
| 图层引用不存在的图层 | 节点上的 `layer` 指向一个不存在的图层时，命令层与校验器都不报（`DiagramValidator` 只查图层集合自身），渲染按缺省层处理。补一条校验记在 P4-02 的 followups |
| 页面、标签、动作的消费方 | 三样都能经命令层增删了，但渲染层与界面都还没读它们：翻页、标签着色、动作触发都还没有接线。IR 与命令先就位，是为了让「一份带页面与标签的文档能存下来、能往返」这件事先成立 |
| 多态序列化的标识符 | 目前每个多态体系各自用 `$` 前缀字段名，尚未统一约定 |

## 三样关系是单向的

标签的成员、动作的目标、调色板令牌的引用者，都是**从定义指向元素**的单向关系：
被指向的元素上没有任何回指字段。这带来三条后果，各自都写在了对应命令的说明里。

| 关系 | 删掉定义时 | 删掉被指向的元素时 |
|---|---|---|
| 标签的成员 | 不用清理，删掉的就是那份列表本身 | 整体校验器报 `TAG_MEMBER_MISSING` |
| 动作的目标 | 不用清理，目标引用挂在动作自己身上 | 整体校验器报 `ACTION_TARGET_MISSING` |
| 调色板令牌 | **挡住**，报 `PALETTE_ENTRY_IN_USE` 并列出引用者 | 不适用（元素只是少了一个引用者） |

前两行与第三行的差别就是那条判据「这件事有没有第二个地方能看见」：
悬空引用有整体校验器会报，命令层留着不管；而被删掉的令牌没有任何东西会报——
渲染层只是静默退回元素自己的样式，用户看到的是一批元素悄悄换了外观。

## 相关文件

Sidecar（`.dsl` / `.layout.json` / `.user.json`）的文件格式、完整性校验与失败处置见
`docs/Sidecar.md`。人工产物的固定位置在加载时转换为只读映射，
指向不存在元素的条目移入孤儿区——细节见该文件。

固定位置是用户「放这儿」的产物，与文档结构无关，因此**只在 sidecar 里、不进 IR，
也不走命令总线**：一次节点拖拽由宿主在松手时写入 `pinnedNodes` 并重做一次布局，
而不是发一条改坐标的 IR 命令。这样「拖动中不发命令」可以直接用总线历史条目数不变来验，
「松手只落定一次」用「固定恰好一个节点、重布局恰好一次」来验；撤销重做把整次拖动算一步。
