# 界面文字与多语言

这一层说三件事：界面上的字从哪儿来、语言怎么切、加一条字或加一种语言要动哪几处。

## 这一轮做到哪儿

**机制落地，界面文字迁了一部分。** 已迁的是「菜单这一条链」加上各块面板的静态标题：

| 已迁 | 处数 |
|---|---:|
| 菜单栏与工具栏的七个档名 | 7 |
| 菜单栏、工具栏与右键菜单的条目文字 | 25 |
| 条目不能点时的理由 | 13 |
| 快捷键与档名的拼法（两处格式串） | 2 |
| 面板标题与空提示 | 8 |
| 画布空提示 | 1 |
| 就地编辑器（字号、颜色、取消、完成） | 4 |
| 变更边栏的标题、空提示与展开/收起 | 4 |
| 导入对话框 | 2 |
| 布局失败对话框 | 4 |
| 人工调整恢复对话框 | 4 |
| 性能诊断面板的关闭按钮 | 1 |

合计 75 条键。第二语言（英文）翻了 74 条，**故意留一条没翻**：界面上的导出还没接上那句。
它是一条临时的占位理由，等导出接上之后会消失，现在翻它没有意义；顺带它当"缺的键要回落中性资源"那一条用例的对象。

**没迁的，以及为什么：**

| 没迁的 | 处数 | 为什么 |
|---|---:|---|
| 各面板的提示条与占位文字（代码里设的） | 约 600 | 它们是逐面板的细活，与机制无关；机制通了之后是机械的搬运 |
| 可访问名称（P5-05 那一层） | 50 | 标记里那 8 处要与代码里那 50 处一起迁，只迁一半会让那一层半新半旧 |
| 错误码呈现表 | 59 | 它同时被命令层与界面读，搬它要连着错误码那一层的口径一起动 |
| 导入报告 | 22 | 报告正文是按导入结果拼出来的，要先把句子改成带占位符的格式串 |
| 变更边栏的摘要与明细 | 12 | 同上：`最近一次：{命令}（{来源}），影响 N 处` 是拼出来的 |
| 样本文档内容与模板文件 | — | 那是**文档内容**，不是界面文字；用户存的文件里当然是他写的字 |
| 装置与命令行的输出 | — | 它们不是界面；`--selftest`、帧率基准、冷启动探针那些读数不进资源 |
| 异常消息 | — | 只给改代码的人看，界面上不会出现；界面上出现的失败提示走错误码呈现表 |

## 语言怎么切

语言是**显式指定的代码**，不是运行期文化：

```csharp
Strings.Language = Strings.English;   // 或 Strings.Chinese
```

**为什么不用 `CultureInfo.CurrentUICulture`。** 这一份程序集在**不变量全球化**下运行
（`InvariantGlobalization=true` 写在根目录的构建属性里，全仓生效）。实测：
`new CultureInfo("en-US")` 直接抛 `CultureNotFoundException`——「Only the invariant culture is
supported in globalization-invariant mode」；`CurrentUICulture.Name` 是空串。
所以按文化去找卫星程序集这条路在本仓根本走不通：**具名文化建不出来，卫星永远选不出来**。

**两个语言都在主程序集里。** 中性那份 `Strings.resx` 装中文，也是缺键时回落的那一份；
第二语言 `Strings.en.resx` 在项目文件里声明成 `WithCulture=false` 并显式给逻辑名，
于是它嵌进主程序集而不是生成卫星程序集。取的时候用
`new ResourceManager(baseName, assembly)` + `CultureInfo.InvariantCulture`，
全程不碰 `CurrentUICulture`。这条路在 `InvariantGlobalization=true` + 原生编译分析器下
构建 0 警告，也真的取得到两份不同的文字。

**换语言要在开窗口之前。** 界面文字在窗口搭起来的时候取一次，已经开着的窗口不会自己重取。
换语言是"下一次打开是什么样"，不是"当场改写"。当前没有任何界面入口改它——
这一层是**预留**，不是给用户用的多语言切换。

## 资源键是接口

- **一处文字一个属性，一个属性一个键。** `Strings` 上的属性是编译期接口（写错属性名编译不过），
  资源文件里的键是运行期接口（翻译者按键取那一句）。
- **整句一个键，不拼。** 带占位符的那几句走格式串：
  `menu.shortcut` = `{0}（{1}）`、`menu.entry-name` = `{0}：{1}`。
  在调用处拼"标签 + 左括号 + 快捷键 + 右括号"的话，换一种语序就拼不成句子了——
  而语序正是翻译要改的东西。同理，条目不能点时的理由也是**整句一个键**，
  不是"先选中"加一个宾语拼出来。
- **键名分段。** `menu.groupname.*` 是档名、`menu.*` 是条目文字、`menu.refusal.*` 是不能点的理由、
  `panel.*` 是面板、`richtext.*` 是就地编辑器、其余按功能名（`import`、`layout.failure`、`sidecar`、`diff`、`canvas`、`diagnostics`）。
- **缺的键回落中性资源；两边都没有直接抛。** 抛而不是返回键名：键名会原样显示在界面上，
  而"界面里出现一串英文键"看起来像界面坏了，实际是漏了一条资源。

## 档的标识与档名分开

菜单的七个档，`MenuGroups` 上的常量**是标识不是文字**：

```csharp
public const string Edit = "edit";                 // 标识：注册表按它分组，用例按它找控件
MenuGroups.Display(MenuGroups.Edit)                // 档名：按当前语言从资源里取
```

**为什么不合并成一个。** 档名原来是"编辑"这两个字，同时被当成身份用：注册表按它分组、
用例断言"工具栏上从左到右就是这四档"。把显示出来的字当身份用的话，换一种语言就找不到自己了——
`On(MenuSurface.Menu, "Edit")` 在中文下会返回空，而那种空看起来像"这一档没有条目"。

同一条口径也落在条目上：`MenuEntry` 的 `Id` 与 `Group` 是标识，`LabelKey` 是资源键，
`Label` 是按当前语言取出来的字。

## 加一条界面文字

1. 在 `DuetDiagram.App/Resources/Strings.resx` 里加一条 `<data name="...">`，键名按上面那套分段。
2. 在 `Strings` 上加一个属性：`public static string Xxx => Get("...");`
   （带占位符的用 `Format`，并加一个把参数收进来的方法，不要在调用处拼）。
3. 想翻的话在 `Strings.en.resx` 里加同名的一条；不加就是回落中文。
4. 代码里用 `Strings.Xxx`；标记里用 `{x:Static res:Strings.Xxx}`（见下）。
5. 跑 `Category=I18n`。

**标记里怎么引。** 属性值写 `Text="{x:Static res:Strings.PanelLayersTitle}"`，
并在文件头加 `xmlns:res="using:DuetDiagram.App.Resources"`。
`x:Static` 由界面标记的编译器在**构建期**解析：成员名写错会直接是构建错误
（试过写一个不存在的成员，报的是"无法解析为静态字段、属性、常量或枚举值"），
所以它不依赖运行期反射。

## 加一种语言

1. 在 `DuetDiagram.App/Resources/` 下加 `Strings.<代码>.resx`。
2. 在项目文件里给它声明 `WithCulture=false` 与 `LogicalName`（照 `Strings.en.resx` 那一份抄），
   否则它会变成卫星程序集，而卫星在不变量全球化下永远选不出来。
3. 在 `Strings` 上加一个常量与一份 `ResourceManager`，并把代码加进 `Languages`。
4. 跑 `Category=I18n`：键的对应关系、回落、未知代码被拒那几条都会自动覆盖到新语言。

## 门禁

`Category=I18n` 十条，各管一件事：

| 用例 | 管什么 |
|---|---|
| 每个键都有取用的人，每个取用的人都有键 | 资源与代码逐键对照，两个方向都查 |
| `Strings` 上每个属性都取得到 | 逐个属性取一遍，键名写错当场抛 |
| 注册表那几个文件里没有硬编码的界面文字 | 源码扫描，跳过注释与异常消息 |
| 标记里没有剩下的可见中文 | 源码扫描，跳过注释与可访问名称 |
| 换语言之后菜单与面板标题真的变 | 判据本身：变了，而且变成第二语言里那一句 |
| 第二语言里缺的键回落中性资源 | 用那条故意没翻的键验 |
| 认不出的语言代码被拒 | 写错一个字母不该默默退回中文 |
| 档的标识不随语言变 | 换语言之后按标识分组的结果一致 |
| 两处界面同一条目显示同一个字 | 菜单与工具栏不许各取各的 |
| 从右到左是同一份布局绕竖中线翻过来 | 逐块比尺寸与位置，见下 |

## 从右到左

不变量全球化下文化给不出"这是从右到左"，所以用例直接设 `FlowDirection.RightToLeft`。

判据是**镜像之后逐块对得上**：尺寸不变、位置正好是绕窗口竖中线翻过来的、
本来就放得下的翻过来也放得下。判据**不是**"每块都在客户区里"——这个窗口尺寸下左栏本来就装不下
（900 × 600 的客户区里，左栏五块面板加起来比它高，模板、调色板与文本预设三块的底边都超过了客户区），
而那种溢出左右两个方向一模一样，与方向无关。

**量矩形要量两个角。** 从右到左不是把每个控件挪个位置，而是给整棵树挂一层镜像：
镜像之下左上角量出来的那个点已经跑到框的右边去了，再往右加一个宽度，
得到的是一个真实位置上不存在的框——左栏会被算成"越出右边界"。
量两个角再归一化，左右两种方向下都得到真实占位。

## 已知取舍

| 项 | 说明 |
|---|---|
| 只有中文与英文两种 | 英文是**用来证明这条路通**的，不是交付一份译文；它自己也没有经过母语者校对 |
| 界面文字只迁了一部分 | 见开头那张表；机制通了之后剩下的是机械搬运 |
| 没有界面入口换语言 | 这是预留，不是给用户用的多语言切换；将来要做的话入口在程序启动参数上 |
| 换语言不重画已开的窗口 | 文字在窗口搭起来时取一次。要做"当场改写"得把每一处文字变成可通知的属性，那是另一件事 |
| 没有按语言变格式与复数 | 数字、日期、复数的写法不在这一层。不变量全球化下连 `CultureInfo` 都建不出来，那要先把全球化模式打开 |
| 排版不随语言变 | 字号、行高、控件宽度都是按中文调的；英文更长的地方会换行或截断，没有按语言调过 |
