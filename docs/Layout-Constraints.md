# 布局约束补齐方案

## 要解决的问题

布局引擎不支持两项约束，而这两项是"人工拖动作为布局约束反馈"的实现基础：

| 缺口 | 后果 |
|---|---|
| 不支持固定位置 | 用户拖好的节点在下一次重排时弹回原位，手动微调形同虚设 |
| 不支持同层约束 | 表达不了"这两个是并列的" |

方案：**两项都在引擎之外补齐**，不改引擎，也不要求引擎配合。
引擎始终只看到一张合法的分层图。

## 三个待定问题的决定

### 一、让位是否保证无重叠

**是。而且是算法的必然结果，不是收敛目标。**

推导：分层布局里层与层的纵坐标本来就不同，跨层重叠只可能由固定节点的自由纵坐标引起；
让固定节点作为障碍物参与到它纵向相交的每一层的让位中，层的划分就不再漏项。
层内让位是一条直线上的排布，一次扫描精确可解。所以不存在"差一点分开"的中间状态。

**唯一的例外是两个固定节点互相压住**——两个都不可动，任何一方让步都违背用户意图，
这是输入矛盾，只能如实报出（见下面的不变量表）。

**前置约束：固定节点之间的重叠应当在写入侧阻止**，也就是拖动时不允许把一个节点放到
与另一个已固定节点重叠的位置。理由是把一个无解的输入喂给布局系统，
事后兜底要比在门口拦住贵得多——兜底意味着要么悄悄挪动用户放好的节点，
要么给出一张明显坏掉的图。

**关键设计决定：让位只把自由节点往右推，保持层内相对次序。**

- 次序本身有语义：它决定连线的交叉情况和视觉上的阅读顺序。
- 打乱次序比整层变宽更糟。变宽只是占地方，乱序会让人看不懂图。
- 副作用是某一层可能被推得很宽。这是可以接受的代价，而且用户能看到原因
  （那一层的某个节点被钉在了左边）。

### 二、同层组展开放不下怎么办

**这个问题在正确的做法下不存在。**

收缩成超节点时，超节点的尺寸按**展开后的总尺寸**申报：

```
宽度 = Σ 成员宽度 + 间隙 × (成员数 - 1)
高度 = max(成员高度)
```

引擎按这个尺寸为它预留空间，展开时就只是把预留好的矩形切成几份填上——
既不溢出，也不会挤压邻居。**展开是纯局部操作，不需要做任何避让。**

这正是分层布局引擎内部处理跨层长边的标准手法（给跨层的边插入虚拟节点并申报尺寸），
我们只是把同一手法用在同层组上。反过来，如果只按"一个节点"的尺寸申报，
引擎会按一个节点宽度的空间来排，展开成三个必然横着压到邻居身上，
那时候再想补救就只能靠挤压，而挤压会连锁。

**边的处理**（容易漏的地方）：

| 情形 | 收缩时 | 展开时 |
|---|---|---|
| 组内成员之间的边 | 从收缩图中移除 | 按原端点还原 |
| 组外指向成员的边 | 改指超节点 | 按原端点还原 |
| 多条边改指后端点相同 | 去重，但不丢记录 | 逐条按原始端点还原 |

组内边必须移除，否则会变成超节点指向自己的自环，引擎会拒绝或者给出无意义的结果。

### 三、补齐逻辑的耗时上限与降级

**上限 100 毫秒，只约束补齐逻辑本身，不含引擎耗时。**

之所以把两者分开计：出问题时必须能立刻判断是引擎慢还是我们自己的算法慢，
这两者的处置方式完全不同——前者要换引擎，后者要改我们的算法。
把引擎耗时算进补齐预算，会让"补齐是否够快"这个判断失去意义。

**信任来自实测而非估算**：1000 节点、950 条边、250 个固定节点的压力用例上，
补齐逻辑合计 **5.3 毫秒**（收缩 0.04 + 展开回填 0.21 + 行内让位 0.31 + 折线重算 4.7）。
其中折线重算占九成，它一开始是 48.7 毫秒，改用空间索引后降下来的——细节见后文。

**超限的处置沿用已有的布局失败策略**，不新造一套：保留上一次成功布局、
状态栏提示、给出重试 / 手动布局 / 简化图三个选项。

## 算法

```
输入：节点（含可选固定坐标）、边、同层组、方向、间距

1. 收缩        同层组 → 超节点（尺寸按展开后总尺寸申报，记录边与组内边）
2. 引擎        按合法分层图求解析坐标
3. 展开        超节点矩形切分填回成员（纯局部操作）
4. 回填        把固定节点搬到目标坐标
5. 行内让位    逐层一次线性扫描，把自由节点排到障碍物之外
6. 折线重算    按最终坐标重新路由每条边
```

第 4 步与第 5 步分开是为了让偏差检查可以独立进行：
只要第 4 步之后偏差不为零，就说明回填写错了，与让位逻辑无关。

第 6 步不可省：引擎返回的折线是按它自己算出的坐标画的，节点被第 4、5 步移动之后，
那些折线就指向了旧位置——看起来是线从节点旁边擦过去，或者悬在半空。

### 行内让位

算法在"层沿纵轴排列"的坐标系里描述，左右方向的布局在进入前把横纵坐标对调、
出来后换回，因此只有一份实现。

```
对每一层：
  障碍物 = 与该层纵向相交的全部固定节点（按横坐标升序）
  成员   = 该层的自由节点（按原横坐标升序，保持次序）
  cursor = -∞
  对每个成员：
     x = max(原横坐标, cursor)
     从左往右扫障碍物：
       若障碍物整体在 x 左侧 → 跳过
       若障碍物整体在 x 右侧 → 停止扫描（后面的更靠右）
       否则 x = 障碍物右边界 + 间隙，继续往后
     放置成员，cursor = x + 成员宽度 + 间隙
```

扫描是单向的，因为让位只会把节点往同一个方向推，已经扫过的障碍物一定落在当前位置之后。
每层一次线性扫描，不需要迭代。

**为什么不用"发现重叠就互相推开"的迭代做法**：迭代收敛慢、结果依赖遍历顺序，
而且必须限制轮数因而可能半途而废，留下一个"差不多分开了"的状态。
直线上的排布是精确可解的，用蛮力逼近它是把简单问题做复杂。
（实测对比：迭代做法在压力用例上要么把节点推离本层，要么在预算内留下近五百处重叠。）

### 让位方向必须随布局方向改变

层内让位的推挤方向是**垂直于分层方向**的：

| 布局方向 | 层的排列 | 层内让位方向 |
|---|---|---|
| 自上而下 / 自下而上 | 层上下叠放 | 横向 |
| 从左到右 / 从右到左 | 层左右并排 | 纵向 |

推错轴会把节点推出它所在的层，分层结构当场就散，而这种情况在上下一维的测试里完全看不出来。

注意这与"层的推进方向"无关：自下而上和自上而下的层内阅读方向都是从左往右，
所以两者用同一个方向让位。RL 同理。

### 边的折线重算

折线走的是分层布局的常规路径：从起点朝向终点的那条边出去，
在两层之间的空隙里走一段，再从对面进入终点。**拐点走空隙**是关键——
那个区域天然是空的，只要不被固定节点占用，横向段就不会压到任何节点。

固定节点的纵坐标是自由的，可能正好卡在两层之间把空隙切碎。
所以挑拐点位置时先把被占用的区间减掉，在剩下的空档里取最宽的一段的中点。
这是精确计算而不是采样试探：采样会漏掉窄但可用的空档，而且结果依赖采样点数量。

空隙被占满时退回中点并计入"穿过节点"的计数，**不假装绕开**：
一条看起来能走通但实际压过节点的折线，比一条明确报告有冲突的折线更难排查。

**性能上必须用空间索引。** 最初写成对每条边遍历全部节点，这是平方复杂度：
950 条边乘 1000 个节点，实测 48.7 毫秒，和布局引擎本身一个量级。
改成均匀网格索引之后降到 4.7 毫秒。

不用"按层分桶"是因为固定节点的纵坐标是自由的，层结构在它那里是断的，
按层分桶会把锚点归到错误的桶里导致查询漏项。网格只依赖坐标，与层结构无关。

查询结果写进复用缓冲区、去重用代次数组、格子遍历用嵌套循环而不是带状态机的迭代器——
这三件事合起来把每次查询的分配降到零。每条边新建一次集合的话，
千条边就是几千次分配，光回收就抵掉了索引省下的时间。

## 不变量

| 不变量 | 性质 | 说明 |
|---|---|---|
| 固定节点坐标与目标值误差为 0 | **硬保证** | 用户显式声明的意图优先于任何自动计算 |
| 自由节点不与固定节点重叠 | **硬保证** | 由让位算法保证，不是收敛目标 |
| 自由节点互不重叠 | **硬保证** | 层内次序保持且不重叠；让位只在一个轴上移动，不跨层 |
| 同层组成员纵坐标极差为 0 | **硬保证** | 由收缩尺寸申报正确保证 |
| 节点数与边数守恒 | **硬保证** | 收缩与展开必须互逆 |
| 让位方向垂直于分层方向 | **硬保证** | 推错轴会把分层结构推散 |
| 折线端落在两端节点的边界上 | **硬保证** | 落在内部是从节点身子里钻出来，落在外部是没接上 |
| 折线穿过其它节点的边数 | **质量指标** | 空隙被占满时无路可走，如实计数而不是假装绕开 |
| 两个固定节点互不重叠 | **前置条件** | 由写入侧阻止，布局阶段无法解决 |
| 布局结果可重复 | **硬保证** | 遍历顺序全部固定，不使用哈希表遍历顺序 |

"两个固定节点互不重叠"作为前置条件而不是布局职责，是本方案最重要的一个取舍：
**承认有些输入是无解的，并在数据进入系统的入口挡住它。**

## 验证结果

**本文件记录的是方案与推导过程。** 实现在 `DuetDiagram.Layout`，不变量测试在 `DuetDiagram.Layout.Tests`——
当初用于验证的脚手架已删除，避免两份实现分叉。

| 用例 | 结果 |
|---|---|
| 基础菱形（无约束） | 无重叠，补齐逻辑不改变引擎结果 |
| 固定节点在重排后保住 | 偏差 0，坐标精确 |
| 固定节点挤开自由节点 | 自由节点被挤走，固定节点不动，无残留重叠 |
| 同层组 | 纵坐标极差 0，展开后横向间距 116，无重叠 |
| 同层组加固定节点 | 两项约束同时成立 |
| 两个固定节点重叠（矛盾输入） | 两个都不动，如实报出残留重叠 |
| 让位之后重算折线 | 18 条边全部端点贴合、零穿越 |
| 四个方向各跑一遍 | 让位方向全部垂直于分层方向，偏差 0，无残留重叠 |
| 1000 节点 / 250 个固定节点 | 偏差 0，无残留重叠，端点在边界上，补齐合计 5.3 ms |

规模用例的耗时分布（1000 节点、950 条边、250 个固定节点）：

| 阶段 | 耗时 | 占比 |
|---|---:|---|
| 收缩 | 0.04 ms | — |
| 展开回填 | 0.21 ms | — |
| 行内让位 | 0.31 ms | — |
| 折线重算 | 4.7 ms | 89% |
| **补齐合计** | **5.3 ms** | 100% |
| 引擎（对照） | 52 ~ 95 ms | — |

**引擎仍然是绝对的大头，但折线重算占了补齐逻辑的九成。**
后续要继续压低开销，先看引擎；若只看补齐逻辑，那么该优化的是折线重算。

### 一个已知的、可解释的穿越

规模用例上有 50 条边（共 950 条）穿过其它节点。原因已经定位清楚，**不是路由缺陷**：

用例把第五层的节点钉到了第一层的条带上，也就是钉到了与它自然层号不同的位置。
于是"第四层 → 第五层"这五十条边必须从第四层一路走到第一层，穿过中间三层的节点。
其余五十条边连接的是相邻层，没有穿越。

也就是说：**锚点把节点拉到别的层时，连到它的边必然穿过中间的层。**
这是锚点语义的直接后果。要在视觉上消掉它，需要让纵向段也走"列间空隙"而不是直接垂直穿过，
那是一个完整的多通道布线算法，不在本轮范围内，记为后续工作。

## 尚未验证

| 项 | 说明 |
|---|---|
| 固定节点数量极大时（例如全图八成节点都被固定） | 压力用例只覆盖了四分之一，更高比例下让位会把层推得很长，实际效果需要单独评估 |
| 真实拖动的分布 | 本次用的是构造出来的输入。真实用户拖动的位置更零散，可能出现构造用例覆盖不到的组合 |
| 逐元素对齐约束与层内顺序约束 | 方案要求的另外两项约束，两个候选引擎都没有入口，本方案未覆盖 |
| 锚点跨层时的折线 | 已知会产生穿越，需要多通道布线才能消掉，见上文 |
| 布局参数变化后的重排 | 本次每次都从零布局，没有验证增量更新（只改动局部时能否复用上一次结果） |

## 实现注意事项

1. **让位方向要随布局方向改变。** 层上下叠放时横向让位，层左右并排时纵向让位。
   做错了会破坏分层结构。用坐标换轴复用同一份扫描逻辑比写两套实现更不容易出错。
2. **障碍物的判定要按垂直于分层的那个轴相交，而不是按层归属。** 固定节点的自由坐标
   可能正好卡在两层之间，只把它算进"最近的那一层"会让另一层的节点被推过去压在它身上。
3. **让位不得改变层内次序。** 实现上体现为"只朝一个方向推"，绝不能反向推。
4. **折线必须跟着重算。** 引擎给的是按旧坐标画的线，节点一动那些线就全废了。
5. **折线路由必须用空间索引。** 写成对每条边遍历全部节点是平方复杂度，
   实测 48.7 毫秒；加索引后 4.7 毫秒。索引不要按层分桶——固定节点会破坏层结构。
6. **重叠与穿越的统计不要放进热路径。** 验证用的两两比较是平方复杂度，
   在规模用例上比整个让位算法还慢两个数量级。生产实现里若需要，应当用扫描线做到 O(n log n)，
   或者只在诊断模式下开启。
7. **分阶段计时要分开，不要合并。** 只记总耗时会在排查时失去全部线索——
   引擎慢要换引擎，补齐逻辑慢要改算法，处置完全不同。
