# 布局约束补齐方案

## 要解决的问题

布局引擎不支持四项约束，而这四项是"人工拖动作为布局约束反馈"的实现基础：

| 缺口 | 后果 |
|---|---|
| 不支持固定位置 | 用户拖好的节点在下一次重排时弹回原位，手动微调形同虚设 |
| 不支持同层约束 | 表达不了"这两个是并列的" |
| 不支持层内次序 | 表达不了"判定之后先走通过再走不通过"，连线交叉数随声明顺序漂 |
| 不支持逐元素对齐 | 表达不了"这几个排成一列" |

方案：**四项都在引擎之外补齐**，不改引擎，也不要求引擎配合。
引擎始终只看到一张合法的分层图。

前两项在 Phase 1 落地，后两项在 Phase 2 落地。两类之间没有依赖：
它们作用在不同的自由度上——分层、层内左右关系、跨层的那个坐标——
所以能同时成立。不能同时成立时由求解器如实报出来，而不是靠优先级丢掉一条。

## 第四类约束：相对位置

IR 里的约束列表后来多了一类**相对位置**（`LayoutHints.Place`）："这个节点在那个节点的某一侧"。
它与上面三类的作用方式不同，所以**它有自己的命令，而不并进按组增删的那两条**。

| | 同层 / 对齐 / 层内次序 | 相对位置 |
|---|---|---|
| 形状 | 一组平级的成员（层内次序是有主语的一组出边） | 一对节点加一个方向 |
| 数量 | 同一主语上可以有多条互不相同的 | 同一对节点、同一归属方只该有一条 |
| 增删 | 加一条、删一条 | 设置一条（再设一次是替换）、清除一条 |

最后一行是它单列命令的原因：前者的"增"与"删"是两个动作，后者的"设置"与"清除"是同一个动作的
两个方向。硬凑进按组增删那两条命令的话，调用方要表达"把这个节点摆到那个节点右边"，
得先构造一条规格再判断该调增还是调删，而那个判断本来就在命令里。

**求解器现在还不消费这一类约束。** 它进结构哈希、进整体校验、进降级计划的计数，
但不改变任何坐标——降级计划只投影同层、层内次序与对齐三类。
也就是说调用方设完之后节点不会动，这一点必须让调用方知道，
否则它会把"命令没生效"当成一次失败。

## 三个待定问题的决定

### 一、让位是否保证无重叠

**是。而且是算法的必然结果，不是收敛目标。**

推导：分层布局里层与层的纵坐标本来就不同，跨层重叠只可能由固定节点的自由纵坐标引起；
让固定节点作为障碍物参与到它纵向相交的每一层的让位中，层的划分就不再漏项。
层内让位是一条直线上的排布，一次扫描精确可解。所以不存在"差一点分开"的中间状态。

**唯一的例外是两个固定节点互相压住**——两个都不可动，任何一方让步都违背用户意图，
这是输入矛盾，只能如实报出（见下面的不变量表）。

**前置约束：固定节点之间的重叠应当在写入侧阻止**，也就是拖动时不允许把一个节点放到
与另一个已固定节点重叠的位置。理由是把一个无解的输入喂给布局系统，
事后兜底要比在门口拦住贵得多——兜底意味着要么悄悄挪动用户放好的节点，
要么给出一张明显坏掉的图。

**关键设计决定：让位只把自由节点往右推，保持层内相对次序。**

- 次序本身有语义：它决定连线的交叉情况和视觉上的阅读顺序。
- 打乱次序比整层变宽更糟。变宽只是占地方，乱序会让人看不懂图。
- 副作用是某一层可能被推得很宽。这是可以接受的代价，而且用户能看到原因
  （那一层的某个节点被钉在了左边）。

### 二、同层组展开放不下怎么办

**这个问题在正确的做法下不存在。**

收缩成超节点时，超节点的尺寸按**展开后的总尺寸**申报：

```
宽度 = Σ 成员宽度 + 间隙 × (成员数 - 1)
高度 = max(成员高度)
```

引擎按这个尺寸为它预留空间，展开时就只是把预留好的矩形切成几份填上——
既不溢出，也不会挤压邻居。**展开是纯局部操作，不需要做任何避让。**

这正是分层布局引擎内部处理跨层长边的标准手法（给跨层的边插入虚拟节点并申报尺寸），
我们只是把同一手法用在同层组上。反过来，如果只按"一个节点"的尺寸申报，
引擎会按一个节点宽度的空间来排，展开成三个必然横着压到邻居身上，
那时候再想补救就只能靠挤压，而挤压会连锁。

**边的处理**（容易漏的地方）：

| 情形 | 收缩时 | 展开时 |
|---|---|---|
| 组内成员之间的边 | 从收缩图中移除 | 按原端点还原 |
| 组外指向成员的边 | 改指超节点 | 按原端点还原 |
| 多条边改指后端点相同 | 去重，但不丢记录 | 逐条按原始端点还原 |

组内边必须移除，否则会变成超节点指向自己的自环，引擎会拒绝或者给出无意义的结果。

### 三、补齐逻辑的耗时上限与降级

**上限 100 毫秒，只约束补齐逻辑本身，不含引擎耗时。**

之所以把两者分开计：出问题时必须能立刻判断是引擎慢还是我们自己的算法慢，
这两者的处置方式完全不同——前者要换引擎，后者要改我们的算法。
把引擎耗时算进补齐预算，会让"补齐是否够快"这个判断失去意义。

**信任来自实测而非估算**：1000 节点、950 条边、250 个固定节点的压力用例上，
补齐逻辑合计 **5.3 毫秒**（收缩 0.04 + 展开回填 0.21 + 行内让位 0.31 + 折线重算 4.7）。
其中折线重算占九成，它一开始是 48.7 毫秒，改用空间索引后降下来的——细节见后文。

**Phase 2 之后重新量过一次**，方法与数据在 `reports/phase2-layout-constraints.md`。
结论有两条值得记在这里：

- 引擎调用在流水线正中间，从外面摘不出去，所以改用量"全流水线（带约束）减全流水线（不带约束）"。
  两者的引擎输入完全相同——固定位置与约束都不进引擎。
- **代价由固定节点的位置决定，不由约束的条数决定。** 251 个固定节点骑在层边界上、
  再加一组次序与一组对齐，差值落在误差里读不出正数；把整层钉到别处之后差值是 3.6 毫秒，
  因为连到那一层的边必须横穿中间十几层。构造评估用例时该盯的是"固定节点落在哪"。

**超限的处置沿用已有的布局失败策略**，不新造一套：保留上一次成功布局、
状态栏提示、给出重试 / 手动布局 / 简化图三个选项。

## 算法

```
输入：节点（含可选固定坐标）、边、同层组、层内次序组、对齐组、方向、间距

1. 收缩        同层组 → 超节点（尺寸按展开后总尺寸申报，记录边与组内边）
2. 引擎        按合法分层图求解析坐标
3. 展开        超节点矩形切分填回成员（纯局部操作）
4. 回填        把固定节点搬到目标坐标
5. 对齐        把一组节点在层内轴上取齐
6. 行内让位    逐层一次线性扫描，把自由节点排到障碍物之外
7. 层内次序    按用户要的先后把同一层里的成员换位
8. 折线重算    按最终坐标重新路由每条边
```

第 4 步与第 6 步分开是为了让偏差检查可以独立进行：
只要第 4 步之后偏差不为零，就说明回填写错了，与让位逻辑无关。

第 5 步与第 7 步的位置不是随手定的，两个方向都有理由：

- **对齐在让位之前。** 取齐可能把节点挪到同层另一个节点的身上，而让位正是用来把那种情况解开的。
  反过来先让位再对齐，对齐的结果就没有人再检查了。
- **次序在让位之后。** 让位保持的是**当前**次序，而次序约束要改的恰恰是当前次序。
  反过来先做次序，让位会按旧坐标的先后把它排回去。

第 8 步不可省：引擎返回的折线是按它自己算出的坐标画的，节点被第 4 至 7 步移动之后，
那些折线就指向了旧位置——看起来是线从节点旁边擦过去，或者悬在半空。

### 行内让位

算法在"层沿纵轴排列"的坐标系里描述，左右方向的布局在进入前把横纵坐标对调、
出来后换回，因此只有一份实现。

```
对每一层：
  障碍物 = 与该层纵向相交的全部固定节点（按横坐标升序）
  成员   = 该层的自由节点（按原横坐标升序，保持次序）
  cursor = -∞
  对每个成员：
     x = max(原横坐标, cursor)
     从左往右扫障碍物：
       若障碍物整体在 x 左侧 → 跳过
       若障碍物整体在 x 右侧 → 停止扫描（后面的更靠右）
       否则 x = 障碍物右边界 + 间隙，继续往后
     放置成员，cursor = x + 成员宽度 + 间隙
```

扫描是单向的，因为让位只会把节点往同一个方向推，已经扫过的障碍物一定落在当前位置之后。
每层一次线性扫描，不需要迭代。

**为什么不用"发现重叠就互相推开"的迭代做法**：迭代收敛慢、结果依赖遍历顺序，
而且必须限制轮数因而可能半途而废，留下一个"差不多分开了"的状态。
直线上的排布是精确可解的，用蛮力逼近它是把简单问题做复杂。
（实测对比：迭代做法在压力用例上要么把节点推离本层，要么在预算内留下近五百处重叠。）

### 让位方向必须随布局方向改变

层内让位的推挤方向是**垂直于分层方向**的：

| 布局方向 | 层的排列 | 层内让位方向 |
|---|---|---|
| 自上而下 / 自下而上 | 层上下叠放 | 横向 |
| 从左到右 / 从右到左 | 层左右并排 | 纵向 |

推错轴会把节点推出它所在的层，分层结构当场就散，而这种情况在上下一维的测试里完全看不出来。

注意这与"层的推进方向"无关：自下而上和自上而下的层内阅读方向都是从左往右，
所以两者用同一个方向让位。RL 同理。

### 层内次序：换位，不是重排整层

约束说的是"组内这几个谁在谁左边"，**没说组外的节点该去哪**。做法因此是**换位**：
把这几个成员当前占的槽位取出来，按给定次序重新填进去，其余节点一个都不动。

```
对每一个次序组：
  要求这些成员落在同一层；落在不同层上时如实报出（拉过去会连带改变分层）
  槽位 = 这一层里全部节点的当前次序（含固定节点），下标就是槽位号
  自由成员依次填进它们自己那些槽位，固定成员占住自己的槽位
  填完之后整体次序必须递增，否则这条约束与固定位置矛盾，如实报出
  每个成员坐回它分到的那个槽位的坐标，然后按新次序跑一次行内让位
```

**"坐回槽位"这一步不能省。** 只改次序、坐标不动的话，摆开那一步会按各人**原来的**坐标往后推，
结果次序虽然对了，整层却被撑宽——而用户只是想换两个人的左右关系。
槽位是同一批坐标的一个排列，按槽位坐回去之后整层的跨度一点没变。

打乱次序比整层变宽更糟：变宽只是占地方，乱序会让人看不懂图。
次序还决定连线的交叉情况，所以它是**语义**而不是排版细节。

### 逐元素对齐：轴与让位轴是同一个

对齐让一组节点在**垂直于分层方向**的那个轴上取同一个坐标。

选它而不是另一个轴的理由很直接：对齐若动分层轴上的坐标，节点就会跑到别的层去，
而分层是另一条约束管的事。由此推出一件必须说清楚的事——
**同一层的两个节点无法在层内轴上取齐**，取齐就等于让它们重叠。
这种组会如实报成冲突，不静默丢掉。对齐的用场在跨层："这几个节点排成一列"。

目标坐标取组里**第一个成员**的坐标，不取平均：取平均会让每次重排都把全部成员挪一点，
图上看起来像整组在抖；取其中一个的坐标至少有一个成员不用动。
组里有固定成员时以固定成员的坐标为准——固定坐标是用户直接给出的意图，
取别的坐标等于让用户的意图去迁就自动计算。两个固定成员坐标不同时这条约束无解，如实报出。

方向适配与让位一样靠坐标换轴：先换成"层沿纵轴排列"的形态，对齐横轴，再换回去。

### 求解阶段与核对阶段都会报冲突，但同一条只报一次

求解阶段报的是"当时算不出来"（跨层、与固定位置矛盾），
核对阶段报的是"算出来了但被后面的步骤推开了"（取齐之后又被让位推开）。

两者都要有：少了后者，那一类失效是**静默**的——约束看着进了流水线，结果上却看不出来。
但求解阶段已经判定做不了的组必须从核对里排除，否则同一条约束会出现两条记录，
而第二条的理由是错的（写成"被让位推开了"，实际是压根没动过）。

### 边的折线重算

折线走的是分层布局的常规路径：从起点朝向终点的那条边出去，
在两层之间的空隙里走一段，再从对面进入终点。**拐点走空隙**是关键——
那个区域天然是空的，只要不被固定节点占用，横向段就不会压到任何节点。

固定节点的纵坐标是自由的，可能正好卡在两层之间把空隙切碎。
所以挑拐点位置时先把被占用的区间减掉，在剩下的空档里取最宽的一段的中点。
这是精确计算而不是采样试探：采样会漏掉窄但可用的空档，而且结果依赖采样点数量。

空隙被占满时退回中点并计入"穿过节点"的计数，**不假装绕开**：
一条看起来能走通但实际压过节点的折线，比一条明确报告有冲突的折线更难排查。

**性能上必须用空间索引。** 最初写成对每条边遍历全部节点，这是平方复杂度：
950 条边乘 1000 个节点，实测 48.7 毫秒，和布局引擎本身一个量级。
改成均匀网格索引之后降到 4.7 毫秒。

不用"按层分桶"是因为固定节点的纵坐标是自由的，层结构在它那里是断的，
按层分桶会把锚点归到错误的桶里导致查询漏项。网格只依赖坐标，与层结构无关。

查询结果写进复用缓冲区、去重用代次数组、格子遍历用嵌套循环而不是带状态机的迭代器——
这三件事合起来把每次查询的分配降到零。每条边新建一次集合的话，
千条边就是几千次分配，光回收就抵掉了索引省下的时间。

## 不变量

| 不变量 | 性质 | 说明 |
|---|---|---|
| 固定节点坐标与目标值误差为 0 | **硬保证** | 用户显式声明的意图优先于任何自动计算 |
| 自由节点不与固定节点重叠 | **硬保证** | 由让位算法保证，不是收敛目标 |
| 自由节点互不重叠 | **硬保证** | 层内次序保持且不重叠；让位只在一个轴上移动，不跨层 |
| 同层组成员纵坐标极差为 0 | **硬保证** | 由收缩尺寸申报正确保证 |
| 节点数与边数守恒 | **硬保证** | 收缩与展开必须互逆 |
| 让位方向垂直于分层方向 | **硬保证** | 推错轴会把分层结构推散 |
| 层内次序组的先后与给定次序一致 | **硬保证** | 只在同一层之内。跨层、或与固定位置矛盾时无解，如实报出而不是丢掉约束 |
| 对齐组在层内轴上的极差为 0 | **硬保证** | 成员落在同一层时无解——取齐等于让它们重叠——同样如实报出 |
| 中级约束的失效必须被报出来 | **硬保证** | 求解阶段报"算不出来"，核对阶段报"被后面的步骤推开了"；同一条只报一次 |
| 换位不改变整层的坐标跨度 | **质量指标** | 换的是槽位而不是新位置；改成"搬到新位置再往右推"会把整层撑宽 |
| 折线端落在两端节点的边界上 | **硬保证** | 落在内部是从节点身子里钻出来，落在外部是没接上 |
| 折线穿过其它节点的边数 | **质量指标** | 空隙被占满时无路可走，如实计数而不是假装绕开 |
| 两个固定节点互不重叠 | **前置条件** | 由写入侧阻止，布局阶段无法解决 |
| 布局结果可重复 | **硬保证** | 遍历顺序全部固定，不使用哈希表遍历顺序 |

"两个固定节点互不重叠"作为前置条件而不是布局职责，是本方案最重要的一个取舍：
**承认有些输入是无解的，并在数据进入系统的入口挡住它。**

中级约束之间也可能互相矛盾（例如把两个固定节点要求成同一次序的反面）。
这一类同样是**承认无解并报出来**，不靠优先级悄悄丢掉一条：
悄悄丢掉的表现是"我设了但没生效"，用户会去反复重设，而每次重设都得不到反馈。

## 验证结果

**本文件记录的是方案与推导过程。** 实现在 `DuetDiagram.Layout`，不变量测试在 `DuetDiagram.Layout.Tests`——
当初用于验证的脚手架已删除，避免两份实现分叉。

| 用例 | 结果 |
|---|---|
| 基础菱形（无约束） | 无重叠，补齐逻辑不改变引擎结果 |
| 固定节点在重排后保住 | 偏差 0，坐标精确 |
| 固定节点挤开自由节点 | 自由节点被挤走，固定节点不动，无残留重叠 |
| 同层组 | 纵坐标极差 0，展开后横向间距 116，无重叠 |
| 同层组加固定节点 | 两项约束同时成立 |
| 两个固定节点重叠（矛盾输入） | 两个都不动，如实报出残留重叠 |
| 层内次序（三个并列分支换位） | 次序成立；组外节点坐标一字不动；整层的坐标集合与换位前完全相同 |
| 层内次序 × 四个方向 | 层左右并排时按纵轴排序；分层轴上的坐标不动 |
| 层内次序 × 固定位置 | 固定节点占住自己的槽位，自由成员填剩下的，无冲突 |
| 层内次序被固定位置挡住（矛盾输入） | 两个固定节点都不动，如实报出，且只报一条 |
| 层内次序的成员跨层 | 如实报出"分布在两层上"，不把节点拉到一层去 |
| 逐元素对齐（跨层两个成员） | 层内轴极差 0，分层轴不动，无残留重叠 |
| 逐元素对齐 × 四个方向 | 对齐轴随分层方向切换，层内轴与让位轴始终一致 |
| 逐元素对齐 × 单个固定成员 | 以固定成员的坐标为准，偏差 0 |
| 逐元素对齐 × 两个固定成员坐标不同（矛盾输入） | 两个都不动，如实报出，且只报一条 |
| 逐元素对齐的成员落在同一层 | 无解，如实报出；报出之后仍然交出一张不重叠、固定坐标不偏的图 |
| 约束里提到不存在的标识 | 不报冲突、不抛异常，按陈旧数据处理 |
| 让位之后重算折线 | 18 条边全部端点贴合、零穿越 |
| 四个方向各跑一遍 | 让位方向全部垂直于分层方向，偏差 0，无残留重叠 |
| 1000 节点 / 250 个固定节点 | 偏差 0，无残留重叠，端点在边界上，补齐合计 5.3 ms |
| 1000 节点带中级约束与固定位置 | 硬保证全部成立，次序与对齐都生效，补齐耗时见下 |

规模用例的耗时分布（1000 节点、950 条边、250 个固定节点）：

| 阶段 | 耗时 | 占比 |
|---|---:|---|
| 收缩 | 0.04 ms | — |
| 展开回填 | 0.21 ms | — |
| 行内让位 | 0.31 ms | — |
| 折线重算 | 4.7 ms | 89% |
| **补齐合计** | **5.3 ms** | 100% |
| 引擎（对照） | 52 ~ 95 ms | — |

**引擎仍然是绝对的大头，但折线重算占了补齐逻辑的九成。**
后续要继续压低开销，先看引擎；若只看补齐逻辑，那么该优化的是折线重算。

Phase 2 重量的全流水线耗时（1000 节点、950 条边，中作业统计）：

| 输入 | 全流水线 | 与无约束之差 |
|---|---:|---:|
| 无约束 | 14.97 ms | — |
| 251 个固定位置（骑在层边界上）+ 一组次序 + 一组对齐 | 14.42 ms | 落在误差里 |
| 整层被钉到别处 | 18.61 ms | **+3.64 ms** |
| 引擎（对照，含构造输入） | 12.13 ms | — |

引擎在流水线里约占 11.5 毫秒。补齐逻辑因此是 3.5 毫秒上下，
而**诊断里的重叠统计很可能占了其中一大半**——它是两两比较的平方复杂度，
在千节点上是五十万次比较，按设计不进分阶段计时，但确实在每次布局的调用路径上。
要压它得换成扫描线，或者只在诊断模式下开启。

### 一个已知的、可解释的穿越

规模用例上有 50 条边（共 950 条）穿过其它节点。原因已经定位清楚，**不是路由缺陷**：

用例把第五层的节点钉到了第一层的条带上，也就是钉到了与它自然层号不同的位置。
于是"第四层 → 第五层"这五十条边必须从第四层一路走到第一层，穿过中间三层的节点。
其余五十条边连接的是相邻层，没有穿越。

也就是说：**锚点把节点拉到别的层时，连到它的边必然穿过中间的层。**
这是锚点语义的直接后果。要在视觉上消掉它，需要让纵向段也走"列间空隙"而不是直接垂直穿过，
那是一个完整的多通道布线算法，不在本轮范围内，记为后续工作。

## 尚未验证

| 项 | 说明 |
|---|---|
| 固定节点数量极大时（例如全图八成节点都被固定） | 压力用例只覆盖了一小部分，更高比例下让位会把层推得很长，实际效果需要单独评估 |
| 真实拖动的分布 | 用的是构造出来的输入。真实用户拖动的位置更零散，可能出现构造用例覆盖不到的组合 |
| 同一层内的成员要求对齐 | 这类组在几何上无解（取齐等于让它们重叠），实现如实报出。真实的界面入口要不要拦住这种设置、还是照报不误，要等有交互数据之后再定 |
| 对齐的轴只有一条 | 约束里没有轴字段，对齐轴固定为"垂直于分层方向"。同一个轴上再区分左对齐与居中对齐需要给约束加字段，本轮不做 |
| 多条次序组落在同一层 | 逐组换位，前一组摆好之后后一组在它的结果上继续。两组要求互相矛盾时按先后各报一次，没有做全局的次序合并 |
| 锚点跨层时的折线 | 已知会产生穿越，需要多通道布线才能消掉，见上文 |
| 布局参数变化后的重排 | 每次都从零布局，没有验证增量更新（只改动局部时能否复用上一次结果） |
| 相对位置约束的求解 | 这一类约束能写进 IR、能进哈希、能进校验，但求解器不消费它——设完之后坐标不变。见上文「第四类约束」 |

## 实现注意事项

1. **让位方向要随布局方向改变。** 层上下叠放时横向让位，层左右并排时纵向让位。
   做错了会破坏分层结构。用坐标换轴复用同一份扫描逻辑比写两套实现更不容易出错。
2. **障碍物的判定要按垂直于分层的那个轴相交，而不是按层归属。** 固定节点的自由坐标
   可能正好卡在两层之间，只把它算进"最近的那一层"会让另一层的节点被推过去压在它身上。
3. **让位不得改变层内次序。** 实现上体现为"只朝一个方向推"，绝不能反向推。
4. **折线必须跟着重算。** 引擎给的是按旧坐标画的线，节点一动那些线就全废了。
5. **折线路由必须用空间索引。** 写成对每条边遍历全部节点是平方复杂度，
   实测 48.7 毫秒；加索引后 4.7 毫秒。索引不要按层分桶——固定节点会破坏层结构。
6. **重叠与穿越的统计不要放进热路径。** 验证用的两两比较是平方复杂度，
   在规模用例上比整个让位算法还慢两个数量级。生产实现里若需要，应当用扫描线做到 O(n log n)，
   或者只在诊断模式下开启。
7. **分阶段计时要分开，不要合并。** 只记总耗时会在排查时失去全部线索——
   引擎慢要换引擎，补齐逻辑慢要改算法，处置完全不同。中级约束各自再记一项。
8. **对齐轴与让位轴必须是同一个。** 两处推错一个，节点就会被推出它所在的层，
   而那种错误在只有上下方向的用例里完全看不出来。四条方向都要有用例。
9. **次序约束是"保持次序"，不是"按给定次序排"。** 组外的节点一个都不许动。
   写错的表现是"我只想换两个人，结果整层都乱了"。
10. **换位要坐回原来的槽位。** 只改次序、坐标不动，摆开那一步会按旧坐标往后推，
    次序对了但整层被撑宽。
11. **求解阶段已经判定做不了的组，核对阶段要跳过。** 否则同一条约束报两次，
    而第二条的理由是错的——它说"被让位推开了"，实际是压根没动过。
12. **两条中级约束各自的耗时单独记。** 与引擎耗时分开的理由一样：
    出问题时必须能立刻判断该换引擎还是该改算法。
