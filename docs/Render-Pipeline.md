# 渲染管线

这一层把「文档 + 布局结果」翻译成一份**绘制列表**，再由画布把列表画出来。
本文说的是绘制列表的约定与它的边界。

## 为什么中间要有一份绘制列表

直接把文档画到画布上也行，代价是画布同时要懂语义、布局与绘图三件事，
于是"画出来的东西不对"这句话里就分不清是哪一层的问题。

拆出绘制列表之后，三件事各自可测：

- 绘制列表是纯数据，可以逐字节比较。**画错了**这件事因此变成一个文本差异，
  而不是"盯着屏幕看哪个像素不对"。
- 它不含界面框架类型，也不含绘图库类型，所以它的回归测试不需要起窗口。
- 换掉绘图后端，绘制列表不变；换掉布局引擎，绘制列表也不变（它只认坐标与折线）。

## 三种指令

| 指令 | 画什么 | 关键约定 |
|---|---|---|
| `DrawShape` | 节点、组合、将来的其它容器 | 形状取自 IR 的节点形状；圆角由主题按形状决定 |
| `DrawText` | 一段文本 | **一段一条指令**，框已经是算好的位置；纯文本的一行正好是一段 |
| `DrawPolyline` | 连线 | 点序从起点到终点，箭头样式是数据，箭头的几何由绘制方算 |

三条共同点：

- **每条指令都带元素标识。** 它不参与绘制，但命中测试、变更高亮、快照差异定位都靠它。
- **颜色是已经解析好的值**，不是令牌名。令牌解析依赖调色板与主题，那一步在构建时做完；
  把令牌留在列表里，等于要求每个绘制方各自再查一次表，两处查表迟早不一致。
- **数字按不变文化格式化到三位小数。** 坐标是算出来的，更多的位数只会把浮点噪声
  写进快照，让本该一致的两次构建产生不同的文本。

## 层叠顺序

**先按页面筛一遍，再按图层分档，档内再按类型。** 页面的判据只有一份
（`PageMembership`：缺省页是次序最小的那一页；边没声明归属时跟着两端走，
两端不在同一页时哪一页都不画），布局与渲染都调它——各判一次的话，
布局算的位置与画出来的东西会分叉，表现是元素画在别处或者漏画。

**不在这一页上的元素一条指令都不出。** 别的页面上的节点本来就不进布局请求，
所以绘制列表里也没有它们的坐标；但过滤不能只靠布局——文档里仍然有它们，
而绘制列表若不自己筛一遍，出笔的会是上一轮留下的坐标。

**先按图层分档，档内再按类型。** 图层次序决定档与档的先后（数值大的画在上面），
每一档内部仍然是下面这个次序。没有图层的文档只有一档，出笔顺序与从前逐字节相同。

**图层在这里由 `LayerPlan` 消费，而 `LayerPlan` 只从文档算一次。** 它同时定下三件事：
档的先后、哪些元素不画、哪些元素画出来但点不中（锁定）。三件事一起算，
是因为它们必须出自同一处——分开算的话，「画的是什么」与「点得中什么」迟早会不一致。

档内的次序：

1. **组合**，外层在前。外层先画，内层框才叠得上去。
2. **连线**。画在节点之下——折线两端落在节点边界上，压在节点上会把边界盖住，
   看上去像线穿进了框里。
3. **节点**，按声明顺序。

**没有图层归属的节点、以及全部连线与组合，归一个隐含的缺省层，它固定在最底下。**
让它随图层次序浮动的话，每加一个图层都会有一批没有归属的元素莫名其妙地换前后。

**看不见的元素不参与。** 不可见图层上的节点一条指令都不出；端点在不可见图层上的连线不画
（一条线连着看不见的东西，画出来是一根悬空的线）；成员全被藏起来的组合不画
（框算不出来）。

**画出来不等于点得中。** 锁定图层上的元素照常画，但命中测试跳过它们——
那份名单挂在绘制列表上（`DrawList.Blocked`），由构建时从文档算出来，
命中测试不去读文档。细节见 `docs/GUI.md`。

**选中、高亮、拖动预览不在列表里。** 它们是画布的状态而不是文档的状态。
放进来会让同一份文档因为"当前选中了谁"而产生不同的列表，
视觉哈希就不再能回答"要不要重绘"了。画布在这份列表**之上**叠加它们。

画布怎么消费这份列表（坐标换算、缩放锚点、输入处理）见 `docs/GUI.md`。

## 视口虚拟化：少画，不是画得不一样

大图上每帧画完整份列表是浪费，所以按视口剔掉看不见的那些。四个类型，判据只有一处：

| 类型 | 管什么 |
|---|---|
| `ViewportCulling` | 两个数的**唯一落脚处**：阈值 500 元素、预取边距 100 像素 |
| `CullingPolicy` | 判据 `ModeFor(元素数)` 与范围 `VisibleArea(视口)` |
| `CullingIndex` | 按**元素**建四叉树，按**指令原顺序**取结果 |
| `ModeSwitch` | 判定、预备、生效分在三帧上 |

**按元素建索引，按指令取结果。** 一个节点对应一条形状加若干行文本，
按指令建索引会把同一个位置重复存几遍，查询结果还要再去重。
取结果时按原顺序走一遍——顺序就是层叠顺序，剔除只是少画几条，
不能把留下来的那几条换个先后，那会让连线跑到节点上面去。

**阈值判的是元素数而不是指令数。** 按指令数判会让"多少个节点才算大图"
随标签行数漂移：同样一百个节点，标签多一行就跨过阈值了。

**预取边距向外扩一圈，不能取零。** 等到元素进入视口才画，已经晚了一帧，
表现是快速平移时贴边元素一闪一闪。边距也不能太大——它占的比例随倍数上升，
图小的时候等于没剔除。它是固定的文档尺寸，所以小图上的剔除率天然比大图低。

**索引建好之后只读，可以跨帧复用。** 绘制列表换了要重建一份：
元素挪过位置之后，旧的包围盒会让它在新位置查不到，而表现是"拖到某些地方就看不见了"。

**换档不瞬时。** 判定那一帧把索引建好，下一帧才真的换过来。
挤在同一帧的话，那一帧必然超时，表现是转一下视图卡一下。
端到端有一条用例专门量这个比值，另一条拿换档前后两帧逐像素比——剔除不得改变画面。

`reports/phase2-render.md` 是这一段的取证：千节点两种模式的帧时、剔除率，以及换档帧的耗时。

## 文本度量是注入的

节点占多大由标签量出来的宽高决定，而量出来的结果取决于字体、字号与渲染后端。
写死成某个绘图库的调用之后，同一份文档在两台机器上会量出不同的尺寸，
于是绘制列表不同、快照对不上，而那种红看起来像画错了。

所以度量走 `ITextMeasurer`：

- 生产路径用 `SkiaTextMeasurer`。
- 测试用按字符数算的假实现，结果与机器无关。

**布局输入里的节点尺寸必须用 `SceneBuilder.MeasureNode` 量。** 绘制时标签在框里居中排，
而居中的前提是框的尺寸就是「标签块加留白」。两处用不同的算法量，
表现是文字贴着边框或者偏在一边，看起来像对齐算错了。

`MeasureNode` 把留白加进去，`MeasureComposite` 只量组合标题——
组合框的大小由成员的最终坐标决定，那要等布局算完才有。

## 富文本的排版

节点有富文本内容时排的是内容，否则排纯文本标签。**两条路最后都汇到 `TextLayout.Place`**，
所以边距、行高与对齐只有一份实现——各写一份的话，两边的偏差看起来像对齐算错了。

排版分三步，前两步只决定"哪几个字落在哪一行"，第三步才定位：

1. **切原子。** 一个拉丁词、一个表意文字、一个空格各是一个原子。表意文字（中日韩）逐字
   成原子，所以中文按字断行；拉丁词整体成原子，所以英文单词不会被从中间切开。
2. **贪心填行。** 装得下就放，装不下就换行；换行处的空格丢掉。**一个原子比整行还宽时
   才按字符硬切**，且保证每段至少一个字，所以不会死循环。同一行上相邻的同样式原子
   **合回一段**，于是"一段"就是"一个 run 在这一行上的那一截"，不随行宽漂移。
3. **定位。** 块宽取最长的一行；行内片段按段落对齐（没写时跟着节点），整块按节点对齐。

几条口径：

- **行高取行内最高的那个 run。** 取平均或取第一个的话，混排大字号的那一行会与下一行叠住。
- **片段的高度一律取行高**，不是片段自己的高度：一行里混排大小字号时，各片段要落在
  同一条中心线上。
- **确定性。** 同一个内容配同一份字体度量，每次排出逐字相同的结果——用哈希做缓存键的
  地方全靠这一条。没有缓存、不依赖集合迭代顺序、不用当前区域设置。
- **不折行时按字面排。** 节点尺寸是量出来的，量之前没有宽度可用，所以按节点排版时不给
  宽度上限，一段就是一行——与纯文本同一口径。折行宽度由调用方给（编辑界面按框宽给）。
- **行内样式六项**（粗体、斜体、下划线、删除线、字号、颜色）里，**斜体要进度量**：
  量的时候按常规体、画的时候按斜体，最后几个字会压到边框上。`Bold` 写成 `false` 与
  "没写"不一样——前者是明确要求不加粗。
- **下划线与删除线由绘制方挂上**（`FormattedText.SetTextDecorations`），指令里只带布尔。
  三项修饰都没设时 `Describe()` 不加任何字，纯文本的既有快照因此逐字节不变。

不做竖排、不做双向文字、不做连字：三样都是各自独立的排版工程，而这一轮要的只是
"富文本正确"。

## 数学排版

节点的 `mathMode` 打开时，标签是**公式原文**，排它的是另一条路（`MathTypesetter`）。
**这一层的核心是边界而不是能力**：LaTeX 的子集一层套一层，每一层都能说"再支持一个记号就好"，
所以判据定成"支持的集合有清单、清单外一律结构化错误"，而不是"画得对"——后者没有可验的形式。

### 支持的清单

清单写死在代码里（`MathSyntax`），并由用例逐个名字守一遍：往表里加一个拼错的名字，
不会有人发现，而那个名字永远排不出来，也永远不会被报错。

| 一类 | 认得的写法 |
|---|---|
| 变量与数字 | 拉丁字母（斜体）、连着写的数字（正体） |
| 单个字符 | `\` `{` `}` `^` `_` 之外的**任何**字符都当一个原子，字母斜体、其余正体（`+ - = ( ) [ ] , . ! < > \|` 都在这一档） |
| 符号名 | `\alpha` `\beta` `\Gamma` `\cdot` `\times` `\le` `\ge` `\ne` `\to` `\in` `\cup` `\infty` `\sum` `\int` 等一张表 |
| 函数名 | `\sin` `\cos` `\tan` `\log` `\ln` `\exp` `\lim` `\max` `\min` 等一张表（正体，后面留一点空隙） |
| 上下标 | `^` 与 `_`，参数是一组 `{...}` 或一个原子；同一个底上各最多一个 |
| 分数 | `\frac{分子}{分母}`，分子在上、分母在下，中间一条线 |
| 根号 | `\sqrt{...}`，只做平方根 |
| 间距 | `\,` `\;` `\!` `\ ` `\quad` `\qquad` |
| 空白 | 公式里的空格、换行与缩进**不占位置**，与 LaTeX 一致 |

命令名**按字母一口气读完**：`\quadb` 读出来是一个名字（于是报"不认得"），
而不是一个间距加一个 `b`。名字后面要接字母时中间留一个空格——
空白不占位置，所以留了也不改变间距。

**清单外的输入给结构化错误**（`MathSyntaxError`：码、出错处的下标、一句话），
渲染层**不画**——原样画出来的话，用户看到的是一串花括号，而他会以为是自己语法写错了；
抛异常又会让一处笔误把整张图变成画不出来。哪一处不认得由整体校验报出来
（`MATH_SYNTAX_INVALID`，带位置与建议），界面上高亮那个节点。

### 只用注入的度量器

公式的宽高一律走 `ITextMeasurer`，**不另起一套字体**——另起一套的话，公式里的字与旁边的字
会来自两个字体栈，表现是同一个节点里两种字形。代价是拿不到字体的升部与降部，
所以基线在行框里的位置、轴线高度、上下标的抬降这些**全是写死的比例**（`MathMetrics`）。
写死之后同一份输入在任何机器上排出同一份结果；换成按实际度量算的话，换一台机器
公式的疏密就变了，快照也跟着变。

### 行内与独立成行

两档的差别**全在基线上**，尺寸一样——节点框总要装得下公式。

- `Inline`：公式的**基线落在这一行文字的基线上**。行框与基线都由文本那一套约定推出来，
  不另立一份。
- `Block`：整块**居中**。它自己占一块，没有别的东西要跟它对。

两档用同一套处理的话，带分数的行内公式会把整行文字顶起来：按框居中之后它的基线
掉到文字基线下面。用例不看具体坐标，看的是两条不变量——行内那一档两个高矮差很多的公式
基线落在同一高度，独立成行那一档两个公式的中心落在同一高度。

### 出的是普通指令

公式拆成**普通的文本段与折线**出指令，不另立一种指令：分数线与根号的上横线是
`DrawPolyline`，每一段字是 `DrawText`。这样画布、剔除、高亮、命中、快照与将来的导出
都照原样认识它，一处都不用改。

### 不做的事

- **不做上下标的二次压缩。** 真排版里"上下标的上下标"还要再小一档，那需要按嵌套层数
  传一个字号下去。
- **不做 `\left` / `\right`**：括号不随内容长高。
- **不做 `\text{}`**：公式里不能夹一段正体文字。
- **不做矩阵、多行对齐、根号的指数**。
- **不做开方指数、极限的上下位置**：`\sum_{i=1}^{n}` 的上下标一律挂在右边，
  不因为换到独立成行就挪到上下——那需要按模式分两套挂法。

## 导出 SVG

`SvgExporter` 把一份**绘制列表**写成 SVG。它不重新遍历文档：重新遍历的话，导出与画布
成了两条绘制路径，而两条迟早对不上——对不上的表现是"导出的图与屏幕上不一样"，
而两边各自都自洽。同一份列表画布画一遍、导出器写一遍，两边对不上的唯一可能就只剩
"某一边漏了"一种，而那种漏有逐类用例守着。

**每一类绘制指令都有对应的元素，认不出的指令抛异常。** 形状按几何种类出
`rect` / `ellipse` / `polygon` / `path`（圆角半径、路径弧的方向与画布同一口径），
折线出 `polyline` 再跟一个箭头标记（`polygon` / `path` / `circle`，尺寸与画布同一组常量），
文字出 `<text>`。跳过一条认不出的指令的话，加一种绘制指令之后导出会少画一样东西
而没有任何报错——这类静默丢失在本仓已经踩过一次，画布那一边同一条口径。

**文字留 `<text>`，不转路径。** 转路径视觉更稳（不依赖对方的字体），但文字搜不到、
选不中，也就没法在 draw.io 里改——而这条导出存在的理由正是"导给同事用 draw.io 打开再改"。
代价是对方要有同一份字体，缺了会按对方的回退字体排、行宽跟着变。这一档没有替代方案，
所以它如实进丢失清单，随导出结果一起交给调用方。

**坐标系显式写出来。** 根元素上同时给 `width` / `height` 与 `viewBox`：只给元素不给
`viewBox` 的话，不同查看器里的尺寸不一样，而用户会以为是导出错了。留白同时挪
`viewBox` 与里面的内容，所以它是真的留白，不是把内容缩进一个没变的框里。

**导出是确定性的。** 同一份列表导出两次逐字节相同：不带时间戳、不带随机标识、
不依赖集合迭代顺序。带上了的话 SVG 没法进版本控制，而"导出的图有没有变"这个问题
就永远答不了。

**导出是只读的**，不进命令总线：版本号不动、历史栈不进、广播不发。

**渲染这一步由宿主喂进工具层。** `diagram_export` 的 `svg` 分支不自己排布局——
它留一个口子，由宿主把"文档 → 绘制列表 → SVG"接上。理由有两条：工具层引渲染层的话，
它连同它的每个宿主都要带上原生绘图库；而 SVG 本来也不是文档的函数（它要布局结果与
字体度量），所以只能由宿主喂进来，与层投影、固定标识同一口径。

## 导出 PNG

`BitmapExporter` 把同一份**绘制列表**光栅化成 PNG，与 SVG 导出同一条口径：
只消费绘制列表、不重新遍历文档、认不出的指令抛异常。于是一份列表画布画一遍、
两个导出器各写一遍，三边对不上的唯一可能只剩"某一边漏了"。

**画什么由 `CanvasPainter` 定，不由它定。** 它只管开一块离屏画布、按选项定范围、
把结果编成 PNG；形状路径、箭头、虚线、字体回退、装饰线全在 `CanvasPainter` 里，
而那一份与 PDF 导出共用。这是 P4-18 抽出来的一层：两种格式的差别只在最后一步，
不在画法上，所以"两种格式导出来不一样"在结构上就不可能发生——
而不是靠两条约定各自维护。

**它是无头的。** 光栅化直接开一块离屏画布，不经过窗口平台。这一条不是可选的美德：
喂它的是 MCP 服务端与模型那条通路，而那两处都没有窗口平台——依赖窗口的话，
命令行导出会失败，而界面上一切正常。

**缩放按倍数给，不给目标像素宽度。** 给宽度的话，同一份文档导两次（一次 1000 像素、
一次 2000 像素）会各自算出一个缩放系数，字体的渲染结果会有一点差别，
而用户以为是自己哪一步写错了。给倍数时"我要两倍图"是一个确定的值。

**背景与透明度显式给，缺省不透明。** 缺省透明的话，导出的 PNG 贴进白底文档里会变成黑底——
这是"导出看起来坏了"里最常见的一种。底色取绘制列表自己的背景色，要透明时才显式打开。

**裁剪范围可选**：整份内容的外接框（绘制列表自己的宽高），或页面尺寸。页面尺寸不是绘制列表的
一部分（它不影响任何一条指令），所以由调用方从文档的画布设置里读出来传进来——导出器自己去读文档的话，
就又多了一条绘制路径。按页面裁而内容超出纸张时，被裁掉的那部分如实进丢失清单：
静默裁掉一块的话，用户拿到一张缺了角而"看起来正常"的图，而那种缺失在缩略图上根本看不出来。

**确定性。** 同一份列表与同一组选项导出两次逐像素相同：不带时间戳、不带随机标识、
不依赖集合迭代顺序，抗锯齿也显式打开而不是听凭默认值。唯一与机器有关的是字体——
字形由本机装的字体画出来，换一台机器字体不同则像素不同。这一条与"节点尺寸由字体量出来"
是同一件事，不是导出引入的。

**字体要挑一次。** 文档点名的家族未必认得出这段字里的每一个字（一份中文标签配上西文家族就是）。
不挑的话那些字会画成空白方块，而看的人第一反应是"程序坏了"。做法是拿点名的家族当线索去问字体管理器：
它认得就把这个家族还回来，认不得就还一个认得的（西文家族遇上汉字，还的是本机的中文字体），
整段换成那个字体。**整段换而不是逐字换**：逐字换字体要真正的文字整形，而这里要的只是"不出现空白方块"。

**度量按同一套回退走，只是粒度不同。** `SkiaTextMeasurer` 与这里的绘制器都问 `FontFallback`
（先拿点名的家族去问，家族画不出这个字再问字体管理器要一个能画的），差别在切分粒度：
**度量按"这一段由哪个家族来画"切成若干段、逐段量再相加；这里整段换成一个字体。**

度量非按段走不可。节点占多大由度量定，而**居中是按量出来的宽度算的**；
度量整段用一个字体、而画布逐字回退的话，同一段字两边量出的宽度不一样，字就偏到一边并且溢出框。
实测中文标签两边量出 18.07 与 28，框是居中的而字偏右 4.96 像素
（见 `reports/phase5-ui-fixes.md`）。按段量之后两边都是 28，偏差消掉。

**还剩一处出入。** 含拉丁字的串两边仍差约 0.45 像素（`"Start"` 度量 28.916 / 界面框架 28.465），
纯全角串则一致（`"开始"`、`"日本語"` 两边都是 28 与 42）。
这是两个字体栈各自选到的西文字面在字距上略有差别，与"全角字画不出来"那条路不是同一件事，
这一轮没有消除，也不随全角字参与而放大。

**位图按 base64 进工具载荷。** 工具结果的载荷是 JSON，装不下裸字节；而调用方本来就要把它
落盘或转发，编码是绕不开的一步。放进一个叫 `base64` 的字段而不是塞进 `text`：
调用方拿到 `text` 会以为那是图的文本。

**渲染这一步同样由宿主喂进工具层**（`DiagramToolContext.BitmapExporter`），
与 SVG 那条同一口径、同一理由。

## 导出 PDF

`PdfExporter` 把绘制列表写成 PDF，画法与 PNG 共用同一份 `CanvasPainter`，
只消费绘制列表、认不出的指令抛异常。**写入器用的是 SkiaSharp 自带的那个**
（`SKDocument.CreatePdf`），不引入新依赖——同一个原生库既量文本、画位图，也写 PDF。
选型过程与四个候选的对照见 `reports/phase4-pdf.md`。

**它是矢量的，这是它相对 PNG 那一档的全部意义。** 线条是路径、文字是真文字，
放大不糊、能选中、能搜索。把内容流解压出来可以看到成对的文字操作符，
以及每个字一份"这个字形是哪个字"的映射表——少了后者，文件里的文字搜不到、
复制出来是乱码。

**它认页。** 一份文档的每一页各占一页，而不是挤在同一张纸上。这是 PDF 与 SVG、PNG
唯一一处结构上的差别：后两者的"页"要靠投影掉，而 PDF 自己就有页的概念。
按内容外接框定范围时各页取同一个尺寸（各页里最大的那个宽与最大的那个高）——
各页各按自己的内容定的话，翻页时页面会跳来跳去，打印时每页的缩放比还不一样。

**纸张尺寸由调用方传，不由导出器去读文档**，理由与 PNG 那一档相同。
文档单位是"96 像素每英寸的那一像素"，而 PDF 的点是 72 每英寸，所以换算系数是
四分之三，由单位的定义推出来而不是选出来。缺省页面尺寸 1123×794 折过去正好是 A4 横放。

**确定性。** 同一批绘制列表与同一组选项导出两次逐字节相同。这一条不是白来的：
写入器在调用方不给日期时**不写日期**，而不是写当前时刻——换成写当前时刻的话，
同一份文档两次导出就不可能相同。所以导出器也不给它日期。

**代价写在丢失清单里：字体整份嵌入，含中文的文档通常十几兆。**
写入器不做子集（`/Length1` 等于源字体文件的大小），一个汉字与一整页汉字代价一样。
换一个做子集的写入器能把这个数字降到几十千字节，但那样会丢掉确定性——
实测过的那个候选每次导出的字体子集前缀都不一样。这一条是取舍的结果，不是疏漏。
要小文件就走 PNG 那一档，代价是文字搜不到。

**它也是无头的**，理由与 PNG 那一档相同；服务端与模型那条通路都没有窗口平台。

**渲染这一步同样由宿主喂进工具层**（`DiagramToolContext.PdfExporter`）。
它与前两条有一处不同：页面标识为空时出来的可能不止一页，而"一份文档有哪几页"
只有宿主那一侧算得出来，所以出几页由宿主决定。

## 主题与调色板的解析次序

`Theme` 是显式参数，不是全局状态。同一份文档配两套主题要能给出两份绘制列表
（导出浅色版与深色版就是同一个文档跑两遍）。做成静态默认值之后，
这件事只能靠"改全局再跑一遍"来做，而那时快照测试会互相干扰。

解析次序，从高到低：

1. 元素上写死的字段（`NodeDef.Style` / `EdgeDef.Style`）。
2. 调色板令牌（`NodeDef.StyleToken` → `Palette`）。
3. 主题兜底。

令牌表达语义、具体字段是有意为之的例外，所以例外优先。反过来排的话，
用户在一处写的颜色会被另一处的令牌悄悄盖掉。

令牌名拼错时**按颜色字面量处理**，不是取兜底。这样表现是"颜色不对"而不是"整块变透明"，
后者会让人以为渲染坏了，而其实只是拼错了一个词。

## 组合的包围盒算了两遍

布局层自己算过一份组合包围盒，用来定连线的落点；这里再算一份，用来画框。
两份不一样是**有意**的：布局那份只包住成员的可见范围，它明确不管渲染要留的那一圈。
代价是线会稍微扎进分组框一点，而这比让布局去猜渲染的内边距准得多。

没有成员的组合不出现在结果里——它没有地方可画。画一个空框出来，
用户会以为那是个可以往里放东西的位置。

## 组合的框与命中

**组合没有坐标字段。** 框的大小与位置由成员的最终位置加上一圈内边距与标题高度算出来
（见上一节），所以"拖组合"实际改的是**全部成员的固定位置**——不存在"挪一下组合的坐标"
这种操作，下一个人不要去找那个不存在的字段。框画在成员下面，成员被半透明的框罩住
会让整幅图的颜色都偏一层，而用户会以为是自己配的色不对。

**四种形态的记号在几何上，不在颜色上**（`CompositeFrame`）：
分组是实线圆角框加标题带；泳道是直角框加顺着流向那一侧的池头带与指向流向的箭头
（圆角会让相邻两条的角上出现缝）；子流程是双线框加右上角的展开／折叠标记，
折起来时是加号；组合框是虚线框——按普通节点画会与分组分不开，
而"四种形态一眼分得开"排在约束的第一句。

**点选与框选对组合是两种态度。** 点组合框的空白处，选中的是组合本身
（命中测试从层叠顶端往下找，成员的指令在框之上，点成员命中的自然是成员）；
框选则只收节点——框到成员必然同时碰到组合的框，把组合收进来等于把它全部成员
都拖走，比用户框的多。组合由点框选中，与"全选不收组合"同一口径。

**点组合框与点节点同一条手势路**：按下进入拖拽（拖的是全部成员）、松手落定。
落点判据与节点拖拽同一条（P2-06）：压在已固定节点上整次挡下、整次拖拽算一步撤销。
由于组合没有坐标，一次按下即进入拖拽也意味着**点一下组合框会把它的成员固定在原地**
（与点节点把它固定在原地同一条规则）；不想要这个固定，撤销一步即可。

## 快照

十三个场景在 `DuetDiagram.Render.Tests/Scenes/` 下，进版本库。
覆盖的是全部指令类型与全部分支：空文档、单元素、连线、八种形状、带标签的分支、
嵌套组合、泳道、调色板令牌、四种边样式、多行文本、富文本（`11-richtext`，
行内混排与段落对齐）、数学的行内与独立成行两档（`12-math-inline` / `13-math-block`）。
**加一种指令类型而不加场景，等于那种指令没有回归网。**

比对是逐字节的，不做容差——容差会让"差了零点零几"这类真实变化被吞掉，
而坐标算错往往就是差这么点。

不一致时会把实际结果写成 `.received.txt`（不进版本库）并报出**第一处差异所在的行**。
行首就是指令类型与元素标识，所以那条报错直接说出了是哪个元素的哪一条指令变了。

**看到快照变红时不要顺手把新输出盖上去。** 那份文件就是"上一次确认过的样子"，
要先判断这次变化是不是有意的。快照文件缺失时测试会报错而不是自动生成——
自动生成会让第一次运行永远通过，而那份刚生成的快照没人看过，
等于把当前行为当成了期望行为。

## 与规格文档不一致的地方

- **画布控件不在这一层。** 规格文档把「Avalonia Canvas 渲染」写在渲染层名下，
  而这里只做到绘制列表为止。带上窗口与面板之后，快照测试就不再是
  「同一份输入永远同一份输出」了。理由与端到端测试的分工见 `AGENTS.md` 的差异表。
- **快照比对没有用规格文档在测试分层表里列的那个工具。** 用的是仓库里的冻结文本加一段
  几十行的比对代码。那个工具不在技术选型表里，而这里要的东西——逐字节可比、
  差异能定位到元素——一段文本比对就够了。理由同样记在差异表里。
- **组合折叠没有实现。** `CompositeDef.Collapsed` 为真时，成员仍然参与布局、
  仍然被画出来。要让折叠真的生效，得先让布局不摆放这些成员，那是布局侧的事。
