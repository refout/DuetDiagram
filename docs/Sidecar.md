# Sidecar

Sidecar 是文档的附属文件，与文档同名同目录。代码在 `DuetDiagram.Core/Sidecar/`。

## 为什么拆三个文件

按"丢了会怎样"来拆，而不是按内容类别：

| 文件 | 内容 | 丢了会怎样 |
|---|---|---|
| `文档名.dsl` | 语义文本，LLM 纯文本模式的入口 | 可由 IR 重新导出 |
| `文档名.layout.json` | 自动布局结果 | **可以重算**，只是慢一点 |
| `文档名.user.json` | 人工产物：固定位置、固定折线、自定义端口 | **重算不出来**，用户的手工调整全丢 |

`文档名.dsl` 有**两种身份**：它既是 `<文档名>.dgm` 的文本视图（导出方向写出来的那一份），
**也是它自己的一种绘图文件格式**——「文件」那一档里的「打开…」认 `.dsl`，
打开得到的是一份独立文档，保存写回打开的那一个文件（见 `docs/GUI.md` 的「打开一份绘图文件」）。

两种身份在同一目录下撞上时（`a.dsl` 与 `a.dgm` 并存）：打开哪个就是哪个，保存写回打开的那一个。
两者共用 `a.user.json` 与 `a.layout.json`（`SidecarPaths.Stem` 只去一层后缀），
所以同名同目录下这两种文件不该并存——那会让两份文档的固定位置互相串台。
`pin` 意图随 DSL 文本走，**`.dsl` 那一形态既不读也不写 `user.json`**，
所以打开 `.dsl` 再保存不会动到 `user.json`。

这条不读不是缺口，是决定：读了它，打开一份 `.dsl` 就会把另一份 `.dgm` 的固定位置
带进来、保存时再写回去，而串台之后没有任何提示。
**代价是折点在这一形态下存不下来**（`pinnedEdges` 只有 `user.json` 一个落点），
如实记在下面的「尚未实现」表里。

放在文档旁边而不是统一的缓存目录：复制、移动、删除文档时不会漏掉附属内容。
放到缓存目录里虽然好清理，但用户把文档发给别人时会**无声地**丢掉自己所有的固定位置。

## 布局缓存

它是**缓存**，不是事实源。有效性靠一个字段判断：`structuralHash`。

| 情况 | 状态 | 处置 |
|---|---|---|
| 文件不存在 | `Missing` | 正常首次打开，直接布局 |
| 哈希与文档一致 | `Loaded` | 直接用 |
| 哈希不一致 | `Stale` | **静默重算** |
| 文档标识对不上 | `Unusable` | 丢弃 |
| JSON 解析失败 | `Unusable` | 丢弃 |

**"缓存过期"不是错误。** 用户只是改了图，缓存自然失效。把它当成错误弹出来，
会让每次正常编辑都伴随一次弹窗。

它与"文档标识对不上"必须分开：过期是正常的，文档对不上说明文件被错放了——
后者值得排查，前者不值得。

哈希变与不变的判据见 `docs/IR-Schema.md` 的"哈希覆盖范围"。
注意改标签**不会**让结构哈希变化，因此不会让布局缓存失效——坐标仍然有效。

## 人工产物

三样东西的共同点是"人工覆盖了自动结果"：固定位置覆盖布局算出的坐标，
固定折线覆盖路由算出的路径，自定义端口覆盖按形状均分的端口。

### 孤儿

条目指向了不存在的元素时，加载器**如实报告而不丢弃**。

理由是指向的节点可能只是被临时删掉了，撤销回来之后这条固定位置仍然有意义。
直接丢掉等于让用户的一次误删顺手毁掉他手工调整过的东西。

要不要真丢由调用方决定——`SidecarStore.PruneOrphans` 是"确实要丢"时用的。

### 大小写

标识一律区分大小写，与 IR 中的比较规则一致。不区分的话，
`Node1` 与 `node1` 会指向同一条记录，而 IR 里它们是两个不同的节点——
一个的固定位置会跑到另一个身上，而这个错位不会有任何提示。

## 加载状态的四个取值

状态与内容分开，因为"没有内容"有四种原因，而它们该触发完全不同的后续动作：

| 状态 | 含义 | 布局缓存的处置 | 人工产物的处置 |
|---|---|---|---|
| `Loaded` | 读到了并且有效 | 用 | 用 |
| `Missing` | 文件不存在 | 直接布局 | 空手起步 |
| `Stale` | 内容过期 | 静默重算 | 不适用 |
| `Unusable` | 损坏或不属于本份文档 | 丢弃 | **提示用户，走备份恢复** |

合成一个空值让调用方自己去猜，是最容易把"缓存过期"当成"文件损坏"处理的做法。

## 写入的原子性

先写 `.tmp` 再改名。直接覆写时写到一半断电或进程被杀，原文件会变成半截内容——
而人工产物正是那份丢不起的。改名在同一分区上是原子操作，
要么旧的完整、要么新的完整，不会出现中间态。

## 失败的边界

- **JSON 解析失败** → 转成 `Unusable`，不抛异常。一个附属文件格式坏掉不该让整个文档打不开。
- **文件读写异常** → 照常抛出。那是环境问题（权限、磁盘），静默吞掉会让它变成更难查的"保存没生效"。

## 备份与恢复

只有人工产物需要备份。布局缓存可以重算，给它做备份等于给一个能随时重建的东西留副本。

### 保留策略的两个上限各自生效

方案写的是"保留最近 10 个或 30 天"，"或"字有歧义。这里取**交集**：
一份备份被留下，条件是"既在前若干份之内、又没有超过最大年龄"。

取交集而不是并集的理由是**存储要有上界**。并集在"一天之内改一百次"时会保留全部一百份，
而那正是最需要收敛的场合。

交集下"30 天"这一条并不多余：偶尔编辑的文档几天才存一次，
十条记录可能横跨好几个月，这时年龄上限才会起作用。

### 时间戳的含义

备份名里的时间戳是**做备份的时刻**，不是被备份内容的写入时刻。

第三天做的那次备份，备份的是第二天写入的内容，但文件按第三天命名——
它如实记录了"这份副本是什么时候留下的"，而那正是恢复时想知道的。

### 什么时候会产生备份

| 情况 | 是否备份 |
|---|---|
| 已有内容且能解析 | 备份 |
| 文件不存在（首次保存） | 不备份，没有旧内容 |
| 已有内容但解析不了 | **不备份** |

解析不了的内容没有可恢复的东西，放进备份列表只会让用户在恢复对话框里
选到一个同样打不开的文件。下一次写入会覆盖它，而覆盖一份坏文件没有损失。

### 保存的顺序不能换

先备份、再写入、最后清理。反过来先写再备份的话，备份下来的就是刚写进去的新内容，
等于没有备份。

清理只动备份文件，当前内容不受影响——它不是备份列表里的一员。

### 清理时机

方案给的是启动时、每次保存后、以及每小时一次。三处都落了：

| 时机 | 谁做 |
|---|---|
| 启动时 | 主窗口构造时清一次 |
| 每次保存后 | 写入路径自己带（`SidecarBackup.Save` 里先备份、再写、最后清理） |
| 每小时一次 | 主窗口排一只表；文档没有文件、或者打开的是 `.dsl` 时为空——那两种情况下人工产物根本不参与 |

**定时那一次要由宿主来排**——Core 里没有调度器，也不该有。窗口关掉时表要停。

### 谁在读、谁在写

`DuetDiagram.Core/Sidecar/` 只提供读写与校验，调用点在主程序这一侧：

| 时机 | 做了什么 |
|---|---|
| 打开一份 IR JSON 文档 | `SidecarStore.LoadUser` 读一份，结果原样带给会话；装不装由会话定，**读不出来时文档照常打开**，另摆恢复提示 |
| 打开一份 `.dsl` 文档 | 不读。固定位置随文本的 `pin` 走 |
| 会话建起来时 | 把固定位置、固定折线、自定义端口装进去；**孤儿原样留着**（惰性、无害） |
| 显式保存 | `SidecarBackup.Save`：先给旧内容留一份备份，再写新的，最后按策略清理。**三样都空、而且原先没有这个文件时不建它** |
| 用户选「从备份恢复」 | 由新到旧试 `SidecarBackup.List` 里第一份 `Restore` 说得通的，装回去并重排一次 |

**写入走带备份的那一条，不走底层的写入方法。** 直接写平时看不出区别，
直到某天文件坏了、用户点开恢复对话框、发现里面是空的。

### 列表与恢复是两步

`SidecarBackup.List` 只按文件名里的时间戳排序，不读取内容。
列备份是打开恢复对话框时就会调的一步，为了排序去解析每一份内容不划算。

内容能不能用由 `SidecarBackup.Restore` 判断。恢复出来的内容同样要按当前文档校验一遍——
备份是旧快照，里面的节点可能早就删了，那些条目会以孤儿形式报出来。
