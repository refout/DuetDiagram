# 用户测试：变更高亮的三种手段

这份文档是**协议**：收数据之前把口径定死，收完之后不再改。量表事后改会把已经打过的分
变得没法解释；顺序分配事后改等于承认之前那批数据的顺序是偏的。

**装置齐了不等于测过了。** 本仓交付的是量表、顺序分配表、录入模板、分析脚本与判定规则；
十二条结论必须由真人数据给出，编码 agent 写不出来。
因此 `reports/phase2-user-study.md` 在数据收上来之前**不生成**——生成一份空的或占位的报告，
后来的读者会以为测过了。

## 被测对象

变更高亮的三种非颜色手段，各自单独使用：

| 手段 | 说明 |
|---|---|
| 脉冲 | 元素边框 1.5 秒脉冲三次，不改填充色 |
| 角标 | 元素右上角一个小圆点，按来源分色 |
| 虚线轮廓 | 变更元素外部叠加一圈虚线轮廓 |

三种手段各自独立可辨，叠加时不互相盖住，颜色只是辅助线索——这些由渲染层的用例管着。
这份测试问的是另一个问题：**哪一种手段让人一眼看出哪里变了，而且不碍事。**

## 受试者

- 人数：**12 到 15 人**。少于十二人时，配对检验的精确 p 值最小也只能到 0.125 上下，
  连"所有人一致"都够不到 0.05 那条线——这是人数下限的来由，不是拍脑袋定的。
- 招募口径：用过流程图或框图工具的人优先；不要求用过本软件。
- 受试者可以参与过本项目的讨论，但**不能是三人评审组的成员**（见下）。

## 设计

**交叉设计**：每个受试者依次使用全部三个手段，各自打完分。这样比较的是同一个人的判断，
个体差异被消掉，样本量才够用。

**顺序要均衡。** 受试者按编号轮转取拉丁方的行：第 0 个看甲乙丙，第 1 个看乙丙甲，
第 2 个看丙甲乙，之后重复。每连续三人构成一个完整的拉丁方，每个手段在三个位置上各出现一次。
十二人与十五人都是三的整数倍，整块分得完，顺序效应被抵消。

不做这一步的后果是实打实的：先看到的那一个会拿到偏低的分（不熟、在摸索），
而那个差会被算成手段之间的差，最后选出来的可能是"排在最后的那一个"。

均衡与否由 `assignment.md` 里的核对表给出，分析脚本每次跑也会重新核一遍并写进报告。

## 量表

每个手段用过之后按 1 到 5 打分。打分只看"变更被标出来这件事有多容易看见、有多不碍事"。

| 分 | 意思 |
|---|---|
| 1 | 完全没注意到有变更 |
| 2 | 事后回想才觉得好像有变化 |
| 3 | 找一下能看出变更在哪儿 |
| 4 | 一眼就看出变更在哪儿 |
| 5 | 一眼看出变更在哪儿，而且完全不干扰读图 |

三个手段之间不提示"接下来换一种标法"，让受试者自己发现。

## 定性部分

每个手段之后记一条反馈，问的是同一个问题：

> 你刚才注意到画面上哪些东西变了？靠的是什么看出来的？

定性材料不参与统计判定，但要原样汇总进报告。它的用途是解释数字：某一种手段分数低，
是因为看不见，还是因为看得见但嫌吵——这两件事的处置完全相反。

## 四条统计判定

四条都写死，逐条给出算出来的值。**只给一句"通过 / 不通过"，读的人没法判断差多少**，
而"两条达标时交评审组"这条规则本身就要求知道差多少。

| # | 判定 | 门槛 |
|---|---|---|
| 1 | Friedman 检验 | p < 0.05 |
| 2 | Wilcoxon + Holm-Bonferroni | p < 0.05 / 3 |
| 3 | Kendall's W | W ≥ 0.3 |
| 4 | 平均排序分 | 领先项平均分 ≥ 五分量表上的四分（4.0） |

**第一条**：三个手段之间至少有一对存在系统差异。**能算精确的地方不近似**——三个手段、
十来个人的样本量下，卡方近似算出来的 p 与精确分布能差好几个数量级，而这份数据唯一的用途
就是决定手段保不保。卡方那一档同时列出来做对照，两个数摆在一起，读的人自己看得出近似偏在哪边。
评分是整数，并列是常态，所以并列按平均秩算，**并且并列本身进置换分布**：每个评分者各自的
秩向量决定他自己那一组可能取值，每种等可能。

**第二条**：领先项与其余每一项的配对比较，经 Holm 校正后都要达标。族就是三组配对，
所以第一步的阈值正好是 0.05 / 3——判定门里写的那个数就是它。Holm 是逐步收紧而不是一律
除以总数（后者是 Bonferroni，更保守，协议里点名的是 Holm）；走到第一个不达标的就停，
后面的全部算不达标。

**第三条**：Kendall's W 是评分者之间的一致度，零表示各排各的，一表示名次完全一致。
它不带 p 值，判定门要的是这个数本身。这一条不达标时，前两条即使显著也只能说明分歧很大，
不能说明大家一致认为哪一种更好。

**第四条**：领先项的平均分要够高。前三条说的是"差异是真的"，这一条说的是"绝对值够用"——
一个所有人都讨厌、但讨厌程度有系统差异的手段，前三条可能都过，而它并不该保留。

### 结论

- **达标三条或四条 → 保留。**
- **恰好达标两条 → 交三人评审组多数决。**
- **不足两条 → 砍掉。**

三人评审组的构成：**一名设计师、一名工程师、一名产品**。多数决，**成员不得参与本设计**——
让设计者自己投票决定自己的设计保不保，这条规则就没有意义了。这一条写进协议，
是为了在"两条达标"时不必临时商量怎么办。

## 装置与复现

```bash
# 自检：统计量在构造好的已知答案上算得对不对。不需要真人数据，随时可跑。
dotnet run --project tools/UserStudy -c Release -- verify

# 生成量表、顺序分配表与录入模板（已有的录入文件不覆盖）
dotnet run --project tools/UserStudy -c Release -- template
dotnet run --project tools/UserStudy -c Release -- template --raters 15

# 读录入数据，算四条判定，写结论报告
dotnet run --project tools/UserStudy -c Release -- analyze
```

产物：

| 文件 | 内容 | 进版本库 |
|---|---|---|
| `reports/user-study/scale.md` | 量表与定性问题 | 是，由脚本生成 |
| `reports/user-study/assignment.md` | 顺序分配表与均衡核对 | 是，由脚本生成 |
| `reports/user-study/study.json` | 录入数据 | **是** |
| `reports/phase2-user-study.md` | 结论报告 | 是，由 `analyze` 生成；**没有数据时不生成** |

**录入数据与脚本一起进版本库**：同一条命令跑多少次都是同一组数，这一点靠"数据在库里"
才验得了。报告里写着数据文件的指纹，对得上才认。

受试者只用编号（`R01` 这样的假名），不写姓名、部门、联系方式。定性反馈原样收，
但录入时去掉能认出人的内容。

报告正文里**不写生成时间**。同一份数据每次跑出同一份文件，比对才有意义；
"这份报告是哪天跑的"在提交记录里查得到。

## 这一轮做到哪儿

- 量表、拉丁方顺序分配表、录入模板、分析脚本、四条判定与结论换算：**已落地**，自检四十几条全通过。
- 统计量全部自己算，不引第三方统计库：它们各自只有几十行，而判定门的数字必须逐字节可复现，
  多一个依赖就多一处会随版本变的行为。

## 尚未实现

- **真人数据。** 十二到十五个人的测试不可能由编码 agent 完成，四条判定的结论必须由人给出。
  在那之前 `reports/phase2-user-study.md` 不存在——这是有意的，不是漏了。
- **三人评审组。** 规则写进了协议，但"恰好两条达标"时具体请谁、怎么记票，等真的走到那一步再定。
- **录音与计时。** 这一轮只收打分与定性反馈；完成时间、求助次数这类过程指标没有装置。
  它们对"哪一种手段更省事"有用，但会带来另一套知情同意与数据留存的要求。
