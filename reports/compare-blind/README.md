# 盲评装置

这个目录里的东西由 `reports/raw` 那份冻结语料算出来，命令是：

```bash
dotnet run --project tools/CompareHarness -c Release -- listings
```

## 目录里有什么

| 文件 | 进仓库 | 给谁看 |
|---|---|---|
| `README.md` | 是 | 就是你正在看的这份 |
| `conclusion.md` | 是 | **结论**。B 这一项定下来什么、没定什么 |
| `parse-report.md` | 是 | **证据**。解析统计与判定门第四条，可机械核对 |
| `semantic-report.md` | 是 | **证据**。语义拒绝率，以及映射阶段消解掉了多少 |
| `checkability.md` | 是 | **证据**。检查项为什么判不了机器，以及改写后的结果 |
| `predicate-report.md` | 是 | **证据**。谓词口径的端到端准确率，以及它为什么不能当结论 |
| `agreement.md` | 是 | **结论**。谓词与人工评分的一致率，分歧逐条。**还没生成，见下** |
| `rater.md` | 否 | 评分者。150 份结构清单，已打乱，看不出组别 |
| `items.json` | 否 | 后续自动核对用。同上内容，机器可读 |
| `key.json` | **否** | **不要给评分者。** 它把匿名编号对回组别 |
| `sample-rater.md` | 否 | 评分者。60 份抽样清单，已打乱，看不出组别 |
| `sample-key.json` | **否** | **不要给评分者。** 抽样编号对回组别，同时冻结了抽样结果 |
| `human/` | **否** | 人工评分的原始文件与空白模板。整目录不进版本库 |

`parse-report.md`、`semantic-report.md`、`predicate-report.md` 分别由
`-- listings`、`-- semantic`、`-- score` 生成，命令见 `AGENTS.md`。
`predicate-report.md` 可以随时重跑（不调模型），但它**不是判定门的答案**，理由写在它自己开头。

六个"否"的文件都不进版本库，理由是它们**逐字节可复现**或**属于人的工作产物**：
清单类的由 `reports/raw` 算出，打乱的种子写死在代码里、也写进了产物（两次运行的输出已核对为一致），
它们是评分时的工作材料而不是结论；把 `key.json` 的副本留在仓库里只会多一份泄露面。
评分文件则是评分者本人的判断，混进仓库会让"语料冻结"这件事变得模糊。

## 双盲是怎么做到的

评分者看的不是模型输出的原文——Mermaid 与 DSL 的文本形态一眼可辨——而是从输出**解析出来的结构清单**：
节点（编号、标签、形状）、分组（编号、标签、成员）、边（起点、终点、标签）。

只投影到这一层还不够。实测发现清单里还有两处会自报组别，都已整批抹平：

| 残留痕迹 | 实测 | 处理 |
|---|---|---|
| 标识的写法 | `c-dsl` 451 个标识里 43 个带连字符，`b-documented` 一个没有；反过来 `b-documented` 有 11 个下划线、14 个全大写，`c-dsl` 两样都是零 | 标识整批换成流水号 `n1`、`n2`… |
| 标签里的换行标记 | `<br>` 出现在 `a-bare` 的 13 个标签与 `b-documented` 的 8 个里，`c-dsl` 一个都没有 | 换成空格 |

换成流水号是**唯一能证明中立、而不是尽力而为**的做法——标签保留，因为检查项判的就是标签与结构，
而 150 份里只有 1 个节点没有标签。

**没被抹平、也抹不平的：** 清单里没有端口、样式、坐标与布局意图，因为前三样只有一种格式能表达。
代价是这份清单**看不见 DSL 的布局表达能力**——而那恰恰是 DSL 存在的主要理由。
四个指标量的都不是这件事，判读时不要把这一点算成某一方的优点或缺点。

## 评分者要做的事

分两轮。**先做校准那一轮**——它的结果决定检查项能不能交给机器，
进而决定判定那一轮要花多少人工。

### 第一轮：校准（60 份）

谓词是拿这 150 份语料对着调出来的，还没跟人核过。这一轮就是去核它。

```bash
dotnet run --project tools/CompareHarness -c Release -- sample
```

产物是 `sample-rater.md`（60 份，每组 20，已打乱）与 `human/template.json`（空白评分文件）。
把模板复制成 `human/ratings-<你的名字>.json`，逐项填好后跑：

```bash
dotnet run --project tools/CompareHarness -c Release -- agreement
```

结论写进 `agreement.md`。**这一轮读的是分歧，不是一致率**：分歧逐条列出来的那些，
就是谓词写错的地方；改完谓词重跑 `-- score`。

抽样是分层的（谓词判不通过、且解析成功的优先收），所以它**对"谓词太松"不敏感**，
分组之间的对比也不成立。这一点 `sample-rater.md` 的开头也写着。

评分文件除了逐项的 0/1，还要填 `steps`（人工修正步数）与 `extra`（多出来的东西）。
那两栏是谓词判不了的东西，也是判定门里首轮通过率与人工修正步骤要的数——
**校准这一轮顺带把它们的第一批数据收上来。**

### 第二轮：判定（150 份）

校准通过之后才做。这一轮用的是 `rater.md`。

1. 读 `docs/Compare-Criteria.md`，那里有四个指标的计算口径与判定规则。
2. 打开 `rater.md`，逐份对照「提示词」与「检查项」，看「结构清单」是否满足每一项。
3. 逐项记 0/1。全部通过才算这一份端到端通过。
4. 需要修正的份，按口径那张表数操作步数（**移动节点位置与调整间距记 0 步**）。

`key.json` 只在评完之后用来汇总，评的过程中不要打开。

### 为什么这里还没有 `agreement.md`

装置齐了，评分没收。**先放一份假的报告进去，后来的读者会把它当成真数据读**——
报告开头写着"评分者：某某"，而那个某某从来没评过。
所以它等评分收上来之后再生成。

## 已知的局限

- **样本量 50/组**，单条差异约 2 个百分点。阈值（15/20 个百分点）远大于噪声，但压线的结论不可靠。
- **只有一份装置**。把两种格式的抽象语法树抹平成同一种形状是手工做的，
  见 `tools/CompareHarness/Structure.cs` 的注释——**那是这套装置里最该被复查的一段**。
  已经在这上面栽过一次：`c-dsl` 的 C02 里模型让节点与泳道共用标识 `pay`，
  匿名化把两个东西编成了同一个流水号，清单里一个标识既是节点又是分组。
  求值器按"先节点、后分组"解析端点，重号会让它把节点当成分组而**静默判错**。
  已改成节点与分组各一张表，150 份里现在零重号。
- **语义拒绝率算出来了，但它本身没有区分度**：三组都是 0%，差别在旁边的
  "映射阶段消解掉了多少"。见 `semantic-report.md`。
- **谓词口径的数字不是独立测量**。谓词是拿这 150 份语料对着调出来的，
  可复现，但是"对着答案调过判据之后"的可复现。见 `predicate-report.md`。
- **谓词判不通过的条目极少**：150 份里只有 4 份（a-bare 3、c-dsl 1、b-documented 0），
  其余 146 份三组谓词全过。这不只是"三组之间没差别"，而是"几乎没有一份被谓词判过不通过"。
  对抽样的直接影响是分层只能多收 4 份，另外 56 份按固定顺序补。
- **B 组的语法参考承诺了解析器不接受的写法**（`linkStyle`）。这次没有被触发，实际影响为零，
  但它是装置本身的缝，已记在 `parse-report.md` 里。
