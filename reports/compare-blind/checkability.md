# 检查项能不能机械判定

`docs/Compare-Criteria.md` 把评分交给了人。在真的开始评之前先问一句：
**那 256 个检查项里，有多少能靠程序判？** 如果能判的够多，四个指标就不用靠人的主观。

答案是**几乎都不能**。下面是量出来的依据。

## 一、检查项里的引用对不上生成的标签

检查项用「」引出它要的节点，例如「检查会话是否过期」。把它当成字符串去和生成结果里的标签比：

| 匹配方式 | 命中率 | 说明 |
|---|---:|---|
| 子串 | 约 60% | 「连接服务器」对不上「连接邮件服务器」 |
| 子序列（字符按序出现） | 约 75% | 无自由参数，已经是最松的"确定"匹配 |
| 字符袋（只要求字符都在） | 约 77% | 更松，但已经开始把不同的节点混为一谈 |

三组分别是 75.5% / 69.1% / 75.5%（子序列口径）。**剩下那 25% 不是模型没做到，是措辞不同。**

抽十例看：

| 检查项要的 | 实际生成的 | 该判 |
|---|---|---|
| 「检查会话是否过期」 | `会话是否过期?` | 通过 |
| 「记录是否存在」 | `目标表中存在该记录?` | 通过 |
| 「是否首次运行」 | `首次运行？` | 通过 |
| 「检查文件大小」 | `文件大小是否超过限制` | 通过 |
| 「写本地事务」 | `主服务执行本地事务 并记录事务日志` | 取决于是否允许合并 |

也就是说，**字符串匹配判的是措辞像不像，不是图对不对**。它会系统性地少给分，
而且少给的比例三组不一样（69% 对 76%），差出来的那部分会被算成格式的差别。

## 二、再松一点就得引入阈值，而阈值是判断不是测量

要覆盖那 25%，只能上相似度打分加一个阈值。阈值取多少没有客观依据，
取 0.6 还是 0.8 会把结果改掉几个百分点——而判定门要的差别正好是十几个百分点。
把判断藏在阈值里，比明说是人判更糟：它看起来像是量出来的。

## 三、检查项本身也不全是结构性的

256 项里有一批根本不描述结构：

- 「节点名称体现日志采集语义」
- 「补偿顺序与正向相反」
- 「有长款与短款的区分」
- 「两套路径最后都记录水位线」

这些是语义判断，没有谓词可写。

## 结论

**四个指标里的「端到端准确率」「人工修正步骤」「首轮通过率」只能靠人判。**
这一条从假设变成了实测结论，依据就是上面的命中率。

要让它能机械化，得改的是**检查项的写法**，不是评分程序：
把「有『检查会话是否过期』的判定节点」写成「存在一个 shape=diamond 的节点，其标签包含『过期』」，
并允许一组同义词。那是提示词与检查项的重写，属于 P1-17 之后的事。

## 附：复核 150 份里的前 50 份时发现的缺陷

以下都来自人眼复核，**只覆盖了三分之一**，所以是下限不是全貌。

### 解析器的两处

**1. 竖线定界的边标签不剥引号。**

```
idem -->|"已处理"| ackSkip
```

`docs` 的语法参考写的是 `A -->|标签| B`，模型写成了带引号的。
结果是标签原样留成 `"已处理"`（带引号）。

同一个解析器对同一件事有两种做法：方括号里的节点标签走 `Unquote`（`MermaidParser.cs:287`、`:534`），
竖线里的边标签不走（`MermaidParser.cs:582`）。

**真实 Mermaid 剥不剥引号需要查证**——这决定该改解析器还是该改语法参考。
50 份里命中 2 份（都在 `b-documented`）。登记给 P1-09。

**2. 边指向分组。**

`ODS -- "清洗" --> DWD` 里的 ODS 与 DWD 是 `subgraph` 的名字。
这是 Mermaid 里表达"这一层流向那一层"的常见写法，50 份里出现 8 份（见 `parse-report.md`）。
IR 现在不接受这种端点，见待决策项 A。

### 生成结果本身的

| 现象 | 例 | 为什么算缺陷 |
|---|---|---|
| 两个具名步骤被合并成一个节点 | 「写本地事务」与「记录日志」写成 `主服务执行本地事务 并记录事务日志` | 检查项点名四个步骤，图上只有三个 |
| 同名节点出现两次 | 两条分支各自接一个「流程结束」 | 语义上是一个终点 |
| 循环边接错 | 「等待订单完成」接向「执行下架」而不是回到判定 | 检查项明确要求回到检查 |
| 无谓的判定 | 提示词只要四步直链，多出一个「有数据？」分支 | 检查项明确要求无判定分支 |
| 分组之间直接连边，标签是无意义的 `L2`/`L4` | 采购审批泳道 | 泳道图里分组间连线不是流程 |

这些都会进"人工修正步骤"，按 `docs/Compare-Criteria.md` 那张表计步。

## 后续：2026-09-21 已按上面的建议改完

上面写的「要改的是检查项的写法（显式谓词 + 同义词表），不是评分程序」已经做了。
256 个检查项全部改写成谓词，写在 `tools/CompareHarness/prompts.json` 每条检查项上，
求值器在 `tools/CompareHarness/Predicate.cs`，结果在 `predicate-report.md`。

**改写让能自动算的指标从一项变成两项**（解析错误率、谓词口径的端到端准确率），
**但端到端准确率这一项失去了区分力**，这是写这份文件时没预料到的：

| 组 | 谓词口径端到端准确率 |
|---|---:|
| `a-bare` | 88.0 % |
| `b-documented` | 100.0 % |
| `c-dsl` | 98.0 % |

253 个检查项里只有 23 个在三组 150 份上不是全过。检查项绝大多数是
「有 X 节点」「X 通向 Y」这类存在性断言，而给足语法文档之后这类断言基本都成立。
**存在性断言分不出「写对了」和「写得刚刚好」**，而后者才是差别所在。
判定门要的「C 比 B 高 15 个百分点」在这个口径下不可能达成，与 C 好不好无关。

另外两条必须记下来的：

- **谓词是拿这 150 份语料对着调出来的。** 凡是结构上明明做到了、而谓词判成没做到的地方
  都放宽了（补同义词、把「有边」改成「可达」、允许一个节点的标签同时覆盖两件事）。
  每一条都记在 `predicate-report.md` 的「改写过文本的检查项」里。所以那份数字可复现，
  但它是「对着答案调过判据之后」的可复现，**不是独立测量**。
- **有一处是检查项本身写错了，不是谓词写错了。** S04 的「无判定分支」与它自己的提示词
  冲突——提示词写的是「设置成功后提示完成」，那句话本身就带一个条件，
  三个组都据此画了「设置成功?」。这条检查项已删掉：一条谁都做不到的检查项
  不区分任何东西，只会把三组的分一起压低。

谓词求值器本身有自检，不需要语料：

```bash
dotnet run --project tools/CompareHarness -c Release -- verify
```
