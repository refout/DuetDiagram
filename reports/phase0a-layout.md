# P0-04 取证报告：备选布局引擎对比与选型结论

- 备选对象：`Mostlylucid.Dagre` **2.0.1**（分层布局的另一个实现，零依赖，同时目标 net6.0 / net8.0 / net10.0）
- 对照基线：`Sugiyama` 0.12.2（主选，已在 `phase0a-mermaider.md` 判定不成立）
- 验证时间：2026-09-20
- 验证程序：`tools/Poc/LayoutCandidates`（两个候选跑**完全相同**的判据）
- 结论：**改用备选，但固定位置与同层约束两个候选都不支持，必须由我们补一层。**

## 并排结论

| 判据 | Dagre（索引式入口） | Sugiyama |
|---|---|---|
| 确定性 | 支持 | 支持 |
| 方向（四种互不相同） | 支持 | 支持 |
| 节点间距与层间距 | 支持 | 支持 |
| 复合分组（成员落在框内） | 支持 | 支持 |
| **固定位置** | **不支持** | **不支持** |
| **同层约束** | **不支持** | 支持 |
| **横宽·菱形** | **116** | 136 |
| **横宽·两列十层完全二分（20 节点）** | **116** | **19852** |
| **横宽·十列十层无交叉（100 节点）** | **1044** | 1152 |
| **横宽·十列十层带交叉（100 节点）** | **1044** | **330248** |
| 规模·长链 1000 | 50.4 ms | 23.9 ms |
| 规模·多层 20×50（1000 节点） | 277.8 ms | 46.4 ms（横向散布 **27.7 亿**） |

## 决定性的一条：坐标是否有界

看"无交叉"与"带交叉"两行的对比：

- Dagre 的两行都是 **1044**，也就是加上交叉边之后宽度**完全没有变化**。
- Sugiyama 从 1152 涨到 **330248**，放大近 287 倍；在 20 节点的极小图上就从 116 涨到 19852。

这说明 Dagre 的坐标分配是有上界的（它用的是 Brandes-Kopf 算法），而 Sugiyama 的不是。
直接后果是：Sugiyama 在 1000 节点时算出 27.7 亿像素的画布宽度，
渲染出来要么内容小到看不清，要么必须靠缩放兜住，而缩放会让节点尺寸失真。

仅此一条就足以决定选型。

## 性能

方案的目标是 100 节点不超过 50 毫秒、1000 节点不超过 1000 毫秒。

Dagre 有两个调用入口，算法相同但内部索引用整数还是字符串不同，耗时差别很大：

| 入口 | 长链 1000 | 多层 20×50（1000 节点） |
|---|---:|---:|
| 默认入口 | 653.8 ms | 1204.1 ms |
| **索引式入口** | **50.4 ms** | **277.8 ms** |

索引式入口是唯一可用的入口：默认入口在 1000 节点多层图上已经超出预算。
选定入口之后，1000 节点耗时约为预算的三分之一，留有三倍余量。

## 两个候选都缺的能力

### 固定位置

这是设计里最要紧的一项：用户拖动节点之后，那个位置必须能带进下一次布局，
否则"手动微调"这个功能根本不成立。

- **Sugiyama**：输入类型只有标识与尺寸，连坐标字段都没有，调用方无从表达。
- **Dagre**：输入类型里**有**坐标字段，看起来像支持。但实测把坐标写进去之后会被覆盖：

  ```
  写入 (1000,1000) → 得到 (98,20)
  写入 (1500,1500) → 得到 (40,132)
  ```

  也就是说那些字段是算法的**输出**，不是输入。仅凭"字段存在"就判定支持会掉进坑里，
  这也是本次验证坚持做行为探测而不只看接口清单的原因。

### 同层约束

"同层"对应的视觉诉求是"这两个是并列的"，方案给出的上下文示例里就有"成功与失败同层"。

- **Sugiyama**：有专门字段，实测生效（未约束时纵坐标差 112，约束后差 0）。
- **Dagre**：两条路径都试过，都不可用。

  | 尝试的路径 | 结果 |
  |---|---|
  | 用最小层距为 0 的边连接两个节点 | 抛异常：`Not possible to find intersection inside of the rectangle`。两个节点同层之后连线变成水平的，边路由阶段处理不了 |
  | 两遍布局，第二遍把两个节点的最小层号与最大层号都锁在同一层 | 抛异常：`ArgumentNullException: Value cannot be null. (Parameter 'key')`。这个异常没有携带任何关于哪个引用为空的线索，看起来是库内部的空值处理问题，需要单独定位 |

  第二条路径的失败原因尚未定位清楚，不排除是我们的用法不对。
  但就当前可用的公开用法而言，**这条约束表达不出来**。

## 选型结论

**布局引擎采用 `Mostlylucid.Dagre` 2.0.1 的索引式入口。**

理由：坐标有界这一条是硬门槛，Sugiyama 过不了；Dagre 的性能在预算内且留有三倍余量；
方向、间距、复合分组、确定性都达标。

**代价：固定位置与同层约束必须由我们自己实现。** 这不是可以延后的细节——
方案要求的是"人工拖动作为布局约束反馈"，没有这两项，人工调整会在下一次重排时全部丢失。

## 能力补齐的可行路径

两条都在布局之外，不需要改动引擎：

1. **固定位置：布局后回填。** 布局完成后，把被固定的节点搬回目标坐标，
   再对被牵连的邻居做一次局部避让。需要明确的边界：是否保证无重叠、是否可撤销、耗时上限。
2. **同层约束：把同层组收缩成一个超节点参与布局**，布局完成后再把超节点展开成横向排列的一组节点。
   这样引擎看到的始终是合法的分层图，不会触发它的同层处理缺陷。

这两条都应当先写清楚不变量再实现，并且要有可计算的验收判据（例如"固定节点的坐标误差为 0"
"同层组的纵坐标极差为 0""展开后无重叠"）。

## 顺带发现的文档与接口不一致

备选引擎的说明文件与真实接口有多处不符，直接照抄说明会编译不过：

| 说明文件写的 | 实际接口 |
|---|---|
| `using Dagre;` | 命名空间是 `Mostlylucid.Dagre` |
| `new DagreGraph { IsDirected = true, IsCompound = false }` | 构造函数是 `new DagreGraph(bool compound)`，没有这几个属性 |
| — | 非复合模式下布局主流程会抛异常，实际上必须传 `compound: true` 才能跑完最简单的图形 |

最后一条尤其值得注意：**传 `false` 时连四节点的菱形图都跑不完。**
这个行为与说明文件的示例直接冲突，实现时不能按说明文件写。
