# P0-05 取证报告：MCP 传输与自定义会话字段

- 验证对象：`ModelContextProtocol` **2.2.0** + `ModelContextProtocol.AspNetCore` 2.2.0
- 验证时间：2026-09-20
- 验证程序：`tools/Poc/McpTransport`（命令行运行即复现全部结论）
- 结论：**三条传输全部可用；自定义会话字段双向可用，但通道与方案设想的不是同一个。**

## 一句话结论

协议链路完全可用。但有两处必须按实测结果调整设计：

1. **当前协议版本用服务发现请求取代了初始化请求**，方案里围绕 `initialize` 写的握手设计需要改名。
2. **自定义字段只能走能力声明的扩展位**，协议给自定义字段留的元数据位在当前版本下没有入口。

## 验证覆盖

三条传输，每条九项检查，全部通过：

| 检查项 | 内容 |
|---|---|
| 一·握手与会话建立 | 客户端拿到服务端名称与版本 |
| 二·工具发现 | 三个工具全部列出 |
| 三·工具调用 | 带参调用并取回结果 |
| 四·上行·客户端状态到达服务端 | 服务端从请求里读到客户端声明的文档与版本 |
| 五·上行·显式传参回显 | 工具收到并回显调用方传入的状态 |
| 六·下行·响应元数据 | 服务端能往响应里注入自定义字段 |
| 七·下行·能力扩展位 | 客户端能从服务端能力里读到自定义字段 |
| 八·消息往返 | 双向消息都到达 |
| 九·会话建立方式 | 记录实际使用的会话建立方法与字段位置 |

| 传输 | 结果 |
|---|---|
| 内存流对 | 9 / 9 |
| 父子进程标准输入输出 | 9 / 9 |
| 网络传输 | 9 / 9 |

## 关键发现一：会话建立请求换了名字

抓到的第一条上行消息是：

```json
{"method":"server/discover","params":{"_meta":{
  "io.modelcontextprotocol/protocolVersion":"2026-07-28",
  "io.modelcontextprotocol/clientInfo":{...},
  "io.modelcontextprotocol/clientCapabilities":{"extensions":{...}}
}},"id":1,"jsonrpc":"2.0"}
```

**协议版本 `2026-07-28`，会话建立走 `server/discover`，不是 `initialize`。**

服务端收到的完整请求序列是 `server/discover` → `tools/list` → `tools/call`。
早期协议版本里的 `initialize` 在当前版本下不再出现。

### 影响

- 方案里"initialize 请求携带 clientState、响应返回 clientStateAck"这套表述需要按新协议改写。
- 任何按方法名 `initialize` 做分支的代码在新协议下都会静默失效——**服务端不会报错，只是那条分支永远不走**。
  本报告的验证程序一开始就踩了这个坑：过滤器按 `initialize` 匹配，结果什么都没抓到。

## 关键发现二：自定义字段的可用通道

客户端选项里有一个"附加到初始化请求元数据"的设置，实测**完全没有上线**：
在抓到的一千三百多个字符的上行内容里，找不到该设置写入的键名。

原因很直接：**根本没有初始化请求可以挂**。那个设置对应的是上一版的协议流程。

真正可用的是**能力声明的扩展位**：

| 方向 | 位置 | 客户端能否读到 |
|---|---|---|
| 上行（客户端 → 服务端） | `clientCapabilities.extensions["duetdiagram/session"]` | 服务端能，直接按类型读 |
| 下行（服务端 → 客户端） | `serverCapabilities.extensions["duetdiagram/session"]` | 客户端能，直接按类型读 |

抓到的上行内容证实了这一点：

```json
"io.modelcontextprotocol/clientCapabilities":{
  "extensions":{"duetdiagram/session":"{\"documentId\":\"doc-7f3a\",\"hasVersion\":12,...}"}
}
```

### 一条比方案设想更好的性质

扩展位是**随每一条请求**携带的，不只是会话建立那一次：

```
server/discover  → 带
tools/list       → 带
tools/call       → 带
```

方案里 clientState 只在会话建立时传一次，之后靠会话标识关联。实测的行为更宽松：
**每次请求都自带状态**。这意味着连接中断重连、服务端换成另一个实例、
甚至服务端完全不保留会话上下文，调用语义都不变。

### 一个使用上的坑

扩展位的值声明上是对象，但往返之后拿到的是 JSON 节点，也可能被对端当成字符串。
读取时必须两种都认，否则会得到"字段明明在但读出来是空"这种很难查的现象。

## 关键发现三：无状态网络传输下不能靠服务端注入

网络传输配置成无状态时，工具的调用失败了。服务端日志给出了真正的原因：

```
"diagram_echo_session" threw an unhandled exception.
System.ArgumentException: The arguments dictionary is missing a value for the required parameter 'holder'.
```

**无状态模式下服务端不持有服务容器，工具参数里的非基础类型不会被解析成注入的服务，
而是被当成"必须由调用方提供"的工具参数。** 调用因此直接失败。

这个失败很有迷惑性：客户端只看到"调用出错"，服务端日志才说明是参数绑定问题，
不看日志会误判成协议不兼容。

### 处置

**会话状态作为显式参数传入，不依赖服务端注入。**

这反而更符合无状态传输的设计意图：调用是自包含的，服务端换实例、重启、
不保留上下文，结果都一样。对多实例部署这是必要条件——靠服务端保存状态的话，
请求必须落到同一个实例上，运维成本高得多。

方案里"工具调用可覆盖 clientState"这条设计因此是对的，而且应当**升级为默认做法**。

## 顺带发现：标准输入输出下日志必须走标准错误

标准输出被协议占用，一条日志写进去就会让对端解析失败。
症状是解析错误而不是超时，很容易被误判成消息格式有问题。

验证程序里的处理是把控制台日志整体改道标准错误。这一点必须在产品实现里同样处理。

## 对后续实现的约束

1. **不要按 `initialize` 做分支。** 会话建立方法的名字会随协议版本变化。
   验证程序里按"第一条请求"取样本，不按方法名匹配，这样协议改名不会让断言静默失效。
2. **自定义字段放能力扩展位。** 两端都能按类型读到，不需要拦截原始消息。
3. **会话状态随每次请求携带，并且作为工具参数显式传入。** 不要依赖服务端保存会话上下文。
4. **标准输入输出下日志改道标准错误。**
5. **网络传输默认用无状态模式。** 有状态会让请求必须落到同一实例上。
