# P0-03 取证报告：Sugiyama 布局引擎约束支持

- 验证对象：`Sugiyama` **0.12.2**（`Mermaider` 0.12.2 的布局依赖，独立包，零依赖，目标框架 net10.0）
- 验证时间：2026-09-20
- 验证程序：`tools/Poc/MermaiderConstraints`（命令行运行该工程即复现全部结论）
- 结论：**主选不成立。布局引擎必须改走备选，或由我们自己补一层后处理。**

## 一句话结论

方向、间距、同层约束、复合分组、确定性、速度都达标，
但**固定位置完全没有输入通道**，且**只要出现交叉边，横向坐标就会爆炸式膨胀**——
20 个节点的图上就能把 116 像素的合理宽度撑到 40803 像素。
后者直接摧毁"渲染一张能看的图"这个基本目标。

## 逐项取证

| 项 | 结论 | 证据 |
|---|---|---|
| 确定性 | 支持 | 同一输入两次计算结果完全一致 |
| 方向 | 支持 | 四个方向产生 4 种互不相同的排布：`TD → a:108,40`、`LR → a:40,88`、`RL → a:344,88`、`BT → a:108,264` |
| 间距 | 支持 | 调整节点间距与层间距都改变了输出坐标 |
| 坐标输出 | 支持 | 每个节点都返回 `(X, Y, Width, Height)` |
| 同层约束 | 支持（成对形式） | `SameRankConstraints` 生效：`c` 与 `d` 纵坐标同为 264 |
| 复合分组 | 支持（含嵌套） | 分组框正确生成，子节点全部落在框内 |
| 规模上限 | 无限制 | `MaxNodeCount` 默认 `int.MaxValue` |
| **固定位置** | **不支持** | `LayoutNode` 的公开成员只有 `[Id, Width, Height]`，没有任何坐标或固定标记 |
| **层内顺序 / 对齐 / 相对位置** | **不支持** | 图输入成员为 `[Direction, Nodes, Edges, Subgraphs, SameRankConstraints]`，选项成员为 `[Padding, NodeSpacing, LayerSpacing, CrossingIterations, ComponentSpacing, SeparateComponents, CancellationToken, MaxNodeCount]`，均无对应入口 |
| **有交叉图的横向坐标** | **不支持（严重缺陷）** | 见下节 |

## 关键缺陷：交叉边导致横向坐标爆炸

四种形态从简到繁对照，合理上限按"同层节点紧挨着排"估算再放宽 3 倍：

| 形态 | 横向散布 | 合理上限 | 判定 |
|---|---:|---:|---|
| 两个节点的单层交叉 | 116 | 696 | 正常 |
| **两列十层完全二分串联（20 节点 / 36 边）** | **40803** | **696** | **超标约 59 倍** |
| 十列十层，无交叉 | 1152 | 3480 | 正常 |
| **十列十层，带交叉** | **330248** | **3480** | **超标约 95 倍，是同尺寸无交叉版本的 287 倍** |

对照关系很干净：**无交叉版本正常，加上交叉边就爆炸**，且爆炸幅度随层数增长。
最小组件只需要 20 个节点就能复现，因此不是"大图才有的性能问题"，而是坐标分配本身没有上界。

放大到目标规模后：

| 规模 | 耗时 | 节点横向散布 |
|---|---:|---|
| 长链 100 | 0.8 ms | X[40..40] |
| 长链 1000 | 20.9 ms | X[40..40] |
| **多层 1000（20 层 × 50，带交叉）** | 43.3 ms | **X[40..2769089088]**（约 27.7 亿像素） |

长链形态的速度很好（1000 节点 20.9 毫秒），说明算法主体是高效的；
问题精确定位在**存在同层交叉时的横向坐标分配**这一段。

### 影响

1. 横向坐标失控意味着画布宽度失去意义。渲染时要么得到一张内容小到看不清的图，
   要么必须靠视口缩放兜住，而缩放又会让节点尺寸失真。
2. 27.7 亿像素已经进入 32 位整型的危险区，一旦下游某处把它当整数用就会溢出成负数。
3. 这个缺陷在**完全合法的输入**上触发，我们的校验层拦不住它，只能靠布局之后再做一次修正，
   而修正本身就是"重写坐标分配"，等于自己实现半个布局引擎。

### 复现方式

```bash
dotnet run --project tools/Poc/MermaiderConstraints -c Release
```

## 不受影响的能力

下面这些结论是可靠的，可以被后续实现直接采用：

- 引擎接受的是纯拓扑输入（节点尺寸 + 边），不依赖 Mermaid 语法，可以独立使用。
- 复合分组支持嵌套，分组框与子节点包含关系正确。
- 四个主方向都真实生效，不是只改了枚举值。
- 提供取消令牌，可以配合执行时限使用。
- 结果确定性，可作为"内容没变就不重算"的缓存依据。

## 处置建议

### 立即可做

1. **布局引擎改走备选**，并把本报告的复现用例作为验收门槛：
   布局实现必须能在"两列十层完全二分串联"上把横向散布控制在合理范围内。
2. **布局接口必须早于实现固定下来**，且输入里必须包含固定位置。
   接口形态建议：
   - 输入：节点（含尺寸与**可选的固定坐标**）、边、分组、方向、间距、逐项约束、取消令牌
   - 输出：节点矩形、边折线、分组框、画布尺寸
   - 约束项至少覆盖：固定位置、同层、层内顺序、对齐、相对位置
   - 引擎只负责求解拓扑与坐标，**不感知降级级别**；降级由协调器在外面做
3. **把"坐标合理性"做成回归断言**。这次的缺陷靠肉眼读代码看不出来，
   只有把"横向散布不得超过同层节点数 × 列距 × 常数"写进测试才能长期防住。

### 需要向上游反馈

横向坐标爆炸是引擎自身的缺陷，与我们的用法无关（复现用例只用公开 API）。
建议向上游提交最小复现：两列、十层、每层两个节点完全二分串联，20 节点 36 边。
在上游修复之前，不应把它当作唯一布局实现。

### 对整体排期的影响

- 布局引擎这一项从"按计划"改为**走备选**，需要重新验证备选方案在同两组用例上的表现
  （约束支持面 + 坐标合理性），这属于原计划中备选评估任务的范围。
- 关键路径增加了"备选验证"这一段。在这个结论被消费掉之前，渲染层不应开工。
