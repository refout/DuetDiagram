持续集成里的原生发布作业跑在自带工具链的运行器上，可以关掉这一项。

## P0-02 界面框架与绘图库验证

### 结论：渲染链路可用，冷启动达标，原生发布未完成

技术栈：`Avalonia` 12.1.2 + `SkiaSharp` 4.148.0。

### 实测数据

以构建出的可执行文件直接运行（进程启动到出图后退出）：

| 指标 | 实测 |
|---|---|
| 冷启动（进程启动 → 出图 → 退出） | **~700 ms**（三次：725 / 693 / 697） |
| 其中：平台就绪 | ~440 ms |
| 其中：首帧渲染 | ~215 ms |
| 绘制元素数 | 4 |
| 位图尺寸 | 900 × 600 |

框架无关的启动开销（进程创建 + 运行时初始化）约 260 毫秒，由总时长减去进程内计时得出。

目标上限是 2 秒，当前约 700 毫秒，**留有接近三倍余量**。
需要说明的是这次测量是带运行时即时编译的构建，原生编译后的启动通常更快，
所以这个数字是偏保守的。

### 已经证实的能力

1. **自绘路径可用。** 直接重写控件的渲染方法，用绘制上下文画矩形、圆角矩形、
   自定义路径（菱形与箭头三角形）以及文字，产出结果正确，见 `phase0a-selftest.png`。
2. **文字渲染正确。** 中文标签在没有额外配置的情况下正常显示，没有出现方块或缺字。
3. **原生绘图库可加载。** 直接调用它读取版本、加载字体并测量中英混排文本宽度，
   返回 `4.148.0.0`、字体 `Segoe UI`、示例文本宽度 57.0。这说明原生库被正确带起来了，
   不是只在托管层假装可用。
4. **界面声明用编译期绑定。** 已开启，这是能通过裁剪与原生编译的前提。

### 阻塞项：原生发布无法完成

```
error : Platform linker not found. Ensure you have all the required prerequisites
        documented at https://aka.ms/nativeaot-prerequisites, in particular the
        Desktop Development for C++ workload in Visual Studio.
```

失败点非常明确：**托管编译与中间代码生成都已完成，卡在最后一步的原生链接**。

本机的实际情况（逐项核实过，不是从报错反推的）：

| 检查项 | 结果 |
|---|---|
| 列出已安装的 Visual Studio 实例 | 空 |
| 注册表中的实例表项 | 无 |
| `C:\Program Files (x86)\Microsoft Visual Studio\2022` | 空目录 |
| 查找 `cl.exe` / `lld-link.exe` / `rc.exe` / `mt.exe` | 都不存在 |
| 全盘查找 `link.exe` | 只找到 Git 自带的同名工具，那是做硬链接的，不是链接器 |
| 已安装程序里的相关条目 | 只有 Visual Studio 安装器本身与一个 SDK 附加组件，没有任何工具链 |
| `Windows Kits\10` 目录内容 | 只有通用元数据目录，没有库文件与头文件 |

结论：**本机只有 Visual Studio 的安装器，没有安装任何工作负载，也没有 Windows SDK 本体。**
托管层能否通过裁剪与原生编译分析已经得到确认（构建过程 0 警告，包括裁剪分析器与原生编译分析器），
但"能链接成原生可执行文件并运行"这一点尚未验证，而它正是这个任务要回答的核心问题。

一个可预见的风险是：界面框架与绘图库在运行时是否依赖反射式类型解析。
这类问题只在原生编译后才会暴露，分析器不一定能全部覆盖。

### 安装前需要先解决磁盘空间

安装通道是现成的（安装器已在，命令行包管理器也可用），但磁盘余量是个硬约束：

| 盘 | 可用空间 |
|---|---:|
| C: | **9.7 GB** |
| D: | 0.1 GB |
| L: | 0.4 GB |

C++ 工具链加 Windows SDK 装完通常需要 5 到 7 GB（含下载缓存峰值），
装完 C 盘会只剩两三 GB。而原生编译本身很吃磁盘——它会生成大量中间文件，
再把 NuGet 缓存与构建输出算进去，这个余量偏紧。

两条可行路线：

1. **本机安装精简版工具链。** 装独立的生成工具而不是完整界面版，只选 C++ 生成工具与 Windows SDK，
   体积比完整工作负载小得多。需要管理员权限，且建议先清理磁盘。
2. **交给持续集成。** 流水线里已经加了原生发布作业，跑在自带工具链的托管运行器上。
   不占本机磁盘，代价是反馈链路变长，且不能在本机复现失败。

### 顺带发现的接口变化

界面框架 12 版本把位图保存的编码参数从"质量整数"改成了独立的选项类型
（`PngBitmapEncoderOptions` / `JpegBitmapEncoderOptions`）。
不带编码参数的重载已标记为过时。导出功能实现时要按新接口写。

## P0-03 布局引擎验证

详见 `phase0a-mermaider.md`。要点：

- 主选引擎在方向、间距、同层约束、复合分组、确定性、速度上都达标。
- **固定位置完全没有输入通道** —— 人工拖动的位置无法带入下一次布局。
- **只要出现交叉边，横向坐标就会爆炸**：20 个节点的图上，116 像素的合理宽度被撑到 40803 像素；
  1000 节点时达到 27.7 亿像素。

## 对后续任务的影响

1. **布局引擎改用备选。** 选型与对比数据见 `phase0a-layout.md`。
   实现时必须用索引式入口：默认入口在 1000 节点多层图上要 1204 毫秒，已经超出预算。
2. **固定位置与同层约束的补齐方案已经定下并验证**，见 `docs/Layout-Constraints.md`。
   硬保证是锚点坐标不偏；无重叠是算法的必然结果而不是收敛目标。
3. **外部代理接入按实测结论实现**，见 `phase0a-mcp.md`：
   会话字段走能力扩展位、随每次请求携带、作为工具参数显式传入，
   会话建立方法不要按名字硬编码，标准输入输出下日志改道标准错误。
4. **坐标合理性要成为长期回归断言。** 主选引擎的缺陷靠读代码看不出来，
   只能靠"横向散布有上界"这类可计算的性质来防。
5. **持续集成里加一个原生发布作业**，并用一台装了 C++ 工作负载的机器跑，
   把 P0-02 与 P0-04 里被阻塞的那一项真正关闭。
