## P0-02 界面框架与绘图库验证

### 结论：渲染链路可用，冷启动达标，原生发布未完成

技术栈：`Avalonia` 12.1.2 + `SkiaSharp` 4.148.0。

### 实测数据

以构建出的可执行文件直接运行（进程启动到出图后退出）：

| 指标 | 实测 |
|---|---|
| 冷启动（进程启动 → 出图 → 退出） | **~700 ms**（三次：725 / 693 / 697） |
| 其中：平台就绪 | ~440 ms |
| 其中：首帧渲染 | ~215 ms |
| 绘制元素数 | 4 |
| 位图尺寸 | 900 × 600 |

框架无关的启动开销（进程创建 + 运行时初始化）约 260 毫秒，由总时长减去进程内计时得出。

目标上限是 2 秒，当前约 700 毫秒，**留有接近三倍余量**。
需要说明的是这次测量是带运行时即时编译的构建，原生编译后的启动通常更快，
所以这个数字是偏保守的。

### 已经证实的能力

1. **自绘路径可用。** 直接重写控件的渲染方法，用绘制上下文画矩形、圆角矩形、
   自定义路径（菱形与箭头三角形）以及文字，产出结果正确，见 `phase0a-selftest.png`。
2. **文字渲染正确。** 中文标签在没有额外配置的情况下正常显示，没有出现方块或缺字。
3. **原生绘图库可加载。** 直接调用它读取版本、加载字体并测量中英混排文本宽度，
   返回 `4.148.0.0`、字体 `Segoe UI`、示例文本宽度 57.0。这说明原生库被正确带起来了，
   不是只在托管层假装可用。
4. **界面声明用编译期绑定。** 已开启，这是能通过裁剪与原生编译的前提。

### 阻塞项：原生发布无法完成

```
error : Platform linker not found. Ensure you have all the required prerequisites
        documented at https://aka.ms/nativeaot-prerequisites, in particular the
        Desktop Development for C++ workload in Visual Studio.
```

失败点非常明确：**托管编译与中间代码生成都已完成，卡在最后一步的原生链接**。
本机只装了 .NET SDK，没有装 Visual Studio 的 C++ 桌面开发工作负载，
因此缺少链接器。

这意味着：

- 托管层能否通过裁剪与原生编译分析，已经得到确认（构建过程 0 警告，
  包括裁剪分析器与原生编译分析器）。
- 但"能链接成原生可执行文件并运行"这一点**尚未验证**，而它正是这个任务要回答的核心问题。
- 一个可预见的风险是：界面框架与绘图库在运行时是否依赖反射式类型解析。
  这类问题只在原生编译后才会暴露，分析器不一定能全部覆盖。

**需要安装「使用 C++ 的桌面开发」工作负载后才能关闭这一项。**

### 顺带发现的接口变化

界面框架 12 版本把位图保存的编码参数从"质量整数"改成了独立的选项类型
（`PngBitmapEncoderOptions` / `JpegBitmapEncoderOptions`）。
不带编码参数的重载已标记为过时。导出功能实现时要按新接口写。

## P0-03 布局引擎验证

详见 `phase0a-mermaider.md`。要点：

- 主选引擎在方向、间距、同层约束、复合分组、确定性、速度上都达标。
- **固定位置完全没有输入通道** —— 人工拖动的位置无法带入下一次布局。
- **只要出现交叉边，横向坐标就会爆炸**：20 个节点的图上，116 像素的合理宽度被撑到 40803 像素；
  1000 节点时达到 27.7 亿像素。

## 对后续任务的影响

1. **布局引擎这一项从"按计划"改为"走备选"。** 备选方案必须在下面两组用例上重新取证：
   - 约束支持面：固定位置、同层、层内顺序、对齐、相对位置
   - 坐标合理性：有交叉的多层图，横向散布不得超过同层节点数 × 列距 × 常数
2. **布局接口的输入必须包含固定位置**，这一点在主选上根本无法实现，说明接口设计不能再迁就引擎。
3. **坐标合理性要成为长期回归断言。** 这次的缺陷靠读代码看不出来，
   只能靠"横向散布有上界"这类可计算的性质来防。
4. **渲染层暂不开工。** 布局结果还没有可信来源，先把渲染做出来会立刻被返工。
5. **持续集成里加一个原生发布作业**，并用一台装了 C++ 工作负载的机器跑，
   把这个任务真正关闭。
