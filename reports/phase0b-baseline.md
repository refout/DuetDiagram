# Phase 0b 性能基线

- 测量时间：2026-09-20
- 测量机器：AMD Ryzen 5 6600H，12 逻辑核 / 6 物理核，Windows 11 25H2
- 运行时：.NET 10.0.11，x64 RyuJIT
- 用途：Phase 1 及以后的验收目标以本基线为基准，允许的退化幅度是一点二倍

## 基线数据

| 指标 | 基线 | 测量方式 |
|---|---:|---|
| 冷启动（进程启动到出图退出） | **857 ms**（5 次实测 794 ~ 1029） | 外部计时 |
| 其中平台就绪 | 473 ms | 进程内计时 |
| 其中首帧渲染 | 275 ms | 进程内计时 |
| 100 节点布局 | **0.52 ms** | 统计基准，15 轮迭代 × 2 次启动 |
| 1000 节点布局 | **11.8 ms** | 同上 |
| 其中输入构造 | 0.63 ms | 同上 |
| 1000 矩形帧率 | **134.6 帧每秒**（单帧 7.43 ms） | 脱屏渲染 60 帧 |
| 全量结构哈希 1000 节点 | **0.18 ms** | 统计基准 |
| 全量视觉哈希 1000 节点 | **0.35 ms** | 同上 |
| 全量序列化 1000 节点 | **0.43 ms** | 同上 |
| 全量反序列化 1000 节点 | **1.52 ms** | 同上 |

## 与 Phase 1 验收目标的对照

| 指标 | 目标 | 基线 | 余量 |
|---|---:|---:|---:|
| 100 节点布局 | ≤ 50 ms | 0.52 ms | **96 倍** |
| 1000 节点布局 | ≤ 1000 ms | 11.8 ms | **85 倍** |
| 冷启动 | ≤ 2 秒 | 857 ms | **2.3 倍** |
| 1000 矩形帧率 | ≥ 30 | 134.6 | **4.5 倍** |
| 全量哈希 1000 节点 | ≤ 5 ms | 0.18 ms | **28 倍** |
| 全量序列化 1000 节点 | ≤ 20 ms | 0.43 ms | **47 倍** |

**全部达标，且除冷启动外余量都在四倍以上。**

这意味着 Phase 1 的实现只要不引入数量级的退化，就不会碰到性能门槛。
反过来说，**性能不是现阶段需要花力气的地方**，应当把预算花在正确性上。

## 四条观察

### 一、布局的内存分配值得盯

1000 节点布局每次分配 **10.8 MB**。布局在每次结构变更时都会跑，
这个量级意味着明显的垃圾回收压力——在交互式编辑里，一次结构变更就制造十兆垃圾。

作为对照，序列化只分配 339 KB、反序列化 1038 KB。

Phase 1 若要优化性能，**这里是首选目标**，而不是去压那零点几毫秒的耗时。
当前耗时已经足够快，而分配量会在连续编辑时累积成卡顿。

### 二、测量作业的长度会显著影响结论

同一份布局基准，两种作业配置给出差 25% 的结果：

| 作业 | 预热 | 迭代 | 1000 节点布局均值 | 误差 |
|---|---:|---:|---:|---:|
| 短作业 | 3 | 3 | 14.9 ms | ±30 ms |
| 中作业 | 10 | 15 | 11.8 ms | ±0.08 ms |

短作业的误差棒比均值还大——那个数字根本不能用。
**基线必须用足够长的作业跑**，否则后面拿它比对时会得出错误的退化结论。

### 三、冷启动只能看量级

同一个程序，先前测得 693 ~ 725 ms，本次测得 794 ~ 1029 ms，
不同时段差三成，与机器负载有关。小数点后的数字没有意义，只能看"不到一秒"这个量级。

好在目标是两秒，即使按最差的 1029 ms 算也还有一倍余量。

### 四、帧率测的是光栅化耗时

单帧 7.43 ms 是**把一帧内容光栅化出来**的耗时，由它反推可达到的帧率上限。

它**不等于**真实窗口里数出来的帧率：后者还要经过合成器、受垂直同步限制。
不在真实窗口里数的原因是那样依赖桌面会话、噪声大且不可复现。

光栅化耗时是帧率的主导因素，也是后续优化真正要压的部分，所以用它做基线是合适的。
但引用这个数字时要说明它的口径。

## 后续补充的性能基线

Phase 1 落地了两块带性能指标的东西，数字记在这里，供 Phase 2 比对。

### 布局引擎与补齐（`DuetDiagram.Layout`）

| 指标 | 实测 |
|---|---:|
| 100 节点布局 | 0.52 ms |
| 1000 节点布局 | 11.8 ms |
| 补齐逻辑（收缩 + 回填 + 让位 + 折线，不含引擎） | 约 5.3 ms |

四个方向、固定坐标精确、无残留重叠等不变量由 `DuetDiagram.Layout.Tests` 持续保证。

### 四叉树视口索引（`DuetDiagram.Render`）

| 指标 | 实测 | 方案要求 |
|---|---:|---|
| 单次视口查询（千节点） | **305 ns** | < 1 ms |
| 建树（千节点） | 191.6 µs | — |
| 插入一千次 | 223.4 µs | 增删按深度 |

查询**零分配**：缓冲区由调用方复用。方案要求的一毫秒在这里有三千倍余量，
真正要盯的不是耗时而是**剔除率**——裁掉的元素越多，每帧画的越少。

建树与插入各分配约四百字节每节点。如果将来发现频繁重建是瓶颈，
优化方向是复用节点对象，而不是去压查询耗时。

## 复现方式

```bash
# 可统计的项：布局、序列化、哈希
dotnet run --project DuetDiagram.Benchmarks -c Release -- --filter "*" --job medium

# 帧率
dotnet run --project DuetDiagram.App -c Release -- --benchmark-frames --rectangles 1000 --frames 60

# 冷启动（外部计时，进程内分阶段耗时由程序自己打印）
dotnet run --project DuetDiagram.App -c Release -- --selftest --out reports/phase0a-selftest.png
```

基准工程用 BenchmarkDotNet，逐项做预热、多轮迭代与统计分析，
不使用秒表单次计时。**加 `--job medium` 是必须的**，短作业的数字不可用。
