# P2-08 变更高亮 — 验证结论

任务 `tasks/phase2/P2-08-change-highlight.yaml`，依赖 P2-07 与 P1-02。状态 `done`。

## 交付内容

### 渲染层：三种非颜色手段（纯计算，可逐条断言）

`DuetDiagram.Render/Highlight.cs` 的 `Highlight.Build` 给一批标记、一份基准绘制列表与一个脉冲相位，
算出这一帧要叠哪些指令。三种手段各是各的形状与位置：

| 手段 | 形状 | 位置 | 要点 |
|---|---|---|---|
| 脉冲 | 加粗的实线圆角框 | 元素外扩 2px | **不改填充色**，只动边框；粗细与不透明度按相位起伏 |
| 角标 | 实心圆点 | 元素右上角之外（让开轮廓一圈） | 颜色区分来源；靠"点"这个形状本身就能认出 |
| 虚线轮廓 | 虚线圆角框 | 元素外扩 7px | 靠"虚线"这个线型本身就能认出 |

颜色只是辅助线索（人工蓝 `#1f6feb`、LLM 紫 `#8250df`，其余来源各一色）。只靠颜色的话，
色觉障碍用户看到的是一张没标过的图，而这一点无法事后补救。三种手段叠加时各有各的位置，
谁也不盖住谁——`Means_do_not_occlude_each_other` 直接断言角标与脉冲、轮廓都不相交。

脉冲的次数与时长写进主题常量（`HighlightPulseSeconds` = 1.5、`HighlightPulseCount` = 3）。

### 应用层：只听通知，不自己猜

`DuetDiagram.App/Interaction/HighlightTracker.cs` 订阅命令总线的变更广播器，按通知里的
**来源**与**受影响元素**攒出标记。界面若靠比较前后两份文档来推断"哪个字段变了"，
LLM 改的东西就不会亮——那条路径根本不经过界面。

撤销/重做单独处理：通知来源是 `Undo` / `Redo`，但用户想看的还是"谁改的"，
所以 tracker 按元素记住上一次**真实**来源，撤销重做时继承它，另加 ↶ / ↷ 符号。

通知在后台投递线程上到达，画布在界面线程上读，两者之间用一把锁隔开——
无锁的并发字典读起来快，但"读一遍得到一份自洽的快照"它保证不了。

### 叠加层，不进绘制列表

高亮是 `CanvasViewModel._highlight` 一层，与手势层的 `_overlay` 分开两栏（手势一松手就清，
高亮要留到下一次变更）。混进绘制列表的几何之后，动画的时间戳会污染快照测试，
而那些快照本该是"同一份输入永远同一份输出"。

画布只在真有脉冲在跑时才按帧重绘（`DispatcherTimer`，约 30 帧每秒）；空闲时也转的话，
省电模式下会被系统降频，而那个降频会被误读成性能退化。通知到达时由 `HighlightsChanged`
事件叫醒画布——不接这一下的话，一次变更之后画布只在"文档重载"那一帧刷新过，
而通知通常比那一帧晚到，高亮就会一直不出现。

### 边栏 diff

右下角 `DiffSidebar` 默认折叠，只显示最近一次变更的摘要（命令、来源、影响几处），
点开看逐字段明细。明细来自**版本日志**，不在界面侧另算一份——界面自己比较文档的话，
它会与版本日志对"这次改了什么"给出两个说法，而两者迟早会分叉。

## 验收

| 命令 | 结果 |
|---|---|
| `dotnet test --project DuetDiagram.Render.Tests -- --filter-trait Category=Highlight` | 15/15 |
| `dotnet test --project DuetDiagram.E2E.Tests -- --filter-trait Category=Highlight` | 3/3 |
| `dotnet run --project DuetDiagram.App -c Release -- --benchmark-frames --nodes 1000 --frames 120 --highlight` | 达标 |

高亮全开（30 个节点各挂三种手段）时的帧率：

```
  虚拟化   单帧平均     9.59 ms  → 约  104.2 帧每秒
  虚拟化   单帧中位     7.71 ms  → 约  129.7 帧每秒
  剔除率              86.3 %  （2968 条里只画 496 条）
```

判据与不带高亮时同一条（虚拟化不低于 30 帧每秒），所以它验的是"高亮叠加层没有拖垮帧率"。

## 与规格文档的差异

- **判据的验收方式不一样。** 方案 §14.3 这一条写的是"通过用户测试"，而用户测试在 P2-13
  由人给出。本任务只交付**可测**的高亮——一个编码 agent 说"高亮方案很好用"没有意义。
- **高亮不进绘制列表的几何。** 见上文，已登记进 AGENTS.md 的「已知差异」表。
- **来源色里没有"冲突橙"。** 方案 §9.3 点名人工蓝、LLM 紫、冲突橙，但本仓的 `ChangeSource`
  没有"冲突"这一档（冲突是并发检测的结果，不是一次命令的来源），所以其余来源各给一个
  一眼分得开的颜色。颜色只是辅助线索，认手段靠形状。
