# Phase 2 中级布局约束：结论与基准

- 测量时间：2026-09-21
- 测量机器：AMD Ryzen 5 6600H，12 逻辑核 / 6 物理核
- 运行时：.NET 10.0.11，x64 RyuJIT（x86-64-v3），.NET SDK 10.0.303
- 基准工具：BenchmarkDotNet 0.15.8
- 用途：Phase 2 的中级布局约束验收（层内次序与逐元素对齐），以及后续高级约束的对照基准

## 复现

```bash
dotnet test --project DuetDiagram.Layout.Tests/DuetDiagram.Layout.Tests.csproj -- --filter-trait "Category=Layout"
dotnet test --project DuetDiagram.Layout.Tests/DuetDiagram.Layout.Tests.csproj -- --filter-trait "Category=OrderAlign"
dotnet test --project DuetDiagram.Layout.Tests/DuetDiagram.Layout.Tests.csproj -- --filter-trait "Category=LayoutFallback"
dotnet run --project DuetDiagram.Benchmarks -c Release -- --filter "*LayoutBenchmarks*" --job medium
```

最后一条会同时跑两个基准类：`LayoutBenchmarks`（第三方引擎本身）
与 `ConstraintLayoutBenchmarks`（我们这条全流水线）。两者必须在一次运行里出数，
理由见「基准数据」一节。

## 验收口径达成情况

| 口径 | 要求 | 实测 | 余量 |
|---|---:|---:|---:|
| 既有的固定位置与同层约束一条都不能退化 | 全通过 | `Category=Layout` **32 项**全通过 | — |
| 层内次序与逐元素对齐的不变量 | 全通过 | `Category=OrderAlign` **23 项**全通过 | — |
| 降级路径仍然认得四类约束 | 全通过 | `Category=LayoutFallback` **20 项**全通过 | — |
| 千节点布局 | ≤ 1000 ms | **12.13 ms** | **82 倍** |
| 千节点补齐逻辑 | ≤ 100 ms | 常见情形读不出正数；最坏情形 **3.6 ms** | **27 倍** |

补齐逻辑的绝对耗时读不出来——引擎调用在流水线正中间，从外面摘不出去——
但整条流水线（引擎加补齐）最坏也只到 **18.61 ms**，所以补齐一定在 100 毫秒预算之内。

## 交付了什么

四项约束全部在引擎之外补齐，引擎始终只看到一张合法的分层图。
前两项是 Phase 1 的，后两项是本轮的：

| 约束 | 作用在哪 | 手法 |
|---|---|---|
| 固定位置 | 绝对坐标 | 布局后回填，再按层做一次线性让位 |
| 同层 | 分层 | 收缩成超节点参与布局，布局完再展开 |
| 层内次序 | 层内的那个轴 | 按给定次序把成员换位到它们自己占过的槽位上，再跑一次让位 |
| 逐元素对齐 | 层内的那个轴（与让位同一个） | 取齐到组里第一个成员（有固定成员时以它为准）的坐标 |

流水线因此是八步：收缩 → 引擎 → 展开回填 → **对齐** → 让位 → **次序** → 折线重算。
对齐必须在让位**之前**（取齐可能把节点挪到别人身上，而让位正是用来解开那种情况的），
次序必须在让位**之后**（让位保持的是当前次序，而次序约束要改的恰恰是它）。
两个方向都不是随手定的，写反了的表现是"约束看着生效了但结果不对"。

## 保留项矩阵

四个降级级别各一行。逐级丢掉的是**约束的归属方**而不是约束的种类：
人定的比模型定的更值得保留，人看到图变样会立刻发觉，而模型只是少了一条提示。

| 级别 | 固定位置 | 同层 | 层内次序 | 对齐 | 相对位置 | 间距 |
|---|---|---|---|---|---|---|
| `Full` | 保留 | 全部 | 全部 | 全部 | 尚未实现 | 保留 |
| `DropLlm` | 保留 | 除模型提出的 | 除模型提出的 | 除模型提出的 | 尚未实现 | 保留 |
| `DropAll` | 保留 | 全丢 | 全丢 | 全丢 | 尚未实现 | 保留 |
| `PureAuto` | 丢 | 全丢 | 全丢 | 全丢 | 尚未实现 | 用引擎缺省 |

四类约束走的是同一段归属方过滤，所以新增的两类不会各自演化出不一样的降级行为。
这一层里有一条不显眼但会致命的转换：**层内次序在 IR 里存的是出边标识，而求解器要的是节点标识**
（平行边只能靠边标识区分，节点标识区分不了）。转换少做一次，求解器在节点里找不到那几个标识，
一声不吭地跳过——表现是"约束进了流水线却毫无效果"，与降级丢掉了它长得一模一样。
`Category=LayoutFallback` 里有三项专门盯这一段。

## 基准数据

中作业（`MediumRun`）：15 轮迭代、2 次启动、10 次预热。
规模：1000 节点、950 条连线、20 层。

| 基准 | 均值 | 误差 | 标准差 | 每次分配 |
|---|---:|---:|---:|---:|
| `LayoutBenchmarks.Layout_1000_Nodes`（引擎 + 构造输入） | 12.127 ms | ±0.078 ms | 0.112 ms | 10.80 MB |
| `LayoutBenchmarks.Build_1000_Nodes`（只构造输入） | 0.625 ms | ±0.011 ms | 0.016 ms | 2.32 MB |
| `ConstraintLayoutBenchmarks.Pipeline_1000_Nodes_No_Constraints` | **14.97 ms** | ±0.418 ms | 0.625 ms | 11.79 MB |
| `…Pipeline_1000_Nodes_With_Constraints`（251 个固定位置 + 次序 + 对齐） | **14.42 ms** | ±0.125 ms | 0.175 ms | 12.12 MB |
| `…Pipeline_1000_Nodes_With_Teleported_Layer`（整层被钉到别处） | **18.61 ms** | ±0.168 ms | 0.247 ms | 12.45 MB |

**为什么是"与无约束那一条之差"。** 引擎调用在流水线正中间，从外面没法把它摘出去单独计时。
而几条基线的引擎输入完全相同——固定位置与中级约束都不进引擎，它们是在引擎之外补齐的——
所以差值剩下的就是补齐逻辑本身。

引擎单独约 **11.5 毫秒**（12.127 减 0.625），全流水线 14.97 毫秒，差额约 **3.5 毫秒**。
其中很可能有一大半是诊断里的重叠统计：它是两两比较的平方复杂度，在千节点上是五十万次比较，
按设计不进分阶段计时，但确实在每次布局的调用路径上。**这是补齐逻辑里最值得优化的一段。**

## 四条观察

### 一、引擎仍然是绝对的大头

11.5 毫秒对 14.97 毫秒，引擎占七成以上。要继续压低布局耗时，先看引擎。

这与 Phase 1 的结论是同一条：**性能不是现阶段该花力气的地方。**

### 二、补齐逻辑的代价由固定节点的位置决定，不由约束的条数决定

常见情形（251 个固定节点骑在层边界上，再加一组次序与一组对齐）的耗时是 14.42 毫秒，
**比无约束那一条还低 0.55 毫秒**——差值落在误差里，方向还不稳定，所以准确的说法是"读不出正数"。

最坏情形（把第十五层整层钉到第一层的条带上）是 18.61 毫秒，比无约束高 **3.64 毫秒**。
两者的区别不在约束条数，而在**固定节点跑到了哪里**：整层被搬走之后，
"第十四层 → 第十五层"那五十条边必须横穿中间十几层，折线要在被切碎的空隙里找拐点。

这条结论对后面有用：要评估补齐逻辑的开销，构造用例时该盯的是"固定节点落在哪"，而不是"设了几条约束"。

### 三、无解与"我设了但没生效"必须能分辨

中级约束之间、以及中级约束与固定位置之间都可能互相矛盾。这一轮把它们分成两种报告：

- **求解阶段报"当时算不出来"**：成员跨层、两个固定成员坐标不同、固定节点挡住了要求的次序。
- **核对阶段报"算出来了但被后面的步骤推开了"**：取齐之后又被让位推开。

两者都要有：少了后者，那一类失效是静默的。但**求解阶段已经判定做不了的组必须从核对里排除**，
否则同一条约束会出现两条记录，而第二条的理由是错的——它写"被让位推开了"，
实际是压根没动过。这一条是写测试时才暴露出来的，现在有两条测试专门盯"只报一条"。

### 四、同一层的两个成员无法在层内轴上取齐

对齐轴与让位轴是同一个（都垂直于分层方向），这个选择是对的：对齐若动分层轴，
节点就会跑到别的层去。但它推出一件事——**同一层的两个节点在层内轴上取齐，等于让它们重叠**。
这种组无解，实现如实报成冲突，而不是悄悄丢掉约束。

代价是语法文档里 `align pass, fail` 那个例子举的是同一层的两个分支，按本轮的语义它是无解的。
真正有意义的用法是跨层："这几个节点排成一列"。

## 已知取舍与未验证

| 项 | 说明 |
|---|---|
| 同一层的成员要求对齐 | 几何上无解（取齐等于让它们重叠），实现如实报出。界面入口要不要拦住这种设置，等有交互数据之后再定 |
| 对齐的轴只有一条 | 约束里没有轴字段，对齐轴固定为"垂直于分层方向"。再区分左对齐与居中对齐需要给约束加字段，本轮不做 |
| 多条次序组落在同一层 | 逐组换位，前一组摆好之后后一组在它的结果上继续。两组互相矛盾时按先后各报一次，没有做全局的次序合并 |
| 等宽网格上无法跨层取齐 | 每层都排满的网格里，任何跨层的取齐都会撞上目标层已有的节点。基准里那条对齐是靠把一个固定节点放到整层之外才成立的 |
| 诊断里的重叠统计 | 平方复杂度，按设计不进分阶段计时，但在每次布局的调用路径上，很可能是补齐逻辑里最贵的一段。要压它得换成扫描线，或者只在诊断模式下开启 |
| 固定节点比例更高时 | 只测到四分之一。更高比例下让位会把层推得很长，实际效果需要单独评估 |
| 真实拖动的分布 | 用的是构造出来的输入。真实用户拖动的位置更零散，可能出现构造用例覆盖不到的组合 |
| 界面入口 | 本轮的界面入口不在范围内，先把引擎侧的接线做出来。界面先做出来会得到一个能点但没效果的控件 |
| 布局参数变化后的重排 | 每次都从零布局，没有验证增量更新（只改动局部时能否复用上一次结果） |
