# Phase 5 无障碍——键盘导航与屏幕阅读器

- 测量时间：2026-09-26
- 测量机器：AMD Ryzen 5 6600H（6 物理核 / 12 逻辑核），16 GB
- 系统：Windows 11 专业版 10.0.26200
- 运行时：.NET 10.0.11，x64 RyuJIT，.NET SDK 10.0.303
- 用途：Phase 5 判据「WCAG AA」的可机验部分——每个交互控件有可访问名称、键盘能到达、焦点顺序跟着功能分组

## 复现

```bash
dotnet build DuetDiagram.slnx -c Release

# 无障碍用例（10 条）。全通过则退出码 0
dotnet test --project DuetDiagram.E2E.Tests/DuetDiagram.E2E.Tests.csproj -c Release -- --filter-trait "Category=Accessibility"
```

用例在无头宿主里起一个**真的窗口**（`HeadlessFixture.Open`），走的是主程序自己那个应用类型，
所以量到的是界面上真正摆出来的控件，不是另造的一套。

## 判据达成情况

| 判据 | 装置能判到什么程度 | 结论 |
|---|---|---|
| 每个交互控件有可访问名称 | 全窗口 127 个交互控件逐个读名字，空的当场失败 | **达成** |
| 键盘能到达 | 逐个断言"能 Tab 停靠且可聚焦"；再从画布起步按 160 次 Tab，看焦点进没进每一块面板 | **达成** |
| 焦点顺序跟着功能分组走 | 四个面板逐对比较号的大小：列表那一排的号必须小于"对它做事"那一排 | **达成** |

退出码 0。下面把"名字从哪来""号为什么是显式给的""哪些只能等人"逐条写清楚。

## 名字从哪来

**名字一律来自数据，不来自控件在界面上的位置。** 这样新加一条条目、加一层、加一个令牌，
名字会自己跟上，而漏掉的那一处会当场失败。

| 控件 | 名字的构造 | 例 |
|---|---|---|
| 工具栏按钮 | `档名：条目标签` | `对齐：同层` |
| 菜单项 | `条目标签`（档名由上一级菜单念出来） | `同层` |
| 顶级菜单 | `档名` | `对齐` |
| 右键菜单项 | `档名：条目标签` | `组合：建分组` |
| 画布 | 固定，说明里列键盘能做什么 | `图画布` |
| 图层行的两个勾选框与两个箭头 | `「图层名」这一层…` / `把「图层名」…` | `「上层」这一层画不画` |
| 页签 | `第 N 页「页名」` | `第 2 页「第二页」` |
| 调色板条目行 | `选中调色板条目「令牌名」` | `选中调色板条目「brand」` |
| 形状 | `把选中的节点换成「形状名」形状` | `把选中的节点换成「六边形」形状` |
| 模板 | `放入模板「模板名」` | `放入模板「基本流程」` |
| 属性面板的字段编辑器 | 字段名 | `字号` |
| 调色板／文本预设的成员编辑器 | `…「条目名」的成员名` | `调色板条目「brand」的填充` |
| 约束行的删除按钮 | `删掉这条约束：这一行的内容` | `删掉这条约束：同层…` |

三处刻意的选择：

**工具栏带档名，菜单不带。** 工具栏上不显示档名，只念 `同层` 的话说明不了它是"让两个节点排在同一层"；
菜单里档名已经由上一级菜单念出来了，再拼一遍会念成"对齐 菜单，对齐：同层"。
代价是「导出」档里那条「导出…」会读成"导出：导出…"——重复，但名字的构造方式必须可预期，
不能"看着重复就去掉"，否则读屏用户听到的名字会随标签措辞变。

**名字里带上"是哪一个"。** 图层行的四个控件、调色板与文本预设的成员框，屏幕上靠位置分辨
（"就在选中那一行下面"），而这条线索阅读器听不到，所以名字里必须带图层名、令牌名、预设名。

**画布的说明里列键位。** 画布是一整块自绘区域，里面画了哪些节点、哪一条边阅读器读不到，
能读的只有名字与说明，所以键盘在这块地方能做什么必须写在说明里（空格加左键平移、滚轮缩放、
双击改标签、右键出菜单，以及菜单栏与工具栏上那几条带快捷键的）。

## 焦点顺序：号是显式给的

四个面板的界面标记里，底部那一块（新建、改名、应用、删除）**声明在列表之前**，
而默认的 Tab 次序就是控件在视觉树里的先后。于是不处理的话，Tab 会先落到"新建/删除"上，
再落到列表上——用户得先跳过一排"对谁做事"的按钮，才能走到"对谁"。

修法不是把声明挪个位置：**次序是界面的约定，不是文件里那几行的先后**，
照着文件的先后排，下一次谁调整一下标记的顺序，焦点顺序就跟着变，而这件事看不出来。
所以四个面板各占一段互不重叠的号段，面板内部按功能分组给号：

| 面板 | 号段 | 面板内的次序 |
|---|---:|---|
| 图层面板 | 1000 ~ | 逐行（显示、锁定、上移、下移），然后底部那一块 |
| 调色板面板 | 2000 ~ | 逐条，然后新建，然后成员编辑器，最后删除 |
| 文本预设面板 | 3000 ~ | 逐条，然后新建，然后成员编辑器，然后应用、删除 |
| 标签栏 | 4000 ~ | 逐页，然后新建、删页 |

用例判的就是号：列表那一排里最大的号，必须小于"对它做事"那一排里最小的号。
两类各要至少命中一个控件——都落空的话两边都是 `-1`，这一条会假绿。

## 键盘可达：改了什么

| 处 | 之前 | 之后 | 为什么 |
|---|---|---|---|
| 调色板条目行 | 一块能点的画布（`Grid` + 指针按下处理器） | `Button` | 鼠标点得到而键盘到不了：Tab 走不进来，回车也没人接。按钮自带聚焦、回车与空格激活、焦点框 |
| 文本预设条目行 | 同上 | `Button` | 同上 |
| 菜单容器 | 没有名字 | 加了名字 | 阅读器要说出这一块是菜单，不然用户不知道手上是什么 |

**菜单容器没有加"可聚焦"。** 界面框架的菜单交互处理器按焦点所在的那一项判断，
焦点落在容器上时它什么都不做——把容器做成 Tab 停靠，只会多出一个按了没反应的落脚点。
焦点该落在顶级菜单项上（那几项本来就是 Tab 停靠且可聚焦的），方向键在那儿才展开这一档。
用例单独验了这一条：焦点放到第一个顶级菜单项上，按方向键，它的子菜单要打开。

## 发现

### 一、默认文档是空的，所以「每一行」这件事要先造出东西来

样本文档既没有图层也没有页面、没有调色板令牌、没有文本预设。于是「每一层的四个控件名字要能分辨」
「页签排在动页那几颗之前」这两条，在默认窗口里是**空集上成立**——一条断言都没有跑。
用例里补了造一层、造一页、造一个令牌、造一个预设这四步，之后才量。这类「空集上假绿」是
这一轮最容易漏掉的东西：不加这一步，四条面板的用例全绿，而实际上一个控件都没验。

### 二、模板面板的控件数随目录走

形状面板的清单是编译期定下的（8 个），模板面板的清单来自磁盘上的模板目录。
同一台机器上目录里有几个模板，面板上就有几颗按钮——用例里没有对模板面板的条数下判据，
只保证「出现在界面上的那几颗都有名字」。这一条与模板目录的内容绑定，换一台机器数量会变。

### 三、127 个交互控件，按块分

在一层、一页、一个令牌、一个预设的最小规模下量到：

| 块 | 个数 | 块 | 个数 |
|---|---:|---|---:|
| 菜单栏 | 27 | 属性面板 | 24 |
| 工具栏 | 15 | 文本预设面板 | 13 |
| 就地编辑器 | 9 | 图层面板 | 9 |
| 形状面板 | 8 | 调色板面板 | 8 |
| 标签栏 | 4 | 布局失败提示 | 3 |
| 人工产物恢复提示 | 2 | 模板面板 | 1 |
| 变更边栏 | 1 | 诊断面板 | 1 |
| 导入报告 | 1 | 画布 | 1 |

**合计 127。** 计数只算「这一层自己搭出来的」控件：模板里长出来的零件（滚动条两端的箭头、
下拉框右半边那颗按钮）不算——它们不是这一层能命名或该命名的东西，算进来这一条永远绿不了。
判据是「模板父级为空」。

菜单栏那 27 个里有 20 个是菜单项、6 个是顶级菜单、1 个是容器本身。它们只在逻辑树上
（菜单展开之前不进视觉树），所以遍历要把视觉树与逻辑树合起来走——只走视觉树的话，
菜单项会被整块漏掉，而那正是「看不见的地方最容易没有名字」。

### 四、菜单容器自己不收焦点

界面框架的菜单交互处理器按**焦点所在的那一项**判断，落在容器上时它什么都不做。
给容器加「可聚焦」试过，没用：按方向键仍然展不开。焦点该落在顶级菜单项上——
那几项本来就是 Tab 停靠且可聚焦的，方向键在那儿才展开这一档。
用例单独验了这一条：焦点放到第一个顶级菜单项上，按方向键，它的子菜单要打开。

## 只能等人

装置判的是**底座**：名字在不在、名字说得出是哪一个、Tab 到不到、号是不是显式给的。
下面这几项判不了，只能等人——**不写成通过**：

| 项 | 说明 |
|---|---|
| 对比度 | 界面上的颜色全是写死的十六进制（`#8a94a3`、`#d8dee7` 这类）。判据要求 AA（正文 4.5:1、大字 3:1），而这一轮**没有算过任何一组的对比度**，也没写装置去算。要验得逐对取前景与背景算比值，而背景有叠层（面板底色 + 边框 + 半透明诊断面板），不是一个数能算出来的 |
| 读屏软件实际读得顺不顺 | 装置读的是自动化名称这一个字段。真人戴读屏走一遍才知道：名字的断句对不对、切换选中之后该不该主动播报、密集面板里逐控件 Tab 过去是否可忍受 |
| 焦点可见性 | 焦点框由界面框架的主题给，这一轮没验过它在深色底、在自绘画布上是否看得清 |
| 画布里的元素 | 画布是一整块自绘控件，**没有为节点与边建虚拟化的自动化树**。读屏用户听得到「图画布」与那句键位说明，但听不到「图里有五个节点、选中了哪个」。要补这一条得给画布挂一个自定义自动化对等体，把绘制列表映射成自动化子树——那是另一件事，不在本轮 |
| 选中变化不播报 | 状态栏与变更边栏上的字会随操作变，但没有标成活动区域，读屏软件不会主动念出来 |
| 就地编辑器的四颗样式按钮 | 刻意不接收焦点：它们读的是编辑框此刻的选区，而选区是编辑框上的活状态，焦点一挪走就读不到那一段了，一次加粗会变成「对空选区加粗」。代价是这四颗只能用指针按。要补得先把选区从焦点解耦（例如把选区记到状态对象上、按钮不再读控件） |

## 已知取舍

| 项 | 说明 |
|---|---|
| 只有一个窗口尺寸 | 用例在 900 × 600 下跑。窄窗口下左右两栏会不会挤掉、有没有控件被裁到看不见，没有量 |
| Tab 走查是采样不是穷举 | 上限 160 步，是按今天这块界面的规模定的两倍余量。面板再多几块，这个数要跟着涨；涨过头会表现为「某一块没走到」，而那是断言失败，不是静默通过 |
| 号段是按今天的面板数量划的 | 四个面板各占一段（1000 / 2000 / 3000 / 4000），面板内的行按每行十号排。行数超过八百左右会与底部那一块撞号，实际规模远不到 |
| 用例只在无头宿主里跑 | 无头宿主与真实窗口用的是同一套焦点管理，但真实窗口上还有操作系统级的辅助功能桥（Windows UIA）。那一层没有验 |
| 没有验 Tab 之外的通路 | 方向键在面板内的移动、`Alt` 加访问键、`AccessKey` 一个都没做，也没验 |
| 名字是中文且写死 | 与文化相关的那一层见 Phase 5 的 i18n 那一条；名字进不进资源文件由那一条定 |
| 名字与号是横切的 | 命名落在 50 处（42 处在代码里、8 处在标记里），新加一块面板要记得两件事都补——用例能拦住「没名字」，但拦不住「名字给错了」 |
