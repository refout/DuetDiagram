# Phase 5 千节点流畅性

- 测量时间：2026-09-26
- 测量机器：AMD Ryzen 5 6600H（6 物理核 / 12 逻辑核），联想 21D0，16 GB，**无独显（软件光栅化）**
- 运行时：.NET 10.0.11，x64 RyuJIT（x86-64-v3），.NET SDK 10.0.303
- 用途：Phase 5 判据「1000 节点流畅」的常驻取证（帧率 ≥ 30 FPS、剔除率 > 80%、拖拽单帧中位 ≤ 16 ms）

## 复现

```bash
# 千节点帧率与剔除率：两种模式用同一份绘制列表、同一个视口，各测 120 帧，预热 10 帧
dotnet run --project DuetDiagram.App -c Release --no-build -- --benchmark-frames --nodes 1000 --frames 120

# 拖拽单帧处理耗时：一千节点上开一条拖拽，连续采样 200 次，预热 10 帧
dotnet run --project DuetDiagram.App -c Release --no-build -- --benchmark-drag --nodes 1000 --samples 200
```

两条命令都不另造装置：它们就是 P2-03 与 P2-06 落地的那两个基准，这一条只是把它们
从「Phase 2 的取证」提升成「Phase 5 的常驻门禁」，并写进 `AGENTS.md` 的门禁清单。

CI 里其实已经在跑这两条判据，但**帧率那一条跑的是带 `--highlight` 的形式**
（`app-and-aot` 那一组：`--benchmark-frames --nodes 1000 --frames 120 --highlight`）。
判据是同一条（`Check(plain, culled, cullRate)`，与开关无关），所以「千节点帧率 ≥ 30 且剔除率 > 80%」
在 CI 上已经被守着；不带开关的那条命令本地跑，用来量纯基线。
这里说清楚是因为「CI 已经在跑」是这一条能当常驻门禁的理由，而它跑的是哪一种形式必须对得上。

## 验收口径达成情况

| 口径 | 要求 | 实测 | 余量 |
|---|---:|---:|---:|
| 千节点帧率（虚拟化那一档） | ≥ 30 帧每秒 | **139.5 – 152.0 帧每秒**（四次完整运行 + 一次收尾复跑） | 4.7 倍 |
| 虚拟化剔除率 | > 80% | **86.3%**（五次运行完全一致） | 6.3 个百分点 |
| 拖拽单帧处理耗时 | ≤ 16 ms | **0.271 – 0.292 ms**（中位，1000 节点 / 200 样本，五次运行） | 55 倍 |

两条命令的退出码都是 0。

## 量的哪一段（口径写死）

这一节是这一条任务的硬要求：口径不写死，改一处常数就改了结论。

### 一、帧率取稳态帧的**均值**，中位只作对照

`FrameBenchmark.Measure` 每帧量一次 `RenderTargetBitmap.Render` 的墙钟耗时，
丢弃前 10 帧（即时编译、字形缓存、建索引那些首帧成本不算稳态），
再对 120 个样本同时算出**均值**与**中位**，两个都印出来。

**判据读的是均值**（`1000 / culled.Mean < MinimumFps`），不是中位。
中位那一行留在输出里，是让人看见分布的另一半——两者在千节点这一档上差出三成
（均值 6.58 ms 对中位 4.95 ms），差值就是尾部那几帧的停顿。

所以报告里写的「142 帧每秒」这类数字，来源是**均值**。

### 二、剔除率按**指令条数**算，不按面积

`CullingIndex.CullRate = (总指令数 − 可见指令数) / 总指令数`。
千节点这一档是 `(2968 − 406) / 2968 = 86.3%`。

不按面积算：面积口径下「一个盖满视口的大节点」与「一个角落的小节点」权重不同，
而这一档要答的问题是「这一帧少画了多少条」，不是「少画了多少像素」。
代价是它看不见「被剔掉的都是小东西」这种偏差——那一条由逐像素比对守着（`Category=ModeSwitch`）。

剔除率是**确定的**：视口与内容定下来之后，2968 条里恒定只画 406 条，五次运行一模一样。
帧率不是——同一台机器上四次完整运行差出 9%（139.5 ~ 152.0），量的是光栅化耗时，受后台负载影响。

### 三、视口是内容面积的**十二分之一**

`VisibleFraction = 1.0 / 12`，倍数由内容范围反算（`sqrt(1920×1080 / (内容面积 / 12))`），
千节点这一档约 1.39 倍。这对应一个用户真会用的倍数——屏幕上摆得下几十个节点。

这个数不能取更小：预取边距是固定的文档尺寸（100 像素），图越小、倍数越大，
边距那一圈占的比例越高；留到八分之一时它就把剔除率压到八成以下，
而**剔除本身并没有变差**，变的是测量点选在了哪儿。

### 四、拖拽量的是**帧首那一次偏移**，不含布局

计时区间只有 `CanvasViewModel.BeginFrame()` 这一句。同一循环里的
`session.UpdateDrag(...)` 在 `Stopwatch` 之外，不进样本。

这一条是有意的：拖拽中不调布局、不发命令，整条链路只在松手那一刻跑一次，
而这里要卡的是「一帧里把选中节点连同相连边整体挪一下」这一笔。
把 `UpdateDrag` 也算进来的话，量到的是「拖拽这次交互有多快」，
而它一半的开销在松手那一次重布局上——那是另一条判据（`reports/phase2-drag.md`）。

判据读的是 200 个样本的**中位**，最大值照常印出来（3.358 ~ 4.632 ms）。
单次尖峰里混着系统调度与垃圾回收，拿最大值当判据等于让一次停顿否掉整套设计。

## 基准数据

### 帧率与剔除率

一千个节点、968 条连线、2968 条绘制指令、内容范围 3728 × 3434。
画布 1920 × 1080，视口缩到只看得见内容面积的十二分之一。目标位图整段复用一块，不每帧新建。

| 运行 | 造文档到绘制列表 | 回退档均值 | 回退档中位 | 虚拟化均值 | 虚拟化中位 | 剔除率 |
|---|---:|---:|---:|---:|---:|---:|
| 一 | 258.4 ms | 41.95 ms（23.8 fps） | 37.69 ms | 7.03 ms（142.2 fps） | 5.16 ms | 86.3% |
| 二 | 255.8 ms | 42.00 ms（23.8 fps） | 35.26 ms | 6.68 ms（149.8 fps） | 4.97 ms | 86.3% |
| 三 | 260.4 ms | 42.20 ms（23.7 fps） | 36.93 ms | 7.17 ms（139.5 fps） | 5.28 ms | 86.3% |
| 四 | 259.9 ms | 40.03 ms（25.0 fps） | 36.90 ms | 6.58 ms（152.0 fps） | 4.95 ms | 86.3% |

收尾复跑（只取了后六行，没记造文档那一段）：虚拟化均值 6.85 ms（146.0 fps）、
回退档均值 42.52 ms（23.5 fps）、剔除率 86.3%——落在同一区间内。

千节点那一档量的是**虚拟化**。回退档的数字照常报出来，它回答的是另一个问题——
「这个阈值定得对不对」。六倍的差距说明在千节点这一档上，
索引的维护成本远远压不过它省下的绘制。

回退档本身只有 23.7 到 25.0 帧每秒，远低于 30。它**不达标，也不该判它不达标**：
阈值默认 500 元素，这个尺寸上应用跑的就是虚拟化。要求回退档也达标等于说阈值可以取无穷大，
那样虚拟化本身就没有存在的理由了。

平台就绪那一段（349.8 / 361.5 ms）是进程内 `SetupWithoutStarting` 的耗时，
不是冷启动——冷启动是 P5-04 的判据，用另一条命令量。

### 拖拽单帧处理

| 运行 | 单帧处理中位 | 单帧处理最大 |
|---|---:|---:|
| 一 | 0.277 ms | 3.485 ms |
| 二 | 0.292 ms | 3.475 ms |
| 三 | 0.286 ms | 3.685 ms |
| 四 | 0.282 ms | 4.632 ms |
| 五 | 0.271 ms | 3.358 ms |

单帧处理只做「把被拖元素的指令整体偏移、其余原样」这一件纯计算。
一次拖动波及的元素数是**一个节点加它的相连边**（这里是 2 个），与节点总数无关，
所以中位稳定在 0.28 ms 上下。规模化后的耗时来自布局与绘制列表构建，
那是一次性的、不在每帧里。

## 发现：Phase 2 报告里的拖拽中位不可复现

`reports/phase2-drag.md` 记的是 **11.321 ms**，并据此写着「余量 1.4 倍」。
这一轮复测是 **0.28 ms**，差 40 倍。查了一遍，结论是**那个数字不可复现**：

| 查法 | 结果 |
|---|---|
| 当前代码，Release | 0.271 ~ 0.292 ms |
| 该报告所属的那个提交（`c7ef0a2`）在临时工作树里重建，Release | 0.310 ms |
| 同一个提交，Debug | 0.365 ms |
| 机器 | 同一台（Ryzen 5 6600H / 6 核 12 线程，与那份报告里写的一致） |
| `FrameBenchmark.cs` 与该提交的差异 | 无（`git diff` 为空，`RunDrag` 逐字相同） |
| `CanvasViewModel.BeginFrame` 与 `Shift` 的差异 | 无 |

也就是说：**同一台机器、同一个提交、同一条命令，量不出 11.321 ms**。
Debug 与 Release 都试了，都不成立。

剩下的解释只有「量的时候机器状态不同」这一类，而那是无法事后区分的。
所以这一条**不写成「已修正」，写成「不可复现」**：

- Phase 5 这一档以本报告的 **0.28 ms** 为准，判据的真实余量是 **55 倍**，不是 1.4 倍；
- `reports/phase2-drag.md` 的正文不改（那是当时那次测量的记录），
  只在它的「已知取舍与未验证」里加一行指向本报告。

顺带记一处同类差异，避免误读：帧率也比 Phase 2 报告高约 1.4 倍
（虚拟化均值 6.58 ~ 7.17 ms 对那里的 9.83 ~ 12.07 ms）。
但**两种模式同时变快了同一个倍数**，且剔除率一字不差（86.3%），
这与「绘制列表内容变了」和「机器状态不同」两种解释都相容，无法区分。
它不像拖拽那一条那样构成矛盾，所以不单列发现，只作为**跨报告比数字时的告警**记在这里。

## 已知取舍与未验证

| 项 | 说明 |
|---|---|
| 本机值是软件光栅化的结果 | 本机无独显，走的是软件光栅化。这些数字是**本机值，不是产品保证值**；换一台带独显的机器会明显不同，而那种机器上的数字同样不代表别人的机器 |
| 帧率的可复现性 | 同一台机器上四次完整运行差出 9%。剔除率是确定的，帧率不是；判据里那 4.7 倍余量因此不能当成「还有 4.7 倍可花」 |
| 剔除率只在十二分之一这一个缩放点上量过 | 换个倍数数字会变。要做成一张表得先定「用户常用的倍数」是什么，而那需要真实的交互数据 |
| 拖拽只量了单节点拖动 | 加选整批拖、拖组合、拖被锁定图层，走的都是同一段 `Shift`，但波及的元素数不同；这一条只覆盖了最小的那一档 |
| 拖拽的最大值没进判据 | 3.358 ~ 4.632 ms，是中位的十几倍。判据只卡中位，尾巴照常印出来让人看见 |
| 帧率判的是均值、拖拽判的是中位 | 两处口径不同，是有意的：帧率要的是「这一档稳定不稳」，拖拽要的是「常态有没有超标」。改口径会同时改结论，所以写死在上面 |
| 跨机器与跨平台 | 只在本机量过。原生编译（AOT）下的这两个基准没有跑——本机缺 C++ 工作负载，见 `reports/phase0a.md` |
| Phase 2 报告的数字 | 拖拽那一条不可复现（见上一节）。帧率那一条与本次相差 1.4 倍，无法区分是内容变化还是机器状态 |
