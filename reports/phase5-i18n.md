## 这一条最大的约束：不变量全球化

`InvariantGlobalization=true` 写在**根目录的构建属性**里，全仓生效。实测（仓外一次性探测程序，
属性照抄）：

```
new CultureInfo("en-US")
  → CultureNotFoundException: Only the invariant culture is supported in globalization-invariant mode.
CurrentUICulture.Name → ""（不变量）
```

推论有三条，都是硬结论：

1. **`CurrentUICulture` 驱动的卫星程序集查找在本仓永远选不出第二语言。** 具名文化建不出来，
   卫星那一层就没有任何东西会去选它。所以判据里"切换文化"这句话**不能按字面实现**。
2. **语言只能由显式代码指定。** 这一条做的是 `Strings.Language = "en"`，取文字时用
   `ResourceManager(baseName, assembly)` + `CultureInfo.InvariantCulture`，全程不碰 `CurrentUICulture`。
3. **第二个语言不能做成卫星程序集。** 做成了也是一份死重量。它改成嵌进主程序集：
   项目文件里声明 `WithCulture=false` 并显式给 `LogicalName`。

这一条也在同一个探测程序里验过：在 `InvariantGlobalization=true` + `IsAotCompatible` +
裁剪分析器下，两个 resx（一个中性、一个嵌主程序集）都取得到，**0 警告**；
第二语言里没有的键返回空（回落由门面自己写）。

## 语言怎么切

```csharp
Strings.Language = Strings.English;   // 或 Strings.Chinese
```

认不出的代码**直接抛**：默默退回中文的话，配置里写错一个字母的表现是"界面没变"，
而没人会想到去查那个字母。

**换语言要在开窗口之前。** 界面文字在窗口搭起来时取一次，已经开着的窗口不会自己重取。
当前没有任何界面入口改它——这一层是预留，不是给用户用的多语言切换。

## 档的标识与档名分开（这一条真正的工程点）

菜单的七个档，`MenuGroups` 上的常量原来是**同时**当身份与显示文字用的（`"编辑"` 这两个字）：
注册表按它分组（`On(surface, group)` 按序号比较），三个 E2E 用例也拿它当身份
（工具栏那一组断言 `ToolBarOrder.Should().Equal([MenuGroups.Edit, …])`）。
把显示出来的字当身份用的话，**换一种语言就找不到自己了**——中文下
`On(MenuSurface.Menu, "Edit")` 会返回空，而那种空看起来像"这一档没有条目"。

所以拆成两样：

| | 是什么 | 例子 |
|---|---|---|
| `MenuGroups.Edit` | 标识。注册表按它分组，用例按它找控件 | `"edit"` |
| `MenuGroups.Display(id)` | 档名。按当前语言从资源里取 | `"编辑"` / `"Edit"` |

同一条口径落在条目上：`MenuEntry.Id` 与 `MenuEntry.Group` 是标识，`LabelKey` 是资源键，
`Label` 是按当前语言取出来的字。用例里有一条专门验"换语言之后按标识分组的结果不变"。

## 资源键是接口

- **一处文字一个属性，一个属性一个键。** `Strings` 上的属性是编译期接口（写错属性名编译不过），
  资源文件里的键是运行期接口（翻译者按键取那一句）。用例两个方向都查：
  "资源里有键没人取"与"代码里取了不存在的键"各漏一半。
- **整句一个键，不拼。** 带占位符的走格式串：`menu.shortcut` = `{0}（{1}）`、
  `menu.entry-name` = `{0}：{1}`。条目不能点时的理由也是整句一个键，
  不是"先选中"加一个宾语拼出来——在调用处拼的话，换一种语序就拼不成句子了，
  而语序正是翻译要改的东西。这一条也把原来 `MenuRefusals.NoSelection(context, "要删的元素")`
  那种"传一个宾语进来拼"的写法改掉了。
- **缺的键回落中性资源；两边都没有直接抛。** 抛而不是返回键名：键名会原样显示在界面上，
  而"界面里出现一串英文键"看起来像界面坏了，实际是漏了一条资源。

## 标记里的字怎么引

`Text="{x:Static res:Strings.PanelLayersTitle}"`，文件头加 `xmlns:res="using:DuetDiagram.App.Resources"`。

**`x:Static` 是构建期解析的，不是运行期反射。** 试过把一个成员名写错，报的是
`AVLN2000: Unable to resolve "Strings.NoSuchMemberXyz" as static field, property, constant or enum value`，
**构建失败**。这一条很重要：本仓开着原生编译与裁剪分析器，运行期反射的用法在真原生发布下会出问题，
而本机缺 C++ 工具链、跑不了真原生发布（见 `reports/phase0a.md`），
所以"它是编译期展开的"只能靠"写错就编译不过"来旁证。

## RTL 只验不破版

不变量全球化下文化给不出 `TextInfo.IsRightToLeft`，所以用例直接设 `FlowDirection.RightToLeft`。

判据是**镜像之后逐块对得上**：尺寸不变、位置正好是绕窗口竖中线翻过来的、
本来就放得下的翻过来也放得下。逐块量到的（900 × 600 的客户区）：

| 面板 | 从左到右 | 从右到左 |
|---|---|---|
| 图层面板 | 0, 70, 240, 228 | 660, 70, 240, 228 |
| 形状面板 | 0, 298, 240, 305 | 660, 298, 240, 305 |
| 模板面板 | 0, 603, 240, 122 | 660, 603, 240, 122 |
| 调色板面板 | 0, 725, 240, 0 | 660, 725, 240, 0 |
| 文本预设面板 | 0, 725, 240, 169 | 660, 725, 240, 169 |
| 属性面板 | 600, 70, 300, 501 | 0, 70, 300, 501 |
| 标签栏 | 240, 70, 360, 45 | 300, 70, 360, 45 |
| 工具栏 | 0, 32, 900, 38 | 0, 32, 900, 38 |
| 菜单栏 | 0, 0, 900, 32 | 0, 0, 900, 32 |
| 画布 | 240, 115, 360, 456 | 300, 115, 360, 456 |

每一块都是 `x' = 900 − x − w`，尺寸一字不改。

### 量矩形要量两个角（第一次量错的记录）

第一次量出来的是"图层面板跑到 900, 70，宽 240，越出了客户区"——看着像 RTL 破版。
实际是**量法错了**：从右到左不是把每个控件挪个位置，而是给整棵树挂一层镜像，
镜像之下左上角量出来的那个点已经跑到框的右边去了；再往右加一个宽度，
得到的是一个真实位置上不存在的框。改成量两个角、自己归一化之后，
图层面板落在 660, 70 ——正好是 0, 70 绕竖中线翻过来的。

顺带说一句：`Rect(Point, Point)` 这个重载**不做归一化**，两个角给反了会得到一个宽度为负的矩形，
而负宽度看着像"尺寸变了"。归一化要自己写。

### 一个与 RTL 无关的既有情况

判据**不是**"每块都在客户区里"，因为**这个窗口尺寸下左栏本来就装不下**：
900 × 600 的客户区里，左栏五块面板的底边分别落在 298 / 603 / 725 / 725 / 894 ——
模板、调色板与文本预设三块都超过了客户区高度，调色板那块高度甚至是 0。
左右两个方向一模一样，所以它与方向无关，不是 RTL 的问题，是**窗口尺寸与左栏内容高度之间的关系**。
如实记在这里，不在这一条里改（左栏要不要能滚、要不要按比例分高，是布局的事）。

## 与任务清单的出入

1. **卡里的 `Strings.zh-CN.resx` 换成了 `Strings.en.resx`。** 不变量全球化下 zh-CN 卫星永远选不出来，
   是死重量；中性 `Strings.resx` 装中文，第二个语言（英文）嵌主程序集、按显式代码选。
   它的作用是**证明取文字这条路真的通**——只看一种语言时，"来自资源"与"硬编码"分不开。
2. **卡里的验收写"切换文化后…"，实际做的是切语言代码。** 见上面第一条推论：
   `CultureInfo` 在本仓建不出具名文化，按文化切换物理上做不到。这是与卡片口径的一处实质差别。
3. **"所有界面硬字符串迁到资源"只做到一部分。** 卡里 `estimated_loc: 260`，
   而 `DuetDiagram.App` 里带中文的字符串字面量有 1125 处（去掉异常消息 936 处，
   再去掉装置与命令行输出 778 处）。260 行覆盖不了 778 处，所以按仓里已有的
   "收窄 + 记下理由"先例收窄：机制、菜单这一条链、各面板静态标题、门禁、文档；
   其余逐类列在 `docs/Internationalization.md` 的遗留表里，并给出搬运的做法。
4. **`docs/Internationalization.md` 是新增的**，卡里没列（卡里只列了两个 resx）。
   机制与边界不写下来，下一个人加一条文字时会把键拼错、或者又写回硬编码。
5. **多了一条源码扫描门禁。** 卡里没有，但"文字来自资源"这件事只有靠扫描才拦得住回退：
   新加一条条目时忘了写键，屏幕上照样有字，而它不会跟着语言变。
   扫描跳过注释与异常消息——注释是给改代码的人看的，异常消息只给开发者看，界面上不会出现。
6. **可访问名称这一层没迁**（标记里 8 处 + 代码里 50 处）。只迁标记那一半会让这一层半新半旧，
   索性一起留着，与其余未迁项同一条口径。
7. **判据不是"每块面板都在客户区里"**，而是"镜像之后逐块对得上"。
   原因见上面那条：左栏在 900 × 600 下本来就溢出，而那种溢出与方向无关。

## 已知取舍与未验证

| 项 | 说明 |
|---|---|
| 只有中文与英文两种 | 英文是**用来证明这条路通**的，不是交付一份译文；它自己也没有经过母语者校对 |
| 界面文字只迁了一部分 | 75 条键；其余约 700 处逐类列在 `docs/Internationalization.md` |
| 没有界面入口换语言 | 这是预留，不是给用户用的多语言切换 |
| 换语言不重画已开的窗口 | 文字在窗口搭起来时取一次；要做"当场改写"得把每一处文字变成可通知的属性 |
| 没有按语言变格式与复数 | 不变量全球化下连 `CultureInfo` 都建不出来，那要先把全球化模式打开 |
| 排版不随语言变 | 字号、行高、控件宽度都按中文调的；英文更长的地方会换行或截断，没有按语言调过 |
| 英文没有母语者校对 | 那 74 条是我按词义直译的，语感没有验过 |
| RTL 只验了不破版 | 没有验阿拉伯语的排版、镜像图标、数字方向那些；也没有真人用过 |
| 真原生发布下没验过 | `x:Static` 的编译期展开靠"写错就编译不过"旁证；本机缺 C++ 工具链，跑不了真原生发布 |
| 只有一台机器、一个窗口尺寸 | 900 × 600、默认主题、默认 DPI；换尺寸之后左栏的溢出情况会变 |
