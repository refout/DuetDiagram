# Phase 5：布局质量评分

## 一、结论

**语料综合质量分 96.6，达到方案 §14.3 的「Phase 5：布局评分 ≥ 85」判据。**

- 门禁：`dotnet run --project tools/LayoutScore -c Release` 退出码 0。
- 语料 11 份种子图，10 份排得出来，1 份（`cycle-4`）排不出来。
- 排出来的 10 份：简单平均 95.7，最低一份 91.8，没有哪一份低于 85。
- **综合分按节点数加权**，大图更难排、也更能说明问题；简单平均一并报出，不混入主数。
- 排不出来的那一份**不计入综合分**（理由见第四节），但它在报告最前面单列——
  它比分数本身更值得看。

**取证装置比数字重要。** `tools/LayoutScore` 不进解决方案文件（与 `tools/LocCounter`、
`tools/CoverageAudit`、`tools/CompareHarness` 同一口径），语料、四个维度与权重都写死在
`Corpus.cs` 与 `Rubric.cs` 里，换一个人跑同一个装置应得到同一个数。

## 二、取证方法

```
dotnet run --project tools/LayoutScore -c Release                      # 印分数与明细，退出码 0/1/2
dotnet run --project tools/LayoutScore -c Release -- --dump fork-6     # 印某一份图的坐标与折线
dotnet run --project tools/LayoutScore -c Release -- --ratings <路径>  # 与人工评分对照
```

退出码三档：`0` 综合分达标；`1` 综合分低于阈值；`2` **装置自己不可信**——
几何自检没过，或排不出来的超过语料的三分之一（那时剩下的不足以代表语料，出分没有意义）。

装置跑的是**产品里那份布局引擎**（`LayoutRequestFactory.FromDocument` → `LayoutJob.ToRequest`
→ `ConstraintLayoutEngine.Layout`），不是另抄一份：抄一份出来，量到的就是抄件的行为。

**语料写死在 `Corpus.cs` 里，不从文件读。** 与覆盖率取证装置的分母同一条口径：
语料是判据的一部分，换一批图就会换一个分数，所以它必须是仓库里的一份确定内容。

节点尺寸固定 80×40（由 `Corpus.Measure` 给），间距取文档声明的那一组（缺省 40 / 70）。
尺寸不固定的话，"同一份语料两次跑出同一个数"就不成立了。

## 三、评分口径

四个维度各回答一个"图看起来糟不糟"的问题，都是**从布局结果直接数出来的**，
不需要人看、不需要模型判、不依赖时钟或哈希顺序。每个维度满分 100，
分是「100 减掉不合格的比例」，所以满分的含义是"这一项一个毛病都没有"。

| 维度 | 权重 | 怎么算 | 满分是什么样 |
|---|---|---|---|
| 重叠 | 0.30 | 100 × (1 − 互相压住的节点对数 / 节点两两配对数) | 没有被压住的节点对 |
| 交叉 | 0.30 | 100 × (1 − 互相穿过的边对数 / 边两两配对数) × (1 − 折线穿过节点的边数 / 边数) | 折线之间不互穿，也不穿无关节点 |
| 紧凑度 | 0.20 | 100 × min(1, 参照外接框面积 / 实际外接框面积) | 不比"照实际分层按请求间距排下来"更大 |
| 方向一致 | 0.20 | 100 × 前进边数 / (前进边数 + 后退边数) | 每条边都顺着主方向走 |

综合分 = 0.30×重叠 + 0.30×交叉 + 0.20×紧凑 + 0.20×方向。

**为什么权重这么分。** 重叠与交叉是"一眼就看得出糟"的两项，给最高的 0.30；
紧凑度与方向一致是"整体观感"层面的，给 0.20。四者之和为 1。

### 三条口径上的取舍

**交叉只数真正的穿过。** 判据是"交点落在两条线段各自的内部"。下面三种都不算，
因为它们都不影响"这条线往哪儿走"这个判断，而交叉这一项要量的正是那个：

- **共线压在一起**：从同一个节点出去的多条边常常先共一段再分开，那是一条主干分成几股。
  本仓的路由正是在层间空隙里挑一个通道，同层间的边会共用那一条通道。
- **T 形接上**：一条边的端头顶在另一条的中间，看起来是一个分叉。
- **共用一个端点**：两条边接在同一个节点上。

**紧凑度的参照是"重算一遍最小外接框"，不是"节点总面积"。** 用节点总面积当参照的话，
量到的是"这个图的形状密不密"——十二条分支的扇形图中间本来就空着一大片，
那是形状决定的，不是布局排松了。改用"拿实际分出来的层、按这次请求的间距重算最小外接框"
之后，量到的才是"布局有没有比它该占的地方占得更多"。层号不在布局结果里，
由节点在主方向那个轴上的**区间重叠**聚类得到（同一层的节点被引擎对齐到同一个区间）。

**两个维度量的是图本身的形状，不是布局的毛病。** 方向一致在带回边的图上本来就低，
紧凑度在扇形图上本来就低。报告里逐图列出，看图的人知道低分是哪来的，
而不是以为引擎算错了。

### 几何自检

**一个从没数出过东西的计数器不算验过。** 语料上跑出来交叉是零，那可能是引擎排得好，
也可能是判定写反了——两者在报告上长得一模一样。所以装置每次先拿六组手算得出的线段对
把判定本身验一遍（一组该判成穿过，五组不该），不过就退出码 2、一个分都不出。
本轮：6 组全部通过。

**分数是算出来的，原始数才是可复现的那一份。** 分母一起印出来，是因为"零个重叠对"
在八节点的图与三十节点的图里分量不一样。

**重叠与交叉两项在全部语料上都是满分，这是真话，不是没量到。**
重叠是布局引擎的硬保证（让位在每一层内一次扫描完成，层与层之间本来就不同位置）；
交叉低是因为路由在层间空隙里挑一个通道，同一层间空隙里的边共用那一条通道，
于是没有两条边会真正穿过。两者都有回归网的意义：改坏了立刻掉分。

**紧凑度是这一轮唯一有区分度的一项**，从 58.8 到 90.3。最低的两份是 `k33`（九条边
挤在同一个空隙里，拐点只有那一处可用，外接框被撑开）与 `same-rank`（同层约束把两个
节点绑在一起，层内跨度变大）。

## 六、发现：带环的图排不出来

**`cycle-4`（四节点环）在布局引擎里直接抛异常，不是排得难看，是根本排不出来。**

```
排不出来的（1 份，不计入综合分）：
  cycle-4（四节点环，带回边）：DagreException
    Cannot set a named edge when isMultigraph = false
```

异常来自 `Acyclic.Run`——引擎的**去环**那一步：它要把成环的边反向，反向时给边起了个名字，
而这个 Dagre 封装的图**没开多图模式**，于是直接抛异常。也就是说：**只要图里有环，
布局就整个失败**，与环的大小、位置无关。

**这不是边角情形。** 流程图上"重试"就是一条回边，而本仓自己的 DSL 语法文档里那段
完整示例（`bad -> input "重试"`）就是一份带环的图。这条路径目前的表现是布局失败，
而不是排出一个绕回去的图。

**这一条不在本任务的范围内**（P5-01 是评分装置，不是修引擎），所以只如实记下来：

- 装置把它单列在最前面，且**不计入综合分**——"能不能排"与"排得好不好看"是两个问题，
  混在一起的话，一份排不出来的图会把平均分拖下去，而读的人从分数上看不出是哪一种。
- 装置另有一道保险：排不出来的**超过语料的三分之一**时不出分（退出码 2），
  免得一个只覆盖一小半语料的分数被当成结论。
- 修它要动 `DuetDiagram.Layout/Internal/EngineAdapter.cs`（开多图模式，或自己去环），
  并且要有自己的用例与取证——那是另一条任务。

## 七、与任务清单的出入

1. 任务卡的 `files.create` 列了 `LayoutScore.csproj` / `Program.cs` / `Rubric.cs` 三份，
   实际多了 `Corpus.cs`（种子语料）。语料与评分口径是两件事，放在同一个文件里会让
   "改语料"与"改判据"看起来是同一种改动——而它们的后果完全不同。
2. 退出码除了 0 / 1，多了 2（装置自己不可信）。任务卡只写了 0。
3. `--dump` 与 `--ratings` 两个开关是卡里没写的。前者是"分数对不上直觉时看坐标"，
   后者是卡里那条"要与一小批人工评分对照"的落点。
4. 语料 11 份里有 1 份排不出来（见第六节），而卡里的验收写的是"给出综合质量分 ≥ 85"——
   装置给得出，但语料里那一份的失败是这一轮最值得记的发现。
