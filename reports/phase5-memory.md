# Phase 5 内存预算

- 测量时间：2026-09-26
- 测量机器：AMD Ryzen 5 6600H（6 物理核 / 12 逻辑核），联想 21D0，16 GB，无独显
- 运行时：.NET 10.0.11，x64 RyuJIT（x86-64-v3），.NET SDK 10.0.303
- 用途：Phase 5 判据「内存 < 500MB」的取证（大文档 + 千节点场景的峰值工作集）

## 复现

```bash
# 逐档量工作集，并核两处「有上限」的设计。退出码 0 达标 / 1 超预算 / 2 装置自己不可信
dotnet run --project tools/MemBudget -c Release

# 换规模（默认千节点场景 1000、大文档 5000）
dotnet run --project tools/MemBudget -c Release -- --nodes 1000 --big 5000
```

## 量的哪一段（口径写死）

### 一、工作集，不是垃圾回收的已提交字节

读数是 `Environment.WorkingSet`——进程当前映射了多少物理内存。另一份数（`GC.GetTotalMemory`）
只在核有界性时用，两个数在报告里分开列，不混着说。

不拿已提交字节当判据：它只说明托管堆要了多少地址空间，既不含原生字体、布局引擎的内部结构，
也不说明那些页有没有真的落在物理内存里。用户在意的是「这个进程占了我多少内存」，那是工作集。

### 二、峰值靠后台采样，不靠操作前后各读一次

峰值出现在操作的中途——分配完中间结构、还没把它们丢掉的那一刻。前后各读一次读到的是两头都安静的值，
恰好把要量的一段漏掉。所以装置起一条后台线程按 2 毫秒采一次，取这一段里的最大；
再和「操作结束那一刻的读数」取大者，免得操作短于一个采样间隔时峰值读成零。

### 三、逐档增量，不比绝对值

表里每一档先记基线再记峰值。绝对读数里含运行时自己那二十几兆，把绝对值当结论的话，
换一台机器、换一个运行时补丁，同一个实现的「内存占用」就会变，而它一行代码都没动。

每档开始前强制回收一次，让各档的基线可比。不回收的话，上一档留下的垃圾会算进这一档的起点，
表上会出现「增量是负的」这种读不懂的行。

**增量是这一档把进程推到多高，不是这一档新分配了多少。** 两者在高分配、低存活的操作上差得很远——
「重建索引 20 次」那一档增量 15.5 MB，而托管堆一点没涨，那 15.5 MB 全是还没被回收的垃圾。

### 四、有界性用「再做一遍还涨不涨」判

总数好看不能说明某处有界：一个每次换文档都多留一份索引的实现，在千节点上多出来的那点内存
会被运行时自己的开销盖住，而它在大文档上迟早会暴露。所以那两处单独核，判据是「不再增长」：

- **版本日志**：写两批、每批 500 条（远超它自己的上限 100 条），比第二批前后；
- **视口索引**：换一份新的、把旧的丢掉，反复 20 次，比前后。

两处都读托管堆，且读之前做一次强制回收并把大对象堆压实一次。压实那一下是必要的：
不压实的话，一次大分配留下的空段会一直挂着，读数比真实的存活对象高出一截，
而那一截随上一档做了什么而变——同一个检查在两轮里会给出差一倍的两个数。

容差取 2 MB 而不是零：强制回收之后仍有字符串驻留、即时编译后的代码页、
垃圾回收自己的段这些不会退回去的东西，取零会让这一条在任何机器上都不成立。

规模：大文档 5000 节点 / 4929 连线 / JSON 1.0 MB 字符；千节点场景 2968 条绘制指令、
1968 个元素（1000 节点 + 968 连线）、末次查询剔除率 81.8%。

**千节点场景走的是产品默认那一档预算**（结构变更 800 毫秒），所以那一档的内存对得上用户改一下文档
实际会走的路径。大文档那一档要给更长的预算，理由见下面那条发现。

剔除率 81.8% 与帧率报告里的 86.3% 不是同一个测量点：帧率那一档把视口缩到内容面积的十二分之一，
这里视口是固定的 1920 × 1080、不缩放，内容 3728 × 3434 之下看得见约六分之一。
两个数都对，但比较它们没有意义。

## 两处有界性的证据

| 检查 | 判据 | 实测 |
|---|---|---|
| 版本日志条数封顶 | 写 1000 条之后队列是 100 条 | **100 条**，与 `VersionLogLimits.MaxEntries` 一致 |
| 日志写满之后不再增长 | 第二批前后托管堆不再涨 | 9.9 MB 对 9.9 MB，涨 **0.00 MB** |
| 换索引不累积 | 重建 20 次前后托管堆不再涨 | 9.9 MB 对 9.9 MB，涨 **−0.03 MB** |

两处的实现各自只有一处上限：`VersionLog` 入队之后按 `MaxEntries` 出队（100 条），
每条还会在超过 `BulkChangeThreshold`（100 条变更）或 `MaxAffectedPerEntry`（200 个元素）时
被裁成批量变更、只留原始条数；`CullingIndex` 建好之后只读，三个查询缓冲在每次查询时先清空再用。

装置写进去的每一条都压在两个降级阈值之下（50 条变更、20 个元素），
所以量到的是**队列长度**这个上限，而不是「一条被裁成了批量变更所以本来就小」。
裁掉明细那条路径由它自己的用例守，不在这里重复。

## 发现：5000 节点的图排不出来，而光是试着排就吃掉 96 MB

大文档那一档的布局**失败**了，装置把它照实报出来：

```
大文档布局 失败（Full 超时 304 ms，DropAll 超时 155 ms，PureAuto 超时 155 ms）
```

四次运行都一样，逐级超时。原因在降级计划里：**每一级都有自己的预算，而且那个预算是硬上限**
（`levelBudget = min(remaining, entry.Budget)`，见 `LayoutCoordinator` 的那一行）。
缺省计划是 Full 300 ms、DropLlm 200 ms、DropAll 150 ms、PureAuto 150 ms，
合计 800 毫秒——**调用方给多长的总预算都改不了这个上限**。

这一档特意给的是手动重排那一档（2000 毫秒），也就是用户点「重试」能拿到的时长。
它没用：Full 那一级照样只拿到 300 毫秒，试了 304 毫秒之后被放弃，后面几级同理。
**用户点多少次重试都不会有不同结果**，因为重试改的是总预算，而卡住的是分级预算。

另外 `DropLlm` 那一级根本没试——没有模型提出的约束时，它与上一级的输入完全相同，
协调器直接跳过。四次运行都只看到三级，就是这个原因。

这条发现与本轮的判据没有直接关系（判据量的是内存），但它决定了这份报告能覆盖到哪里：

- **大文档的「载入」路径量到了**：IR 17.6 MB、JSON 6.0 MB、反序列化 7.6 MB；
- **大文档的「画出来」路径量不到**：没有绘制列表，因为布局给不出坐标。
  5000 节点的绘制列表会有多大，这一轮**没有数**，不猜。

还有一件值得记的事：**那一次注定失败的布局，自己吃掉了 96 MB**（峰值增量），
是整个装置里最大的一笔。它分配完中间结构、跑到超时被放弃，那些结构等着垃圾回收。
一份排不出来的图，用户看到的是「布局失败」，而进程已经为它花掉了比成功路径更多的内存。

## 已知取舍与未验证

| 项 | 说明 |
|---|---|
| 大文档的绘制列表没有数 | 5000 节点排不出来（见上），所以「一份大图摆在屏幕上要占多少」只有千节点那一档的 32.7 – 36.9 MB，再往上没有实测。按节点数外推是猜，不写进结论 |
| 峰值里有垃圾 | 峰值 139.1 – 140.5 MB 里含相当一部分是还没回收的垃圾（「大文档布局」那一档尤其明显）。判据读峰值是有意的——用户遇到的卡顿与换页看的是峰值，不是回收之后的存活量 |
| 大文档的规模是本仓定的 | 5000 节点 / 4929 连线。方案没写「大文档」是多大，取这个数是因为它明显超出千节点那一档，同时还在本机能跑完的范围内 |
| 只量了工作集，没量托管堆上限 | `--gcHeapHardLimit`、容器内存限额这些都没碰。真要判「在 512 MB 的容器里跑得起来吗」，得在受限环境里跑，不是在本机读一个数 |
| 版本日志只量了「压阈值之下」的条目 | 每条 50 条变更 / 20 个元素。裁成批量变更那条路径（几万条变更一次导入）没有在这里量，它由 `DuetDiagram.Core.Tests/VersionLogTests.cs`（`Category=DiffBoundary`）守 |
| 视口索引只量了「换掉旧的」 | 增量更新没做（整份重建），所以「旧的那份能不能回收」就是全部的有界性问题。哪天真做增量更新，这一条要重做 |
| 滚动只在一个缩放下量 | 与帧率那一档同一条限制：换个倍数数字会变 |
| 跨机器与跨平台 | 只在本机量过。原生编译（AOT）下的工作集没有量——本机缺 C++ 工作负载，见 `reports/phase0a.md` |
| 装置与语料的关系 | 网格语料与帧率基准是**同一种形态**（每层并列、层间连同序号），但代码各写一份：装置进不了那个程序集的私有生成器。两份只要有一处改了尺寸或标签，内存数字与帧率数字就不再描述同一张图 |
