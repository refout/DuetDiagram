# Phase 5 冷启动

- 测量时间：2026-09-26
- 测量机器：AMD Ryzen 5 6600H（6 物理核 / 12 逻辑核），16 GB，系统盘 Micron MTFDKBA512TFH NVMe SSD
- 系统：Windows 11 专业版 10.0.26200
- 运行时：.NET 10.0.11，x64 RyuJIT，.NET SDK 10.0.303
- 发布方式：框架依赖（`dotnet build -c Release` 的输出），**不是原生编译**
- 用途：Phase 5 判据「冷启动 ≤ 2s」的取证（进程创建 → 首帧可交互，逐段可追）

## 复现

```bash
# 先构建界面程序（装置不会替你构建，找不到就退出码 2）
dotnet build DuetDiagram.slnx -c Release

# 冷启动取证。退出码 0 达标 / 1 超判据 / 2 装置自己不可信
dotnet run --project tools/StartupBench -c Release

# 换轮数、换「打开文档」那一档的规模、跳过千节点观察项
dotnet run --project tools/StartupBench -c Release -- --runs 5 --nodes 200 --no-big
```

装置每轮起一个**全新的界面进程**，量到那个进程把首帧画完并上屏为止，再把界面自己写出来的逐段读数读回来。

两次之间差 6 ~ 45 毫秒，千节点那一档波动最大，而它离判据也最近（93% ~ 95%）。

## 量的哪一段（口径写死）

### 一、终点是「首帧画完且窗口已经上屏」，不是「main 返回」

判据要的是「可交互」，而 `main` 返回时窗口可能还没建起来，窗口 `Show` 完时图还没画出来。
两个都比用户实际等的短。所以收工的条件是两个：画布**真的消费掉一份非空绘制列表**，并且窗口**已经上屏**。

上屏之前画的帧不算。窗口还没出来时画的那一帧，尺寸与内容都未必是最终的，
把它当终点会得到一个偏小的读数，而它偏小的原因跟实现快慢无关。

界面自己写出来的旁证也在报告里：首帧消费掉的绘制指令条数、画布尺寸、窗口客户区尺寸。
只报一个总时长的话，读的人没法判断它是「画完了」还是「空窗口上屏了」。

### 二、表在起进程之前开始走，界面自己的读数分开列

墙上时钟由装置看：起进程之前开始走，看到界面的收工标记再停。它从**进程创建**算起。

界面自己的读数从它的入口算起，两者之差就是「运行时装载 + 把入口方法编译出来」那一段（表里的「运行时」）。
两个数分开列而不是取一个：合起来读的话，运行时装起来那一段会被算进界面自己的代码，
而换一个发布方式（原生编译）改的恰恰是那一段。

### 三、每轮都是新进程

同一个进程里开第二个窗口量到的是热路径——绘制列表、字体、即时编译后的代码都在缓存里。
冷启动要回答的正是这些缓存还是空的时候要等多久，所以每轮起一个新的界面进程。

### 四、第一轮与其余各轮分开报

第一轮的状态与后面几轮不同，把两者平均掉会把「第一次打开要多久」这个最要紧的读数抹平。
表里两栏都给：`第一轮` 与 `中位数那一轮`。

**但本机的第一轮并不是操作系统意义上的冷启动**，见下面那条取舍。

### 五、逐段读数由界面自己写文件

从外面只能看到「窗口出现了」这一个外部迹象。拿它当终点的话，量到的是装置轮询的准确度，
而不是界面的速度——而判据要的是后者。

## 判据要求的四段落在哪里

| 判据里的段 | 报告里的段 |
|---|---|
| 加载 | 运行时 + 平台 + 文档（+ 反序列化，读文件时） |
| 反序列化 | 反序列化 |
| 首布局 | 首布局（含首份绘制列表） |
| 首渲染 | 首渲染 |

段比判据细，是因为判据那四段里「加载」把三件不同的事装在一起：
运行时装起来、界面框架装起来、文档到手。它们各自的开销来源不同，能改的余地也不同。

## 发现

### 一、最大两块不是我们的代码

平台初始化（367 – 395 ms）与窗口上屏（374 – 382 ms）合计约 760 毫秒，占总时长的一半，
而且**三个场景里几乎一样**。一个是界面框架把自己装起来，一个是操作系统把窗口显示出来。
想在这两段上再快，改的不是布局或绘制，而是换框架、换窗口创建方式——那已经超出本轮判据的范围。

### 二、「文档」那一列在不同场景之间不可比

默认文档那一档，平台 + 文档 = 893 ms；打开文档那一档，平台 + 文档 + 反序列化 = 905 ms。
差的 12 ms 说明两件事：样本文档是在界面里现造的，读文件那条路是在入口里先反序列化好的；
**同一批代码路径（尤其是即时编译）只是被记在了不同的段里**。

所以比较「文档」这一列在不同场景之间的大小是没有意义的。要么比总账（1634.8 对 1580.3，差 3%），
要么比同一场景的不同轮次。

### 三、首布局与规模弱相关，首渲染强相关

| 场景 | 首帧指令条数 | 首布局 | 首渲染 |
|---|---:|---:|---:|
| 默认文档 | 17 | 101.0 | 47.1 |
| 打开文档 | 585 | 107.4 | 73.8 |
| 打开大文档 | 2968 | 153.9 | 246.9 |

首布局那一段主要是一次性的开销——即时编译与首次字体度量。指令条数从 17 涨到 2968（175 倍），
首布局只多了 53 毫秒。首渲染那一段的活儿与指令条数成正比，所以它从 47 涨到 247。

这条与帧率报告对得上：`reports/phase5-fluency.md` 量的是稳态每帧，这里量的是第一帧。

### 四、第一轮与后面几轮几乎没有差别

默认文档那一档，第一轮 1598.8，其余四轮 1571.1 – 1580.9，差 18 毫秒。
说明这一轮量到的**不是**「磁盘缓存还是空的时候」——装置跑在刚构建好的输出目录上，
那几百兆程序集早就在缓存里了。真正的冷启动没有做，见下一条。

## 已知取舍与未验证

| 项 | 说明 |
|---|---|
| 没有真正的冷启动 | 清空系统文件缓存要管理员权限，本机没做。表里的「第一轮」是装置自己的第一轮，不是操作系统意义上的冷启动。真冷启动的数字会比这里大，大多少**没有量** |
| 只在这一台机器、这一块磁盘上量 | Ryzen 5 6600H + Micron NVMe SSD。机械硬盘上「运行时」与「反序列化」两段会明显变大（要读几百兆程序集），那两段没有在机械硬盘上量过 |
| 没有量原生编译（AOT）下的启动 | 本机缺 C++ 工作负载（见 `reports/phase0a.md`），量的是框架依赖发布的那一份。原生发布没有运行时装载与即时编译，「运行时」那一段应当基本消失，但那是推断，不是实测 |
| 窗口真的会弹出来 | 每一轮都在屏幕上开一个 900 × 600 的窗口，画完首帧立刻关掉。测量时机器若在做别的事，窗口合成会被拖慢，而那一档会计进「上屏」——第 4 轮的运行时 74.3 ms 与总计 1658.9 ms 多半就是这个 |
| 「可交互」是推断出来的 | 判据停在「窗口已上屏 + 首帧消费掉一份非空绘制列表」，**没有真的合成一次指针事件打进去**。合成指针事件要造出输入参数，而那些类型在界面程序集里没有公开的构造入口。要真正证「能收指针输入」，得在无头测试里合成事件，那一条在 `DuetDiagram.E2E.Tests` 里，不在这里 |
| 「运行时」那一段含管道延迟 | 收工标记要经标准输出管道回到装置，读数里含管道与线程调度那几毫秒。两秒的判据之下可以忽略，但拿这个数去比十毫秒级的差异就不行 |
| 千节点那一档只是观察 | 不计入判据，只跑了一轮。它是本轮唯一接近判据的读数（用掉 93%，另一次运行 95%），但没有单独为它定口径 |
| 文档规模是本仓定的 | 200 / 1000 节点，网格形态。方案没写「一份普通文档」是多少个节点 |
| 首帧尺寸是窗口的最终尺寸 | 判据要求「上屏之后画的帧才算」，所以量到的是 900 × 600 下的那一帧。窗口若在首帧之后被改尺寸，那一次重画不在读数里 |
| 装置与语料的关系 | 网格语料与帧率、内存两个装置是同一种形态，但代码各写一份：装置进不了那个程序集的私有生成器。三份只要有一处改了尺寸或标签，三份报告就不再描述同一张图 |
| 这条判据不覆盖热路径 | 连续帧与拖动在 `reports/phase5-fluency.md`，内存峰值在 `reports/phase5-memory.md`。这一份只回答「从双击图标到图出来」 |
