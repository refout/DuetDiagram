## 判据 1：布局评分 ≥ 85

**结论：语料综合分 96.6（阈值 85），退出码 0。简单平均 95.7，最低一份 91.8。**

- 验的是 `tools/LayoutScore`（不进 `DuetDiagram.slnx`，与 `tools/LocCounter` 同口径）：
  语料写死在 `Corpus.cs`（十份：链、分层网格、菱形、分叉、树、扇出、完全二分、同层约束），
  四个维度与权重写死在 `Rubric.cs`（重叠 0.3 / 交叉 0.3 / 紧凑 0.2 / 方向 0.2），
  跑的是**产品里那份布局引擎**，不是另写一份。
- 复跑：`dotnet run --project tools/LayoutScore -c Release`（退出码 0 达标 / 1 低于阈值 / 2 装置自己不可信）。
- 几何自检先跑一遍：6 组线段对全部通过——交叉那一项的判定本身先被验过，
  否则"零交叉"可能只是判交叉的代码坏了。
- 结论与逐图数据在 `reports/phase5-layout-score.md`。
- **一处如实记下：带环的图排不出来。** 去环那一步给反向边起名，而图没开多图模式，
  引擎直接抛异常。流程图上"重试"就是一条回边。装置把它单列在最前面、**不计入综合分**，
  所以 96.6 这个数是"排得出来的那些"的分。
  **已被取代（2026-09-30）：** P5-14 打开了引擎的多图模式，这一条修掉了。
  语料 11 份全部排得出来，综合分 95.9，逐图数据与证伪见
  `reports/phase5-layout-score.md` 的第八节。回边在层间走的那一段仍会压到中间层的节点，
  那是另一条待办（见「遗留」）。
- **与人工评分的对照未验**：装置支持 `--ratings` 读一份人工评分来算一致率，但那一侧没有数据。
  所以 96.6 是装置自己的分，不是"和人评的一致"。

## 判据 2：1000 节点流畅

**结论：虚拟化帧率均值 137.3 帧每秒（判据 ≥ 30）、剔除率 86.3%（判据 > 80%）、
拖拽单帧处理中位 0.290 ms（判据 ≤ 16 ms），两条命令退出码都是 0。**

- 不另造装置，量的就是 P2-03 / P2-06 落地的那两条基准：
  - `dotnet run --project DuetDiagram.App -c Release --no-build -- --benchmark-frames --nodes 1000 --frames 120`
  - `dotnet run --project DuetDiagram.App -c Release --no-build -- --benchmark-drag --nodes 1000 --samples 200`
- 本次读数（1000 节点 / 968 连线 / 2968 条绘制指令）：

  | 档 | 每帧均值 | 每帧中位 | 折合帧率 |
  |---|---:|---:|---:|
  | 未优化（回退档，只作对照） | 43.66 ms | 39.14 ms | 22.9 / 25.6 帧每秒 |
  | 虚拟化（判据读这一档） | 7.28 ms | 5.17 ms | **137.3 / 193.5 帧每秒** |

  剔除率 86.3%（2968 条指令里只画 406 条）。拖拽：中位 0.290 ms，最大 3.368 ms。
- 口径（帧率取**均值**不是中位、剔除率按**指令条数**不是面积、视口取十二分之一、
  拖拽只量帧首那一次偏移）写死在 `reports/phase5-fluency.md` 里。
- **顺带查实一件事：`reports/phase2-drag.md` 记的拖拽中位 11.321 ms 复现不出来。**
  把那份报告所属的提交检出到临时工作树里重建，同一台机器上量出 0.310 ms，
  而 `RunDrag` / `BeginFrame` / `Shift` 与那个提交逐字相同。记成不可复现、不改正文数字，
  只在它的表里加一行指向 `reports/phase5-fluency.md`。
- 本机是**无独显的软件光栅化**，所以这些是"这套实现能跑多快"的读数，不是产品保证值。

## 判据 3：内存 < 500MB

**结论：峰值工作集 146.4 MB（判据 < 500 MB，余量 3.4 倍），退出码 0，两处上限都成立。**

- 验的是 `tools/MemBudget`（不进 sln）：逐档量进程工作集（后台 2 毫秒采样取峰值），
  并单独核两处"有上限"的设计。
- 复跑：`dotnet run --project tools/MemBudget -c Release`（退出码 0 达标 / 1 超过 500MB / 2 装置自己不可信）。
- 逐档（增量是这一档把进程推到多高，不是这一档新分配了多少）：

  | 档 | 增量 |
  |---|---:|
  | 大文档 IR | 17.6 MB |
  | 序列化 | 5.9 MB |
  | 载入（反序列化） | 7.5 MB |
  | 大文档布局 | 102.0 MB |
  | 千节点布局 + 绘制列表 | 40.8 MB |
  | 建视口索引 | 1.2 MB |
  | 滚动 200 次 | 0.1 MB |
  | 版本日志前 500 条 | 4.8 MB |
  | 版本日志再 500 条 | 4.5 MB |
  | 重建索引 20 次 | 15.8 MB |

  两处上限：版本日志写满 1000 条之后队列里是 100 条（上限 100 条）；
  托管堆在第二批前后 9.9 MB 对 9.9 MB（涨 0.00 MB），重建索引 20 次前后涨 −0.03 MB。
- **一处如实记下：5000 节点的图排不出来。** 降级计划每一级各有预算且是硬上限
  （缺省合计 800 毫秒），调用方给多长的总预算都改不了它，**用户点「重试」也不会有不同结果**；
  而那次注定失败的布局自己吃掉了 96 MB，是整个装置里最大的一笔。
  装置照实报出来且不打断整轮测量，见 `reports/phase5-memory.md`。

## 判据 4：冷启动 ≤ 2s

**结论：默认文档中位 1587.3 ms、打开一份 200 节点文档中位 1635.0 ms，都达标，退出码 0，余量两成。**

- 验的是 `tools/StartupBench`（不进 sln）：每轮起一个**全新的界面进程**，
  量到**首帧画完且窗口已上屏**为止——判据要的是"可交互"，
  只量到 `main` 返回或窗口 `Show` 是假的快（前者窗口可能还没建，后者图还没画出来）。
- 复跑：先 `dotnet build DuetDiagram.slnx -c Release`，再 `dotnet run --project tools/StartupBench -c Release`。
- 本次读数（每场景 5 轮，每轮新进程）：

  | 场景 | 第一轮 | 中位数 | 最小 / 最大 |
  |---|---:|---:|---|
  | 默认文档（不读文件） | 1622.5 ms | **1587.3 ms** | 1578.9 / 1622.5 |
  | 打开文档（200 节点，读文件 + 反序列化） | 1636.7 ms | **1635.0 ms** | 1631.1 / 1640.9 |
  | 打开大文档（1000 节点，观察项、不计入判据） | 1880.8 ms | 1880.8 ms | — |

- 逐段读数由**界面自己写文件**（`--startup-probe <路径>`，五处打点：`Program.Main` 入口、
  `DocumentLaunch.File` 之后、`OnFrameworkInitializationCompleted`、会话构造里首布局之后、画布首帧）。
  从外面只能看到"窗口出现了"这一个外部迹象，拿它当终点量到的是装置轮询的准确度，而不是界面的速度。
- 三条发现（详见 `reports/phase5-startup.md`）：
  **最大两块不是我们的代码**（平台初始化 367 ~ 395 ms、窗口上屏 374 ~ 382 ms，
  合计占总时长一半且三个场景几乎一样）；**「文档」那一列在不同场景之间不可比**
  （同一批代码路径只是被记在了不同的段里）；**首布局与规模弱相关、首渲染强相关**
  （指令 17 → 2968 条，首布局 101 → 154 ms，首渲染 47 → 247 ms）。
- **两处如实记下：这一轮量的不是操作系统意义上的冷启动**（清空系统文件缓存要管理员权限，本机没做；
  装置跑在刚构建好的输出目录上，那几百兆程序集早在缓存里了），
  **也不是原生编译下的启动**（本机缺 C++ 工作负载）。真冷启动与原生发布会比这个大，大多少**没有量**。

## 判据 5：WCAG AA

**结论：装置能判的那一半齐备（每个交互控件有名字、键盘到得了），另一半未验。**

- 验的是 `Category=Accessibility`（`DuetDiagram.E2E.Tests`，十条）：
  名字齐不齐、名字说得出是哪一个、键盘可达、焦点顺序跟着功能分组、Tab 走遍每一块面板、
  菜单能键盘展开、画布有名字与说明、工具栏与菜单的名字来自注册表、右键菜单条目也有名字。
- 复跑：`dotnet test --project DuetDiagram.E2E.Tests/DuetDiagram.E2E.Tests.csproj -c Release -- --filter-trait "Category=Accessibility"`。
- 命名收成一条路（`Services/AccessibleName.cs` 的 `Set`，**名字为空就抛**），落点 50 处；
  焦点号显式给四段（图层 1000 / 调色板 2000 / 文本预设 3000 / 标签栏 4000）。
  验报告 `reports/phase5-accessibility.md`。
- **这一条判据含三件不同的事，只有前两件装置能判：**

  | 事 | 能不能机验 | 结论 |
  |---|---|---|
  | 每个控件有没有名字、名字说得出是哪一个 | 能 | 通过 |
  | 键盘到不到得了、Tab 走不走得进每一块面板 | 能 | 通过 |
  | 对比度够不够（4.5:1 / 3:1）、读屏软件念出来顺不顺、焦点框看不看得见 | **不能** | **未验** |

- **未验的三项，以及为什么判不了：** 对比度要取每个控件**最终渲染出来**的前景与背景色再算比值，
  而主题里有些颜色是运行期算出来的；读屏体验要真人用讲述人 / NVDA 走一遍；
  焦点可见性要人看（深色主题下够不够显眼）。这三项如实记成未验，**不写成通过**。
- 四个只收指针的样式按钮（富文本编辑器的加粗 / 斜体 / 下划线 / 删除线）刻意不接收焦点——
  它们读的是编辑框**此刻的选区**，焦点一挪走就读不到那一段了。名字照样有，键盘到不了，留给人工验收。

## 判据 6：i18n 预留

**结论：机制落地、75 条键已迁、换语言菜单与面板标题真的会变、RTL 不破版；其余约 700 处未迁。**

- 验的是 `Category=I18n`（`DuetDiagram.E2E.Tests`，十条）：键与代码逐键对照、
  每个属性都取得到、注册表那几个文件里没有硬编码界面文字、标记里没有剩下的可见中文、
  换语言之后菜单与面板标题真的变、第二语言里缺的键回落中性资源、认不出的语言代码被拒、
  档的标识不随语言变、两处界面同一条目显示同一个字、从右到左是同一份布局绕竖中线翻过来。
- 复跑：`dotnet test --project DuetDiagram.E2E.Tests/DuetDiagram.E2E.Tests.csproj -c Release -- --filter-trait "Category=I18n"`。
- **这一条与卡片口径有一处实质差别，原因是环境而不是取舍。** `InvariantGlobalization=true` 写在
  **根目录的构建属性**里，全仓生效；实测 `new CultureInfo("en-US")` 直接抛 `CultureNotFoundException`，
  `CurrentUICulture` 永远是不变量。所以：一、按文化切语言**物理上做不到**（卡里写的是"切换文化后…"）；
  二、卫星程序集**永远选不出来**（卡里的 `Strings.zh-CN.resx` 会是死重量），
  第二个语言改成嵌进主程序集、按显式代码选。做法与遗留清单在 `docs/Internationalization.md`，
  取证在 `reports/phase5-i18n.md`。
- **只做到一部分：** 75 条键已迁（菜单这一条链、各面板静态标题、四个对话框），
  而 `DuetDiagram.App` 里带中文的字符串字面量有 1125 处（去掉异常消息 936 处，
  再去掉装置与命令行输出 778 处）。卡里 `estimated_loc: 260` 覆盖不了，
  按仓里已有的"收窄 + 记下理由"先例收窄；其余逐类列在文档的遗留表里，并给出搬运的做法。
- **顺带查实一件事：从右到左是同一份布局绕竖中线翻过来**，逐块比尺寸与位置都对得上。
  900 × 600 的客户区里左栏本来就装不下（底边落在 298 / 603 / 725 / 725 / 894），
  而那种溢出左右两个方向一模一样，与方向无关——所以判据不是"每块都在客户区里"。

## 能机验的与要人验的

| 判据 | 装置验过 | 要人验 |
|---|---|---|
| 布局评分 ≥ 85 | 综合分 96.6（2026-09-30 起 95.9） | 这个分**符不符合人看着的好看**（与人工评分的对照没做） |
| 1000 节点流畅 | 帧率 / 剔除率 / 拖拽帧时 | 人眼看不看得出卡（软件光栅化下的读数不等于手感） |
| 内存 < 500MB | 峰值工作集 | 长会话下的手感（连续用几小时） |
| 冷启动 ≤ 2s | 首帧可交互 | 双击图标到图出来的体感；原生发布那一档没量 |
| WCAG AA | 名字 + 键盘可达 | **对比度、读屏体验、焦点可见性** |
| i18n 预留 | 换语言真的变、RTL 不破版 | **英文译文有没有母语者校对、排版在别的语言下好不好看** |

## 只有自建用例、没有真人用过的那几条

六条判据目前**全部**是自建装置与用例验的。**没有任何一条是真人通过 GUI 实际用过的**：
没有人用读屏软件走过一遍界面、没有人肉眼核过对比度、没有人真的双击图标计过启动时间、
没有人连续用几个小时看过内存、没有人用英文界面干过活、没有人用从右到左的语言看过排版、
没有人评价过排出来的图好不好看。

这与 P1-14（人工评分）、P2-13（真人数据）、P3-16（真实代理）、P4-22（四条判据）同一类：
**装置齐了不等于测过了**。这一份里六条判据的"通过"都该读成"装置验过了"，不是"人验过了"。
要人看着跑的，列在上面那张表的右栏里。

   - 界面程序的原生发布是 CI 的 `app-and-aot` 那一组里的一步，只在带 C++ 工具链的运行器上才真跑得通。
   - i18n 那一条里，`x:Static` 是**构建期解析**这一点靠"写错成员名就编译不过"旁证；
     真原生发布下没跑过。

   ——**2026-09-28 更正：第一条子项已经补上了。** `tools/StartupBench` 加了 `--native`（只认 RID 目录下
