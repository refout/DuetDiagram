# 任务 DAG

面向 coding agent 的任务描述。**单任务单 PR，不超过 500 行变更。**
人类只写任务、审 PR、做决策。

## 模板

```yaml
id: P0-02                     # 任务 ID，同时是分支名与 PR 标题前缀
title: 一句话说清交付物
phase: 0a                     # 0a / 0b / 1 / 2 / 3 / 4 / 5
status: pending               # pending / in-progress / done / blocked
depends_on: [P0-01]           # 这些任务必须已合并到 main
estimated_loc: 150
files:
  create: [路径...]            # 新建
  modify: [路径...]            # 修改（已存在的）
  test:   [路径...]            # 测试文件
acceptance:
  - command: dotnet build ...
    expect: exit 0
constraints:                  # 本任务不得违反的约束
  - ...
context:                      # 自包含上下文：要读的文档与代码
  - ...
```

## DAG（Phase 0a）

```
P0-01 NuGet 版本核查+锁定 ──┬── P0-02 Avalonia+SkiaSharp AOT 最小应用
                            ├── P0-03 Mermaider Sugiyama 约束验证
                            ├── P0-04 Mostlylucid.Dagre 复合图+AOT
                            ├── P0-05 ModelContextProtocol 传输+initialize
                            └── P0-09 MEAI+MCP 工具共用 PoC

P0-08 LLM 客户端（从 Day 1 并行，不阻塞）
```

**决策门 0** 在 Phase 0a 结束时判定：全绿（按计划）/ 黄（走备选）/ 红（人类决策）。

## Agent 执行流程

1. 读任务 YAML 与它指向的 `context` 文档
2. 检查 `depends_on` 全部已合并到 `main`
3. 从 `main` 拉分支，分支名 `{id}-{slug}`
4. 实现代码 + 测试
5. 本地跑 `acceptance` 全部通过
6. 提 PR：变更摘要 + 验收输出 + 未决问题 + 依赖解锁清单
7. 人类 review（只审不改）
8. 合并后下游任务自动解锁

## 冲突与失败

- 两个 agent 改同一文件：后合并者负责 rebase
- 冲突超过 50 行：人类仲裁
- 失败自动重试 3 次（每次从干净分支），3 次后标记 `blocked`

**四条命令层任务在最前面，因为它们是 P1-03 的遗留。** P1-03 的 `result.remaining_groups`
里记着节点、边、样式、布局、组合、图层、页面、调色板、标签、动作、文档十一组没做。
方案把命令层算在 Phase 1，而 Phase 3 的八个工具全靠它——不补上，`diagram_edit` 与
`diagram_style` 就只能是个空壳。放在 Phase 3 的第一位，是因为它是 Phase 3 的前置，
不是 Phase 1 的收尾。

**但这十一组不是十一条命令。** 起草第一版时照抄了命令清单里那张「计划中」表，
写成了十一条；对着代码核一遍才发现其中九条已经被 P1-05 的字段表吸收——
`set-node-field` 按字段名分发，label、shape、parent、layer、styleToken、style、text、
ports、richText、mathMode、desc、meta 都在它名下，边只有 label 与 style 两个。
判断标准是**被改的值挂在元素上还是挂在文档上**：挂在元素上的由字段表覆盖，
挂在文档子对象上的（`layout`、`palette`）才需要各立命令。
另外两条（`add-edge-waypoints`、`set-edge-route`）与 P2-07 的决定直接冲突：
折点写在 sidecar 的 `pinnedEdges`、不进 IR 也不走命令总线，所以它们不该有命令，
工具层也不该为折点开 action。

**第二轮核下来只剩一条。** 十一组里剩下 `reorder-node` 与 `disconnect-edge` 两条，
而 `reorder-node` 被查出**效果不可观测**：节点集合顺序在三个可能观察到它的地方都不可见——
结构哈希与外观哈希都先把节点按标识排序再遍历，所以次序进不了任何哈希；布局引擎在同层内
按横坐标排序、并列时用标识断掉，所以次序不改变任何坐标；绘制阶段确实按集合顺序出笔，
但布局保证同层不重叠，所以画面逐像素一致。做出来会是一条通过全部测试、却什么都没改变的命令。
它要成为真功能，前提是先给节点加一个 z 序字段并定义它在绘制里的语义，那是 IR 的改动。
所以 P3-01 只做 `disconnect-edge`。

这条比「查字段表」更值得记：**核到「效果有没有人能看见」才算核完**。字段表那一轮解决的是
「有没有别的路做同一件事」，这一轮解决的是「这件事做完了有没有区别」——两个问题都对着代码问，
而只有第二个能挡住一条自洽但无用的命令。

**P3-02 又核掉两条。** 布局那一组原本抄下来八条，其中 `pin-node` / `unpin-node` 站不住：
IR 里没有任何地方能存节点的绝对坐标（`NodeDef` 没有位置字段，`LayoutHints` 的四个列表
全是相对约束），而 DSL 的 `pin` 意图早就落到 sidecar 的 `pinnedNodes` 了。mapper 的注释
把理由写得很清楚——**坐标属于渲染结果**，存进 IR 会让同一份语义在不同机器上产生不同的
文档内容。命令层再立一条 pin 与这条原则直接冲突，同一个节点还会因此有两个固定位置。

这一条与 `reorder-node` 不同：那一条是「做完了没人看得出」，这一条是「做下去会破坏一条
已经定下的原则」。前者要等 IR 加字段，后者要等「坐标算不算文档内容」这个决定。
**两种都归到同一句：任务不能只对着计划核，也不能只对着代码核，还要对着已经定下的原则核。**

**P3-03 与 P3-04 各核掉一条，两条都是「计划写得比代码里的事实多」。**

P3-03 那一组原本抄下来十二条，其中四类组合（分组 / 泳道 / 子流程 / 组合框）的字段形状
完全一样，差别只在类型名——四类各立一条的话，校验、原子性与撤销三套逻辑要各写四遍，
而抄漏的那一遍不会报错，只会让某一种组合在某个入口下改不动。合成一条
`create-composite`，种类由传进来的记录类型表达。另外 `reorder-layer` 差点写成一个
「改集合位置」的命令，而图层集合在视觉哈希里是按标识排序后遍历的——那会是一条
**效果不可观测**的命令，与 `reorder-node` 同一个坑。改的是次序字段。

P3-04 那一组核出的第一条更值得记：起草时按「引用关系总是双向的」这个直觉写了一条约束，
要求 `remove-tag` / `remove-action` 处理「元素上还挂着它」。**这件事不存在**——
标签的成员列表与动作的目标引用都是单向的，被指向的元素上没有回指字段。所以两条命令
都不需要顺带摘掉任何引用。**直觉补上的约束要对着模型核一遍才算数。**

同一次核对还翻出一处真的漏洞：`remove-palette-entry` 的引用者扫描只看了节点与边，
漏了 `TagDef.Color`（那个字段取的就是调色板令牌名）。`add-tag` 落地之前它没有命令能写，
所以漏着不显；落地之后它就成了第三条引用路径。不补的话，删掉一个被标签引用的令牌，
标签的颜色会静默退回兜底值——正是那条命令自己的说明里要避免的那件事。

**P3-05 核的对象换了：不是命令层，是两个依赖的公开接口。**

核出四件事，前三件都是「说明与实现不符」的老毛病——布局引擎那次已经踩过一遍。

一是**参数约束注入 schema 的方式**。方案里那句「参数约束用 JSON Schema 的 pattern 硬约束」
落在实现上有一条直路：依赖库提供了 `AIJsonSchemaCreateOptions.TransformSchemaNode`，
看起来正是为这件事准备的。实测下来它对每个 schema 节点都被调用，但**路径恒为空、
参数特性提供者恒为空**，认不出当前节点属于哪个参数，也拿不到参数上标的约束。
改成在 schema 生成之后按声明方法的参数表回填：确定，且不依赖回调次序。

二是**代理侧与模型侧能不能同处一地**。担心的是一件具体的事：这个仓库的每个工程都开着
裁剪与原生编译分析器，把代理侧的包加进来会不会因为对方的实现方式而报警告。
实测是 0 警告，所以「一份定义、两处派生」可以落在同一个工程里，
不必把派生那一半挪到协议层去。

三是**「四十多条命令」与八个工具的动作表对不上**，而且这是对的。节点与边的属性各合成一条
按字段名分发的命令，所以「改标签」「改形状」「套令牌」「改字号」在命令层是同一条，
工具层不该把它拆回去——拆回去之后同一个效果会有两条路，而其中一条不进结构哈希。

四是**起草时写错的一条验收**。`diagram_layout` 的验收里写着「pin 与 unpin 走命令层」，
而命令层没有这条命令，IR 里也没有能存绝对坐标的地方。这一条留给 P3-08 开工时改。

还有一个决定要记：**八个工具的执行体在这一条里一律返回结构化的「尚未接上」**，
参数表与说明先定死。参数表是接口，分两次定的话先接上的那些调用方要跟着改；
接上时替换的是各自的方法体，参数表不动。

**P3-06 核的是「摘要该从哪儿取数」，核出的结论是「六块里有三块不在 IR 里」。**

方向、节点、边、调色板令牌取自 IR；而**层数、同层分组、锁定列表、最近修改**四样都不在。
前两样要布局求解之后才有，后两样分别落在人工产物与命令总线的版本日志里。
于是摘取的入口收成一个上下文记录，由宿主把这四样喂进来——**缺省时留空，不自己算一个**。
自己按拓扑算层数的话，摘要里的层数与实际画面会各按一套算法，对不上时没有任何东西会报错，
而模型会照着一个错的层数去提要求。

还有两处是「照抄示例会踩坑」的地方。一是**相对时间**：示例里写「2分钟前」，
而相对时间随调用时刻变，不显式收一个参照时刻的话，「同一份文档逐字节相同」这条根本没法验。
二是**示例的次序**：示例里节点是按图的读法排的（入口在前），而归一化要求按标识排。
两处都取了归一化，示例只当格式用。

顺带定下两件与后续任务有关的事：`diagram_read` 的 `pageId` 现在返回「尚未接上」
（页面还没有消费方，认下它而按整份文档回是个静默的错误答案）；
`DiagramToolset.Create` 与 `ToolRegistry.CreateDefault` 从此都要一份上下文，
且工具声明改成实例方法——**上下文不能当声明方法的参数**，那会多出一条模型要填的 schema。

**第三条判断标准到这里成型了。** 前两条是「被改的值挂在元素上还是挂在文档上」（字段表
能不能覆盖）与「这个改动有没有人能看见」（效果可不可观测），这一条是
**「这件事有没有第二个地方能看见」**（悬空引用该留着让人报，还是在这里挡住）。

**P3-07 核的是「十七加七个动作各自落到哪条命令」，核出的结论是「一个动作一条命令，
所以原子性是现成的」。**

「一个工具调用要么全部成功要么全部回滚」这一条不需要额外机制：每个动作只发一条命令，
而命令自己的 `Apply` 已经是原子的。需要跨命令原子的场合现在没有，出现了再说。

核出的第二件事是**参数表不够用**。`add-action` 要的是事件名、动作类型名与目标，
而表里只有 `id` / `label` / `field` / `value` / `memberIds` / `index`。硬塞进 `field` /
`value` 会让那两个参数的说明变成「有时是字段名、有时是事件名」，而说明是模型唯一的依据。
于是给 `diagram_edit` 补了 `event` / `kind` / `targetId` 三个可选参数——**加可选参数是加法，
不是改接口**，已有的调用方一个字都不用改。仍然表达不了的是 `ActionDef.Parameters`，
记成后续接线项。

核出的第三件事是**两套错误码怎么接**。命令被拒时回的是**命令层**的错误码，不是工具层
那一套：这两套分开是因为处置不同（改文档还是改这一次调用），而「命令被拒」说的正是文档里
的值不对。另起一套的话，按命令层错误码建的修复建议表会漏掉所有经由工具层的失败。
出错参数与期望形式这一轮留空，那是那张表自己的活。

还有两处是**「不这么写就会变成空话」**的地方。一是 `set-style` 与 `set-text` 的区分：
两者最终都走 `set-node-field`，靠字段前缀（`style.` / `text.`）分，**前缀检查就是这两个动作
各自唯一的那点语义**，不查的话把 `text.fontSize` 传给 `set-style` 也会成功。
二是样式白名单：令牌表是文档里的数据、进不了 schema，所以只能在执行体里判，
且判不中时要把**可用的令牌列出来**——只回一句「没有这个令牌」，模型只能猜着重试。

**幂等键是这一条里唯一没有现成实现的东西。** 做法是给注册表的 `Invoke` 加一个可选键，
键与结果存在一张容量 128 的有界表里。它**不进参数表**：键是调用侧的属性、与文档结构无关，
进 IR 会让同一份文档在不同调用历史下得到不同的哈希；进 schema 也不行，模型没有重试的概念，
每次都要它编一个键。

**P3-08 核的是「起草时写的两条约束还成不成立」，结论是两条都站不住。**

第一条是**「pin 与 unpin 走命令层」**。命令层没有这两条命令，IR 里也没有能存绝对坐标的地方
（`NodeDef` 没有位置字段，`LayoutHints` 的四个列表全是相对约束），节点的固定位置落在 sidecar
的 `pinnedNodes`。所以连带着起草时写的「pin 与 sidecar 是两回事、合并规则要定死」也不成立——
**只有一处存放处，没有两份要合并**。这一条与折点同一口径：坐标属于渲染结果，
不进 IR；工具层不为它们开 action，开一个的话那条 action 要么绕开总线直接改 sidecar
（撤销栈与广播都不经过），要么给它们立一条命令（于是推翻已有的口径）。

第二条是**「端口要自动解析」**。这件事本身成立，但**它在 P3-07 就做掉了**：
`fromPort` / `toPort` 确实是边上的字段，而 `EdgeFieldValue` 的字段表里只有 label 与 style——
端点四样必须作为一次操作一起生效，逐字段写会在中途留下一条端点对不上的边。
所以 P3-07 的 `connect-edge` / `reconnect-edge` 已经用 `PortParser` 把「标识.端口名」拆开
交给重连类命令了，而 `diagram_layout` 与 `diagram_composite` 的参数表里根本没有端点。
起草时把这条挂在 P3-08 名下，是因为那时还没核过 P3-07 会做到哪一步。

核出的第三件事是**归属方要由工具层定死**。命令层要求显式给出，理由是给默认值会让模型那条
路径悄悄写出人工归属的约束，而降级时被当成「用户设的」保住。工具层**就是**模型那条路径，
所以缺省写 `llm` 是事实而不是猜测；而 `human` 要拒绝——放行的话模型可以伪造最高优先级的归属，
把用户自己设的约束在降级时挤掉。`auto` 放行：它是更弱的一档，模型表达「这只是个建议」是合理用法。

还有一处是**「重排这件事在这一层验不了」**。命令的 `CommandResult` 报出结构变更，
工具层把它翻译成返回结果里的一个标志，然后就没有然后了——工具层不引布局引擎，
也没有宿主可以回调。所以「改完之后调度了一次重布局」在本工程里只能验到标志为真，
真正的调度在宿主那一侧。

**P3-09 核的是「起草时说的那几样现成能力到底有没有」，核出的结论是「少了一样」。**

起草时写的是「DSL 与 Mermaid 两种文本导出各有用例」，而 `DuetDiagram.Dsl` 只有词法、语法
与语义映射三样，`DslMapper.Map` 是唯一的公开入口，方向是「文本 → IR」——**没有导出方向**。
所以这一条做的实际上只有 Mermaid 一种。

这与「位图还没排到」不是同一件事。位图与 PDF 是 Phase 4 验证的事；而 **DSL 导出是不该现在做**：
DSL 去留那个决策门还开着，判掉之后写出来的导出器要整个删掉。顺带把 `diagram_export` 的说明里
那句「自有 DSL 或 Mermaid」改成只承诺已有的那一半——说明是模型唯一的依据，半个空头承诺
会让它反复试一条走不通的路。

核出的第二件事是**校验的修复建议已经有一处了**。`ValidationIssue.Suggestion` 由整体校验器
逐条给出，那就是「映射表放在一处」里的那一处；工具层再写一张按错误码查的表，
同一个码就会在两个入口给出两种建议。`docs/Error-Codes.md` 里那张表是**界面**怎么呈现，
由 `Category=ErrorPresentation` 逐行核，与工具层无关——两张表名字像，管的事不一样。

核出的第三件事是**撤销重做拿不到「撤掉的是哪一条」**。`Undo()` / `Redo()` 返回的
`CommandResult` 里有受影响标识与两个变更标志，没有命令标识，成功路径上也没有消息。
所以要在动手之前先窥栈顶（`HistoryStack.PeekUndo()` / `PeekRedo()`），从 `HistoryEntry` 上
拿命令标识与会话标识；栈顶那一条的会话与当前会话相同，就说「你自己改的」。
不选「撤销之后去读版本日志」：那条路要多读一份日志，而日志的用途是审计。

还有两处口径在这一条里定死。一是**栈见底不是失败**：`Undo()` 在栈空时返回空操作，
多步时撞上它就是「到头了」，停下并说清实际做了几步——报成失败会让模型以为整条调用没生效。
二是**导出与校验不进动作表**：它们不发任何一条命令，硬塞进那张「动作 → 命令标识」的表里，
逐行核对的用例会要求它们指向「已实现」表里的某条命令，而它们没有。

**P3-10 核的是「起草时说的那张表放在哪儿」，核出的结论是「放不到一处，只能是两张」。**

起草时写的是「错误码到修复建议的映射表放在一处，界面与工具层都读它」。
而 `DuetDiagram.App.csproj` 里**一条到 `DuetDiagram.Llm` 的引用都没有**，
反过来引就成了循环；放进 Core 也不行——Core 只依赖 BCL，而建议里要出现
`diagram_read`、`create-page` 这些工具层与命令层才有的名字，塞进 Core 就是让纯数据层
去认识上层。所以照「同一个形状、两个出口」办：`ErrorPresenterTable` 回答「怎么呈现给用户」，
`RepairHints` 回答「给模型看什么、怎么改」。两张都从错误码出发、各由一条逐行核对的用例兜住，
风险挡在**覆盖**那一层：任何一边漏一个码都会红。

`RepairHints` 比呈现表多覆盖一套码：除了命令层的前置检查，还有工具层的参数校验
（`ToolErrorCodes`）。回灌给模型的失败两条来源都会出现，而界面只看得到前一套。

核出的第二件事是**「可用取值」进不了表**。可用的动作名、样式令牌、字段名、已登记的工具名
都随文档与工具表变，静态表里写不出来，写死了就是错的。它们已经由失败现场填进错误自己的
期望字段（`ActionDispatch.UnknownAction` 填可用动作、`SchemaBuilder.Validate` 填正则与可用参数名、
`StyleResolver.CheckToken` 填可用令牌），所以表里只留两样静态可写的东西：出错参数与一句建议。
信封上的期望形式取失败现场那一份，取不到才回落到表里——顺序不能反过来。

还有两处口径在这一条里定死。一是**回环挂在宿主那一侧**，不挂在 `ToolRegistry` 上：
「同一个错误连着来」与「这一轮试了几次」都是跨调用的状态，而注册表是共享的
（一个进程一份，两个窗口共用一份），挂上去之后一个窗口的错误会算到另一个窗口的账上。
二是**上限数的是回灌次数，不是调用次数**：缺省三次，到上限停下并把整段往返记录
写进应用日志——不设上限的话，一次参数错误会变成无限次调用，而账单上看得出来、日志里看不出来。
判「同一个错误又来了」只比**上一轮**，不比整段历史：中间换过做法之后又绕回原来那一步，
那是另一件事。

**P3-11 核的是「接模型要动哪些依赖接口」，核出的结论是「一处公开委托就够，两处起草假设不成立」。**

起草时列的两项 `files.modify`（解决方案文件、包版本表）都不需要动：没有新工程、没有新依赖，
测试工程经由到 `DuetDiagram.Llm` 的工程引用就取得到 `Microsoft.Extensions.AI` 的类型。

接工具调用循环不用继承依赖里那个客户端类型，它有一个**公开可设的委托**
`FunctionInvoker`，签名是 `Func<FunctionInvocationContext, CancellationToken, ValueTask<object?>>`。
用公开委托而不是继承：继承会把自己的客户端类型钉死在别人的基类上，
而那个基类里真正要用的只有一个受保护的虚方法，升一次大版本就可能改名。

同一处核出的第二件事是**那个委托拿不到 `ToolResult`**：它给的是 `AIFunction`，
而本仓那个包装类把结果序列化成 JSON 才交出去。所以回环这一路回到注册表——
它返回 `ToolResult`，而且与代理侧走的是同一个入口，两条路不会在参数校验上分叉。
参数从调用参数转 JSON 那一步复用包装类里现成的那一段（改成 internal），
两处各写一份的话，某天一边改了转换规则，另一边的参数就悄悄对不上。

上限一共三层，**各管各的**：依赖那两个（一轮往返 40 次、连续失败 3 次）只管停；
我们的回环（回灌 3 次）负责把失败翻成结构化内容、写日志，并用 `FunctionInvocationContext.Terminate`
真正停下这一轮。只少回灌一次内容而不停的话，循环仍由依赖那几十次兜底，
而日志里那句「停下了」就成了空话。

两侧逐字相同这一条**按原文比，不按结构比**。实测两侧的 schema 原文逐字相同
（含可空参数的数组形式 `"type":["string","null"]`）。现有的 `Category=ToolRegistry`
那条按规范 JSON 比，容忍键序与空白差异；新加的这一条按原文比——
「有人把两侧改成各自维护」之后，差异很可能正好出现在键序或空白上，那时结构比较仍然全绿。
数组形式那一条也顺带把 P0-09 留下的「接入外部代理时要实测」变成了一个会红的断言位。

**P3-12 核的是「挂工具要按标注还是按实例」，核出的结论是「按实例，而且会话状态只能逐条现读」。**

按标注扫描静态方法那一套要求参数由服务端容器解析，而标准输入输出这条通路上服务端不持有
容器，非基础类型参数会被当成「必须由调用方提供」的工具参数，调用直接失败——而客户端只看到
「调用出错」，原因只在服务端日志里。挂已经建好的实例没有这个问题，还顺带保证了代理侧与
模型侧是同一份定义（那八条本来就是从模型侧派生的）。

会话状态因此只能**逐条请求现读**，服务端不保存任何上下文。读的位置按
`_meta` → 客户端能力声明 → 扩展位，读不到再落到参数顶层；值的形态三种都要认
（声明上是对象，往返之后是 JSON 节点或 JSON 元素，也可能被对端当成一段文本）。
只认一种的话，症状是「字段明明在、读出来却是空」，既不报错也不抛异常。

起草时说的「声明必须真的接到命令上」在落地时多出一个形状：**读取口是委托不是值**。
工具是按会话建一次、之后一直复用的，存一个值的话第二次调用会拿着第一次声明的版本去比对，
表现是「第一次改得动、第二次改不动」。所以 `DiagramToolContext` 上那个口子的类型是
`Func<VersionCheckRequest?>`，由传输层填；界面那条通路不填，它只有一个写入方。

同一处核出的第三件事是**断言不能按方法名写**。会话建立那一次请求的名字会随协议版本变
（早期叫初始化请求，当前版本换成了服务发现请求），按名字匹配的代码改名之后会静默失效——
服务端不报错，只是那条分支永远不走。所以协议层的断言按「第一条请求」取样本。

**P3-13 核的是「主动推送那条路走不走得通」，核出的结论是「走不通，得换一条」。**

协议那条推送在当前版本下是堵死的，而且不是配置问题：无状态模式明文写着服务端主动发的消息
与所有服务端发起的请求都不支持（理由是响应可能落到另一个进程上），而有状态那条路上唯一能拿到
会话对象的入口是实验性接口、它的空闲超时又被标为过时——本仓把警告当错误，所以那条路连编译都过不去。

于是推送改成一条**独立的变化源端点**：`GET /changes?since=<版本>`，有更新的版本就立刻回，
没有就长轮询等到超时再回空。形状与传输那一节说的长轮询一致，但它不属于协议传输。

同一处核出的第二件事是**只保存最新的一份状态**。断线重连按版本号补差：调用方报上它见过的
最后一版，服务端要么立刻回当前版本、要么等。存通知历史的话，一个断了一小时的调用方会把
这一小时里的每一条都收一遍，而它真正需要的只是「现在是第几版」。

第三件事是**越权的判据只能从请求体里读**，因为工具名只在里面。读之前要开缓冲、读完要复位——
不复位的话协议那一层拿到的是一个已经读空的体，表现是「调用进去了、参数全丢了」。

**P3-14 核的是「§7.4 那张表跟现有实现差在哪」，核出的结论是「差一行，而那一行差得很要紧」。**

`VersionLog.BuildDiff` 的六个分支里有四条与表逐行对上；只有「落在版本日志范围内、但结构哈希
与当前对不上」那一行，它给的是**逐条增量**，而表上写的是全量。按表来：走到那一步说明调用方
声明的结构哈希与服务端对不上，而它的本地副本是否还与它自己声明的那个版本对得上，从这边
无从验证。把字段级的增量按在一份来路不明的副本上，正是产生「静默改错」的方式——改完之后
两边都不报错，而那份图已经与谁都对不上。逐条增量仍然留给界面那条通路，它手里的副本是本地的。

同一处核出的第二件事是**「未声明」那一种原来根本没有落点**。总线上未声明会被判成
「缺少版本声明」，而那个结果里不带任何内容——调用方连「该声明哪一版」都问不出来。
所以传输层要提前判一次：写入工具没带声明时回 409 加一份全量快照。

第三件事是**冲突内容只能落在传输层**。工具调用的失败是协议内的结果，不是 HTTP 状态；
把差异塞进工具结果里的话，「409 + 差异」这条 DoD 就没有落点。而中间件已经为了判越权
读了一次请求体，把声明一起读出来是同一套机器。总线那一道检查仍然说了算——中间件判完之后
到命令真正执行之间还有个窗口，那个窗口里的冲突由总线在门锁内挡下。

第四件事是**图层级的判据必须落到动作上，落不到传输层**。「这次写入点名了哪个图层」藏在
动作参数里：改节点归属时写在 `value` 上，建图层与改图层时写在 `id` 上。传输层要判就得把
这张对照表抄一份，而抄漏的那一格会静默放行——那份图被改了一角，谁都不报错。
于是权限分两档判在两处：粗的那一档在传输层，细的那一档在工具层，两处合起来覆盖全部。

第五件事是**软锁的到期判据只能是「最后一次操作」**。记「拿到锁的时刻加三十秒」的话，
一个每二十九秒动一次的 agent 会被判成过期，而它其实正在写——于是两个 agent 同时以为
自己在改这份文档。释放做成懒的：到期的锁在下一个来拿的人看来就是空的。

**P3-15 核的是「技能扩展在这套实现里落在哪一档」，核出的结论是「落在通用的资源那一档，
而第三层只能是那份文档本身」。**

依赖里那个版本的协议实现里**没有 SEP-2640**（全文搜不到），但它本来就有资源那一档：
清单、读取、内容类型都齐。所以落点是 `WithResources` 加 `McpServerResource.Create`，
URI 的协议名自己定成 `skill://`。等扩展成为标准、或者实现接上之后可以换过去，
URI 与两份正文都不用动。

同一处核出的第二件事是**两条传输都要挂**。只挂一处的话，「两个 Skill 按 `skill://` 取得到」
就成了一条按传输而定的判据——而它读起来像是验过了。

第三件事是**第三层只能是 `docs/DSL-Syntax.md` 本身**。这一条只许在 `Skills/` 下新建两份正文，
而「资源文件才含精确语法」要一份真的语法文件。做法是构建时把它嵌进程序集，不另抄一份：
抄一份两边迟早对不上，而对不上的表现是模型照着一份过期的语法写。
顺带拿真解析器把里面九个 `dsl` 围栏块逐块跑了一遍，全部零诊断——所以判据三直接写成
「每个块交给真解析器，要求零诊断」，那些从来没被验过的例子就此进了门禁。

第四件事是**`skill://` 的路径判据与工作区那道关同一条口径**。前缀比较挡不住 `..`，
也挡不住百分号编码过的 `..`；而直接交给 URI 那一层去解析的话，它自己会把 `..` 规范化掉——
拿它的结果做判断，等于把要判的东西先擦掉了。所以自己切段、先解码再归一，
而**弹到 Skill 名那一层就拒绝**：Skill 名就是这一层的根，越过去之后没有落点。

第五件事是**内部那条通路的入口不认识 Skill 这种类型**。依赖方向是反的（代理那层引模型那层），
所以 `ChatOptionsFactory` 收的是一段纯文本——这一轮匹配上的正文，接在系统提示后面。
选哪一份不在这里：只有调用方知道这一轮要做什么。不传时一个字都不加，缺省就是「这一档不需要」。

**P3-16 核的是「八条判据在这套实现上到底有没有出口」，核出的结论是「有一条没有出口，
而那是实现缺了一块」。**

第一件事是**两条传输回的会话应答不一致**。标准输入输出那条把 `SessionAck` 挂进能力扩展位，
网络那条只挂了服务端信息——同一个客户端换一条传输就读不到应答，而它会以为自己没连上。
修法是把那段选项合成一处（`ConfigureOptions`），两条传输都调它。这与 Skill 那条同源：
「两条传输说的是同一段」这件事不能靠各写一遍来维持。

第二件事是**网络那一档的审计根本没有出口**。命令行起网络服务端时没有传诊断出口，
于是审计与命令层的告警都写进一个丢弃一切的实现——表现是「审计功能已经有了」，
而跑起来一条都读不到。这一条是拿真可执行文件跑才发现的：进程内的用例都传了一个收集器，
所以它一直没露出来。修法是加一个写标准错误的出口并在命令行上接上。

第三件事是**八条判据里有六条只有测试工程的覆盖，没有可人工跑的出口**。用例是给 CI 的，
而报告要的那份「逐条跑一遍」的证据得有个地方出。所以 `tools/McpHarness` 拿真的可执行文件跑：
标准输入输出那条由它拉子进程，网络那条由它带 `--http --workspace --token` 起子进程再连上去——
顺带把 `Program.cs` 那条命令行通路也验了，它在此之前一条用例都没有。

第四件事是**`accepted=false` 在这条协议通路上没有落点**。当前协议版本没有初始化请求，
会话状态随每条请求带上来、服务端每次现读现判，所以不存在「一次协商被接受或被拒绝」。
替代口径是回差异或快照（网络那一档 409 加内容），写进已知差异，**不写成「已通过」**。

第五件事是**多 agent 并发要真的起十个并发调用**。顺序跑验不到版本检查的竞态，
而竞态正是这一条要挡的东西；判据是文档仍然校验通过且版本号单调递增，
不是「没有抛异常」——抛异常那条路早就被挡住了，漏网的是「两个都成功，后一个把前一个盖掉」。
装置与用例都让十个客户端**齐步走**：各自读完版本、都到齐了再一起写，
不然十次写入根本不在同一瞬间，那一档就退化成了顺序跑。

第六件事是**CI 里根本没有 Llm 与 Mcp 两个测试工程**。Test 那一步只列了
Core / Layout / Render / Mermaid / Dsl，Phase 3 的用例一条都不在上面跑。这一条补上了。

第七件事是**依赖验证脚手架用完即删**。`tools/Poc/McpTransport` 与 `tools/Poc/SharedTools`
的题材都被正式工程取代了（前者验「官方实现能不能支撑三种传输与自定义会话字段」，
后者验「一份工具定义能不能两处共用」，结论分别落在真实传输与 `Category=ToolParity` 上），
所以随这一条删掉。`tools/Poc/LayoutCandidates` 不动：它服务的是布局引擎主选那个还开着的决策门。

**核完之后的结果**：八条判据 8/8 通过（装置跑的是真的服务端可执行文件，不是进程内的服务端），
`Category=MultiAgent` 通过，上面那三处缺口都修了；真实代理那一步**未验**。
逐条的观测值、三处缺口的细节、以及真实代理跑不通的证据都在 `reports/phase3-mcp.md`。

## DAG（Phase 4）

方案 §13.8 给 Phase 4 的只有一句话：「图层、页面、形状库、模板、组合（分组/泳道/子流程/
组合节点）、调色板、富文本与数学排版、导入导出。」没有 ID、没有依赖、没有验收。
`P4-01` ~ `P4-22` 这套编号与切分是本仓定的，依据是 §14.3 的 Phase 4 四条判据、
§9 的界面设计与 §19 的可扩展接口。

**切分之前先核了一遍现状**，因为 Phase 3 已经吃掉了一部分题材：P3-02 落了调色板三条命令，
P3-03 落了组合三条与图层三条，P3-04 落了页面两条。核下来 Phase 4 的缺口不在命令层，
在**界面入口与渲染消费**——图层、页面、组合、标签、动作这五样都是「命令能改、画布不认」。
真正从零开始的只有四样：形状库（含自定义形状）、模板、富文本与数学排版、非 Mermaid 的导入导出。

```
P4-01 工具栏与菜单栏骨架 ──┬── P4-03 图层面板
                           ├── P4-07 调色板面板
                           ├── P4-09 形状库与提供者接口 ──┬── P4-10 自定义形状
                           │                              └── P4-11 模板库
                           └── P4-19 导入入口（Mermaid 文件）

P4-02 图层可见性、锁定与渲染消费 ──┘（面板依赖它）
P4-04 页面的元素归属与翻页       （独立）
P4-05 框选与右键上下文菜单       （独立，组合的界面入口）
P4-06 组合的渲染、命中与拖动     （独立）
P4-08 文本样式预设                （独立）
P4-12 富文本内容模型 ── P4-13 富文本排版与渲染 ──┬── P4-14 富文本编辑界面
                                                 └── P4-15 数学排版

P4-16 SVG 导出 ── P4-17 PNG 导出 ── P4-18 PDF 导出（选型验证）
P4-20 DSL 导出                    ── 标 blocked，卡在决策门 1

P4-21 draw.io 覆盖率取证 ── 依赖 P4-06 / P4-11 / P4-15 / P4-18 / P4-19
P4-22 Phase 4 收尾验收    ── 依赖上面全部（P4-20 除外）
```

**P4-01 排在最前面，但它不是别的任务的前置，而是「挂的位置」。** 图层面板、调色板面板、
形状库、模板库都要挂在工具栏或菜单上，而它们各自是独立的界面任务。先把注册方式定下来，
后面每一条才能各写各的文件——不然每一条都要改同一个 `ToolBar.axaml`，两个 agent 同时改
一个文件就是一次冲突。

**P4-01 已落地**：工具栏与菜单栏读同一份条目表（`MenuRegistry.Default`，六档 18 条），
每档一个 `Register` 方法各写各的文件；禁用条目把理由挂在提示上，只读那一句与命令层
拒绝写入时说的是同一句。判据写的是**「要么变了、要么说了话」**，不是「文档版本加一」——
全选、清空选择、重排、把方向设成它已经是的那个，这几条合法地不改文档。
只读时**重排照样点得动**：它不写文档，只是让布局再解一次。

**P4-02 已落地**：图层的可见与锁定各一条命令（`set-layer-visible` / `set-layer-locked`），
渲染层真的照它们办事——**不可见是不画，锁定是画出来但点不中、改不了**。
「画出来但点不中」那份名单挂在绘制列表上（`DrawList.Blocked`），
而不是让命中测试自己去读文档：读文档就意味着「画的是什么」与「点得中什么」成了
两处各自算的判断，而它们迟早会不一致。会话那一层再筛一次选中集合——
全选与撤销之后的重整都走 `SetSelection`，漏掉那一处的话全选会把锁着的元素也选上，
接着一次删除就把它们删了。拒绝锁定的写入报 `LAYER_LOCKED`，
与只读的 `DOCUMENT_READ_ONLY`、凭据的 `LAYER_FORBIDDEN` 分成三个码——
三者的处置分别是解锁、等对方放开、换一份凭据，合成一个的话用户会按一句做不到的处置去办事。

**图层那两条动作没接进工具侧，挂在 P4-03 上。** 核下来代价不在那十几行：
`diagram_edit` 的参数表是冻结的接口（外部代理照着它写代码），而它**没有任何布尔参数**，
两个开关要么新加一个参数、要么把 `value` 当字符串布尔用——两种都是接口层面的决定，
不该夹在一条渲染任务里做。而此刻并不存在「人能关、模型不能」的不对等：人这边的开关要等 P4-03 的面板。

**「组合」拆成两条：入口（P4-05）与呈现（P4-06）。** 命令层在 P3-03 就齐了，
但界面上一个入口都没有——现在只有 LLM 能建分组，人不能。而 §14.3 有一条判据是
「组合全部可用」。两条都落地之后那条判据才有人验。

**P4-11 已落地**：方案对「模板」只写了两个字，形态由这一条的侦察定——
按 draw.io 的语境取「可复用的一份文档片段」。**它是文档片段，不是第二套 IR**：
文件就是一份少了几个集合的文档，读写都走 `DiagramSerializer`，带了模板表达不了的集合
（页面、图层、标签、动作、字体、文本预设、调色板、布局提示）的文件被拒绝而不是静默丢掉。
拼进去是**一条命令**（`insert-template`），先算一份计划再落地，撤销按一次整份退回。
两处判据值得记：**标识冲突要消解且引用跟着改**（只改节点名不改边上的引用，拼进去的是一条
指向旧名字的边），以及**组合的成员表是权威、元素的父级只是冗余索引**——手写模板的人
很自然会只写成员表，于是拼进去时父级由成员表反推；片段里两份对不上时拒绝，
否则拼出来的是一份整体校验报 `MEMBERSHIP_MISMATCH` 的文档。
侦察时还挖出一个更底层的缺陷：源生成的序列化器走全参构造器，手写的稀疏 JSON 里省掉的键
会读成 `default` 而不是声明处的初值，`DiagramDocument` 的构造入口逐字段补齐才修掉。

**富文本拆成四条：模型、排版、编辑、数学。** 四样的失败方式各不相同：
模型错了在序列化上暴露，排版错了只表现为「这几行字看着有点怪」，编辑错了在操作上暴露，
数学排版错了会被当成「语法写错了」。合在一条里做，前三样会互相拖。

**P4-20 标 `blocked`，与 P0-02 那种不一样。** P0-02 卡的是环境缺东西（缺 C++ 工具链），
P4-20 卡的是一个人工判断：DSL 这套格式留不留。留则照做；不留则**这一条不是完成而是删掉**，
连 `DuetDiagram.Dsl` 一起删。`diagram_export` 现在拒绝 `dsl` 那一档，理由正是「去留还没有定论」。

## 任务文件本身要能被解析

它们是给 agent 读的，读不了等于任务不存在。已经踩过两次：
P1-15 的 `expect` 值里有未加引号的冒号加空格，P2-12 的 `followups` 正文里有未加引号的引号。
两次都是整个文件解析失败，而**没有任何东西会报错**——任务就那么静默地消失了。

CI 里有一道门禁拦这件事，本地也可以先跑一遍：

```bash
python -c "import yaml,glob; [yaml.safe_load(open(f,encoding='utf-8')) for f in glob.glob('tasks/**/*.yaml',recursive=True)]; print('ok')"
```

注意以 `*` 开头的列表项会被当成 YAML 别名，以 `` ` `` 开头的会被当成非法记号，整段要加引号。
